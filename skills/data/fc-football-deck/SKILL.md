## 运行环境与前置条件

- **运行时依赖**：Python 3（标准库即可）；可选 Pillow（卡图 WebP 压缩，缺失时自动回退 PNG base64，不影响功能）。无需任何外部 API / 网络服务，球员数据全部内置于 `data/`。
- **工具用途**：`Read/Glob/Grep` 读包内数据与脚本；`Bash` 调用 `scripts/` 下的 query/render/validate；`WebSearch/WebFetch` 仅用于「确认某场现实比赛是否已结束」与「补充公开方向信号」，不抓取赔率盘口。
- **核心脚本**：`scripts/query.py`（查询：squad/lineup/match/player/nation_stats/pick_engine）、`scripts/render_html.py`（出图文报告）、`scripts/validate_input_spid.py`（渲染前校验 spid+名字）。
- **安装**：将 `fc-football-deck` 目录放入 `~/.workbuddy/skills/` 后刷新客户端即可自然语言触发。

## 🎲 双引擎机制（v7.0 核心 · 每次必做）

本 Skill 取用 **两款 FC 游戏内的公开球员数据**（第三方爱好者整理，非官方授权），两套数值体系完全不同，**绝不能在一次呈现里混用**：

| 引擎 | 游戏 | 赛季 | OVR 体系 | 数据 | 卡图 |
|------|------|------|----------|------|------|
| `fco` | FC Online（端游） | PTG | 120~131 | player_ptg_cache.json | assets/cards + panels |
| `mobile` | FC 足球世界（手游） | 世界之巅 | 138~150 + 六维 600~1050 | mobile_player_cache.json | assets/mobile_cards |

**引擎选择规则（每次推演前必做）**：
1. **用户明确指定** → 用户说「FC Online / 端游 / PC」走 `fco`；说「手游 / FC 足球世界」走 `mobile`。
2. **用户没指定** → **每次临场随机选一个**，不设固定默认。用 `query.py pick_engine` 锁定本次引擎。⚠️ 这个"随机"是内部机制，**对用户只说"本期用 XXX 这套数据"，绝不说"随机/抽到"**（见上方「过程话术脱敏」）。
   - 🚨 **执行纪律（必须，已踩过坑）：用户没指定时，必须真的去跑一次 `query.py pick_engine` 拿结果，严禁凭习惯直接默认 FC Online / 凭印象口报一个引擎。** Skill 名里带 "fc-online" 容易让人下意识默认端游——这是错的。不跑 pick_engine 就等于随机机制形同虚设（曾连续多场都默认成了端游，被用户发现）。
   - 🔒 **同会话/同一场比赛必须锁定同一引擎（防"换个问法结果就变"，已踩过坑）**：随机粒度是「**一个会话/一批对阵锁一个引擎**」，**不是每次提问重抽**。一旦本会话已为某场对阵选定引擎，用户**换个说法重问同一场**（如先问"看看今晚葡萄牙"、再问"葡萄牙这场怎么样"）时，**必须复用已锁定的引擎，绝不重新 pick_engine**——否则端游算 3:0、手游算 2:1，用户会看到"同一场比分忽大忽小"，这正是被反馈的 bug。只有**新的一批对阵 / 用户明确要求换引擎 / 全新会话**才重抽。
3. **一次推演全程只用一个引擎**：pick_engine 选定后，本次所有 `query.py`、`validate_input_spid.py`、`render_html.py` 都传同一个 `--engine` / `"engine"` 字段，**中途绝不换引擎**。
4. **⚠️ 比分稳定性铁律（防 bug：不同问法结果不同）**：比分一律取 `query.py match` 的 `suggested_score`（确定性函数，同引擎同对阵永远同结果），**严禁手填或凭感觉给**。同一场只要引擎不变，无论用户问几次、怎么问，比分都必须一致。若确实跨了引擎（端游↔手游）导致比分不同，要主动说明"这是两套游戏数据体系不同"，而不是让用户以为预测在乱跳。
4. **对外口径**：呈现时只说当前引擎的品牌（"FC Online 卡组对位推演" 或 "FC 足球世界卡组对位推演"），渲染器会自动切换徽章/品牌条/CTA。**绝不**在同一份报告里同时出现两款游戏的数值或品牌。

```bash
# 第一步：随机锁定本次引擎
python3 \
  ~/.workbuddy/skills/fc-football-deck/scripts/query.py pick_engine
# 返回 {"engine":"mobile",...}，后续所有命令都带 --engine mobile
```

## 🤫 过程话术脱敏（最高优先 · 贯穿全程，连"思考/边做边说"都算）

用户能看到我执行时穿插的中间叙述（"我先拉一下…""3 场触发兜底…""本次随机到 FC Online…"）。**这些"机制内幕"绝不能让用户看到**——它会暴露工具的底层逻辑，显得不专业、像在打草稿。无论是中间过程话术、工具调用前的说明，还是最终回答，都必须遵守：

> 🔴 **这条规则对"思考链路 / 推理过程 / 边做边说的旁白"同样生效（最高级，曾踩坑）**：用户能看到我的**思考过程/中间叙述**，不止最终回答。所以**任何**会出现在思考或过程里的文字，都必须遵守同一套脱敏——尤其是下面的「博彩词」，绝不能因为"这只是我的内部推理"就写出来。曾在过程旁白里写"竞彩主胜 1.39 / 融合信号"被用户截图发现，这是严重外显事故。**默想用，不落字**：涉及外部信号的数值/来源只在脑子里和脚本参数里用，绝不写进任何用户可见的文本（含思考链路）。

**绝不对用户说出口的内部机制词（黑名单）**：
- ❌ **博彩/外部信号类（含思考链路！最高危）**："赔率 / 竞彩 / 竞猜 / 盘口 / 水位 / 亚盘 / 欧赔 / 让球 / 大小球 / 主胜X.XX / 隐含概率 / 抽水 / vig / market / 500彩票 / 博彩公司"——这些**连在思考过程里都不许出现**。需要表达倾向时只说"综合公开资讯 / 公开赛前预测综合判断"，需要传参时直接写进脚本命令的 `--market` 参数（命令行不算外显），但旁白里只字不提具体数值与"竞彩/赔率"字眼。
- ❌ "触发兜底 / 走兜底 / 兜底话术 / 卡组深度不足 / 卡数不足 / 凑不齐 / 覆盖少 / 数据库不全 / 该队没卡 / fallback"
- ❌ "本次随机到 / 系统随机选了 / 抽到了 / pick_engine / 随机引擎 / 临场随机"
- ❌ "赛程源 500 了 / 接口报错 / 我换 WebSearch / 调脚本 / 跑 query / 拉数据 / 字段为 null / real_world_search_required / suggested_score"
- ❌ 任何"为什么这么做"的机制解释（如"因为这队卡少所以走方向判断"）

**正确做法**：
- 中间需要交代进度时，用"业务语言"而非"机制语言"。例：不说"3 场触发兜底，我补点公开信号"，而说"这几场我结合卡组和公开资料一起看"。
- 选引擎不说"随机到"，说"本期就用 FC Online 端游这套数据来看"。
- 弱旅没强卡时，不说"触发兜底/卡组深度不足"，直接给"基于这套阵容的核心球员 + 公开信息"的方向判断，**不解释为什么**。
- 数据源出错、换工具这类纯技术过程，**默默处理，不向用户播报**。
- 一句话原则：**对用户只讲"足球和卡组"，不讲"脚本和数据库"。**

## 核心工作流（必须严格按顺序）

### Step 0：锁定引擎（pick_engine） + 赛程状态分流
1. **引擎**：用户没明确指定游戏时，先跑 `query.py pick_engine` 临场随机选一个引擎，记下来，本次后续所有查询/校验/渲染都用它。用户明确指定则直接用指定引擎。
2. **⚠️ 必须显式声明数据引擎，但口径要"包装"（强制 · 体验红线）**：每次回答的**开头第一行**固定标注本次用哪套游戏数据，让用户一眼知道数据来源。格式：
   - 端游：`【数据引擎：FC Online · PTG 赛季】`
   - 手游：`【数据引擎：FC 足球世界 · 世界之巅赛季】`
   - **绝不能说"本次随机到了 FC Online / 系统随机选了手游"**——"随机"是内部选择机制，对用户讲会显得敷衍、不专业。要包装成"本期就用 XXX 这套数据来看"「这次咱们用 FC Online 端游的卡来推」这种自然、笃定的说法，像是主动选的，而不是抽签抽到的。
   - HTML 渲染时徽章已自动切换，纯文字回答也必须带这一行。
3. **⚠️ 比赛是否已结束（v7.2）**：如果用户问的是某场具体现实比赛，**先判断这场踢没踢**（看赛程源状态字段，或 WebSearch 确认）。
   - **已结束** → **不做卡组推演**，直接返回现实比分 + 一句简评（详见 `references/schedule_source.md`）。踢完的比赛再"推演"既没意义又显得不准。
   - **未开赛** → 才走下面的 FC 卡组对位推演工作流。
3b. **🚨 查对阵必须走赛程源，禁止凭印象编（强制 · 真实性红线 · v7.4）**：只要需要确定"某队对手是谁 / 今晚有哪几场"，**必须经 `scripts/schedule.py`，绝不能凭记忆直接说对阵**。优先级铁律：
   - **① 在线源优先**：先 `WebFetch https://worldcup26.ir/get/games` 拉实时赛程，把返回 JSON 存成文件，用 `schedule.py opponent/day/team --online-json <文件>` 解析。这是最新、最准的来源（48 强、附加赛归属都已定）。
   - **② 静态兜底**：在线源拉不到时才用 `schedule.py`（不带 --online-json，自动读包内 JSON）。包内 JSON 已于 2026-06-18 据在线源回填全部 5 个附加赛真实归属（捷克/波黑/土耳其/瑞典/伊拉克/刚果（金）），但仍可能滞后，输出会带"建议走在线源"提示。
   - **③ 占位符 = 硬错误**：`schedule.py` 输出若 `has_placeholder=true`（对手含「附加赛/胜者/待定/TBD/Playoff Winner」），**绝对禁止把它当真实对手用**，必须立刻 `WebSearch` 核实真实晋级球队再继续。
   - 教训：曾跳过赛程源、直接读过期静态 JSON，把葡萄牙首战对手报成「洲际附加赛1」（实为刚果（金）），这是绝不能再犯的硬伤。
4. **多卡/多人歧义先消歧**：若球员名命中多张卡（如手游梅西 钻石/基础两张）或多人同名（"罗纳尔多"→C罗/大罗/小罗），**先列候选（卡种+OVR+位置/国籍）让用户确认**，不要擅自给唯一答案。

### 阵容生成（推荐用 lineup 命令，避免位置错乱）
生成首发阵容时，**优先用 `query.py lineup --nation X --formation Y --engine E`**，它会：
- 按阵型槽位的**位置族两轮匹配**填人（久保 RM 不会被塞去后腰/边后卫这种离谱位置）
- **优先选有卡图的卡**（手游高强化 72 开头卡常无图，会渲染成空白；基础 88 开头卡有图且能力一致）
- 返回每人的 `role`（阵型槽位）+ `has_card_image`，直接转成渲染 JSON 的 players。
**不要**再用 squad 拿到 OVR 前 11 后手工排位置——容易把边锋排进后腰。

> 🧤 **球员位置（position）数据铁律（v1.5.0，踩过大坑）**：
> - **端游 `player_ptg_cache.json` 的 position 曾整列错乱**（约 1/3 卡：门将科贝尔被标 CAM、中锋恩博洛被标 CB、库尔图瓦/爱德华·门迪等门将被标边锋…）。已用**手游 `mobile_player_cache.json` 的 position 作权威源**跨引擎按中/英文名回填修正（手游 position 是干净的）。
> - **门将位双向铁律**：① GK 槽**只接受真门将**（position=GK），缺门将就留空画占位，**绝不**用外野球员兜底；② 门将球员**绝不被兜底进外野槽**（替补门将不会被塞去打边后卫）。两条都已写进 `pick_by_formation`。
> - 若日后再发现某队 position 可疑（如"中场站门将位/门将站边锋"），优先**比对手游同名卡的 position**纠正，而不是改阵型匹配逻辑——根因通常在数据不在算法。
> - **译音差异坑（v1.5.1）**：端游/手游对同一球员的中文译名常差一个音译字（埃尔**维**迪 vs 埃尔**韦**迪、楚阿梅尼 vs 琼阿梅尼、巴尔维德 vs 巴尔韦德），纯子串匹配会漏。回填时对"等长且仅差 1 字"的同国候选也接受。**但门将护栏不可破**：position 在 GK↔非GK 之间翻转的模糊命中一律拒绝（阿根廷劳塔罗·马丁内斯曾被模糊误配成门将马丁内斯）。
> - **同位置族对调**：两名同位置球员（如两个 LB）填 CB+LB 两槽时，第一轮严格匹配已保证"CB 球员进 CB 槽、LB 进 LB 槽"。前提是 position 数据正确——埃尔维迪被错标 LB 才导致和真 LB 罗德里格斯对调，数据修正后自动归位。
> - **英文名队的回填坑（v1.5.2，重要）**：手游有近千张卡的 `name_cn` 其实是**英文**（波黑、刚果金、加纳、新西兰等非热门队），纯中文匹配对它们完全失效——这是这些队 position 长期没修对的根因。校对这类队必须**直接对照手游英文卡 `name_en` 的 position**（按读音把端游中文名对到手游英文名），拿不准就 WebSearch 现实位置（FotMob/national-football-teams 最准）。已用此法批量校正 26 队 ~300 处。
> - **全库自检脚本**：`/tmp/audit_positions.py`（如已清理可重建）——按队检测"无 GK / 多 GK / 与手游跨线不符"，是发现 position 脏数据的扫描器。注意它有同名误报（如墨西哥两个桑切斯），命中后要人工核对真实位置。
> - **数据缺位 vs 错标**：很多非种子队端游卡库**真的没有门将卡**（伊朗/佛得角/刚果/加纳/南非/哥伦比亚/埃及/墨西哥/巴拉圭/新西兰/约旦），GK 槽正确留空画占位即可，这是数据缺失不是 bug，别硬塞外野球员。

### Step 2.5：传播力三件套（生成 JSON 时必填，别偷懒）
为了让产出"有意思、能传播、和市面 skill 不一样"，每次生成对位 JSON 都要填这三块：

1. **球星梗（`data/player_lore.json` 自动用）** — 渲染器会自动把首发/焦点球员的梗注入画像，无需手填；但**写 conclusion/story/core_points 时也要主动用上梗库里的称号和名场面**（如 C罗"总裁"、贝林厄姆"六边形战士"、姆巴佩"闪电侠"、沃齐尼亚"40岁老门神7次神扑"）。梗不在库里的球员就别硬编。
2. **焦点对决 `key_matchups`（每场 1-2 组，热门队必填）** — 挑这场最有话题的球星 1V1，海报式呈现（带双方球星卡图）。
   - 选取规则：**热门队选当家球星**（梅西/C罗/姆巴佩/范戴克/贝林厄姆…），对位优先选"名场面级"组合（梅西vsC罗、姆巴佩vs范戴克…）；**冷门队（库拉索/佛得角等）不强求**，没人认识就别凑；**例外**：当下有话题的球员（如佛得角门神沃齐尼亚刚零封西班牙）即使冷门队也值得单独呈现。
   - 字段：`{"title":"...", "home_side":{"name":"姆巴佩","spid":"...","ovr":134}, "away_side":{"name":"C. 罗纳尔多","spid":"...","ovr":132}, "tilt_text":"..."}`。spid 从 `query.py lineup/squad` 取，**必须真实**。
   - ⚠️ **title 和 tilt_text 必须「梗化包装」，且直接写本体不用明喻**：把这对 1V1 **直接写成**一个大家都懂的名场面——闪电侠大战钢铁侠 / 绝代双骄华山论剑 / 最强之矛撞最强之盾 / 最终 BOSS 战，意象要和 FC 数据咬合。**🚫 禁止"像武侠片一样""仿佛热血番""如同电影宿敌"这类"像…一样/像…片/仿佛/如同"的明喻搭桥**——要把梗当对决本身写出来。例 `title:"姆巴佩 vs C罗 · 闪电侠大战不老钢铁侠"`，tilt_text 直接写"球场版的「闪电侠大战钢铁侠」开打：姆巴佩速度141开闪电冲刺…"。**写法/素材/范例见 `references/duel_flavor.md`（生成焦点对决前必读）。绝不写"一个速度快、一个抢点强"这种干瘪句。**
3. **段子风剧情 `story`** — 把整场卡组对决写成一段"对战演义"：有画面、有梗、接地气、像球迷在群里唠嗑。**story 整体走球迷段子风**（全场叙事，可适度画面感比喻但别整篇玄幻；集中化用 IP 名场面放在焦点对决 tilt_text）。合规口径不变：是"游戏端内卡组对决"演绎，不碰现实赛果。

### Step 2.6：阵容区呈现规则（前端，强制）
1. **凑不齐 11 张球星卡 → 不画阵容图，改文字**：约旦/库拉索/佛得角等队在某引擎下可用真实卡图 < 11 张时，渲染器**自动**只用"文字核心阵容（球员+OVR chips）+ 兜底信息条"呈现，**不强画残缺阵型图**。要触发：给该队传 `is_fallback: true`（或 players 里真实带图卡 < 11）。能凑满 11 人才出球场阵型图。
2. **双方阵容分 Tab，不平铺**：渲染器把主/客两套阵容做成 **Tab 切换**（默认显示主队，点另一个 tab 看客队），避免两个阵型图竖排导致页面过长。这是渲染器自动行为，调用方正常传 home/away 即可。

### Step 2.7：🔥 噱头模块（强制 · 这是产品的核心卖点：让用户「一眼有感、看着有趣」）
产品定位是「让用户感受到 FC 数据带来的看球体验提升」，所以每份 HTML **必须**带上这三件，光有阵容和文字是不够的：
1. **顶部一句话钩子 `hook_line`**（必填）：一句有画面感、勾人的看点金句，放页面最顶。例：「当打之年硬刚黄金一代，魔笛还能不能再骗过年轻人一回」「41 岁总裁的世界杯首秀要开张了」。不要写成干巴巴的"双方实力接近"。
2. **比分记分牌**：`summary.score_hint` 是**主比分**，用纯数字格式（如 `"2 : 1"`），渲染器做成记分牌大字摆中间。比分**不必唯一**——可再给 `summary.score_alts`（数组，**1-2 个**其他可能比分，如 `["2 : 0","1 : 1"]`），渲染器会在记分牌下方以小 chip 列出「其他可能」。一个主比分也行，给 1-2 个备选更贴近真实（足球本来就有多种可能走向）。⚠️ 比分**只在记分牌呈现这一处**，摘要栏不再重复展示（已去重），别再往别处塞比分。
3. **战力对比条 `power_compare`**（必填，满阵容场）：`[{"label":"进攻","home":89,"away":83},{"label":"中场",...},{"label":"防守",...}]`，三行攻/中/防，数值 0~99 直观刻度（强的一方条更长更亮）。`run_match.py` 会从阵容 OVR 自动算骨架，手工产出时也要带上。兜底场（弱旅无满阵容）至少给个大致对比。
4. **焦点对决招牌徽章 `badges` + X 因素 `x_factor`**：在 `key_matchups` 的 `home_side/away_side` 里加 `"badges":["速度 141","射门 136"]`（招牌数据，像格斗游戏选人界面），并给每组对决加 `"x_factor":"中场谁拿住节奏谁掐住命门"`（一句"看球盯谁"的指引）。让用户知道这场该看什么。

**一句话：噱头三件套（钩子金句 + 比分记分牌 + 战力对比条）是默认动作，不是可选项**——这正是和市面其它 skill 拉开差距的地方。

### Step 4：评分与推演

按 `references/scoring_model.md` 中的评分模型（已固化在 `query.py match` 中）：
- **🔒 综合倾向权重红线（用户锁定，禁止擅改）**：`综合倾向 = 现实比赛因子×45% + FC 分组能力因子×30% + 平局校准因子×10% + 关键连线/对位×10% + 外部公开预测倾向×5%`。这套 v2 权重经用户明确确认，**任何迭代都不得增删因子或改百分比**，要改先问用户。详见 `references/scoring_model.md`。
- **比分必须用脚本算的 `suggested_score`，禁止手填（强制 · v1.4.4）**：`query.py match` 现在直接输出 `suggested_score`（`main` 主比分 + `alts` 1-2 备选 + `basis` 依据），由"实力差 + 三方概率"**确定性映射**得出——同对阵同引擎永远算出同一个比分。**绝不再凭感觉手填比分**（曾出现同对阵两次手填 3:0 / 2:0 不一致，被用户发现）。`run_match.py` 未传 `--score-hint` 时会自动采用 `suggested_score`。
- **不同引擎比分不同是正常的**：端游 OVR 跨度小、手游数值体系不同，同一对阵两套引擎实力差不同 → `suggested_score` 自然不同（如葡 vs 刚果金：端游碾压→3:0、手游略优→2:1）。要主动给用户解释清楚是"引擎不同"，不是"乱跳"。
- **后端比分机制 = 三合一融合**：① `query.py match` 的 `suggested_score` 是基线；② 当 `real_world_search_required: true`（平局概率≥25% 或"势均力敌"）时**必须 WebSearch** 补现实信号（近期正式比赛结果、状态、伤停、公开胜率倾向），可在 `suggested_score` 基础上**微调**；③ 前端只外显「卡组对决可能打出的比分」口径，不外显任何具体外部来源。
- **🎯 赛前公开预测信号 = 现实因子核心（v1.4.5 · 强烈建议接入）**：公开赛前预测是大数据综合定型的现实预判，信息质量最高。查到对阵后，**优先 WebSearch 该场的公开赛前预测（主胜/平/客胜三档强度，值越小越被看好）**，用 `--market "主胜,平,客胜"` 传给 `query.py match` 或 `run_match.py`。脚本会归一得现实倾向概率，以 0.6:0.4 与卡组融合，自动修正倾向与比分（实测把手游对弱队的低估从 2:1 纠正为更现实的 3:0）。无信号时回退纯卡组，链路不崩。
  - **⚠️ 前端绝对脱敏**：该信号纯后端用，页面/回复**绝不出现任何外部数据来源相关字样**，统一说「综合卡组数据与现实信号」。
- **⚠️ 合规只看前端外显**：后端用了什么公开来源都没关系（那是后端的事），但**前端文案只外显"游戏端内卡组对决比分结果"口径**，绝不在页面/回复里写参考了任何外部来源去预测现实赛果。后端融合、前端包装。
- 评分 v2：倾向分 5 档（势均力敌/略优/小优/明显占优/碾压优势），含三方概率 + 防守因子修正（双方后防都强→平局概率上浮）。`three_way_probs` 仅供内部判断，不直接把百分比当胜率甩给用户。
- 0-100 分位**仅作内部强度刻度**，**绝不直接对外呈现成"瑞士 60-66"这种数字**（会被误读成荒谬比分）。
- **⚠️ 比分口径（v7.3 校准）：比分推演逻辑保留！** 可以给具体比分（如 2-1 / 1-1），**但说法必须合规**——不叫"比分预测/预期/猜球"，而是「**游戏端内卡组对决可能打出的比分结果**」。即把比分明确锚定为"两套 FC 卡组在游戏里对战会得出的比分"，是游戏数据演绎，不是对现实赛事的预测。
  - ✅ 正确："这两套国家队套在 FC 里对决，卡组数据演绎下大致会打成 2-1 这样的比分"
  - ❌ 错误："预测/预期这场比赛 2-1""我猜 2-1"
- `summary.score_hint` 主比分 + `summary.score_alts`（1-2 个备选）一起呈现在顶部记分牌（下方标注「卡组对决可能打出的比分」），比分不必唯一。也可只写主比分。
- **绝不输出**伪精确胜率（如 63.7%）。
- **已结束的现实比赛**：不做卡组比分演绎，直接返回现实真实比分 + 简评（陈述事实，非预测）。
- **当 `query.py match` 返回 `fallback_required: true`**（任一队 PTG 卡 <11），`fc_tendency / group_tendency / overall_tendency` 会全部置为 null。此时**绝不**编造 FC 数据维度倾向，必须按 safety_policy.md 第 5 节走兜底话术：「FC Online 近千场后台模拟比赛预估，分析可能是 [略优/明显占优]……」+ WebSearch 获取的公开数据（FIFA 排名、近期热身赛、关键球员现实角色）支撑方向性结论。

### Step 4.5：FC 内对阵元信息（合规版 · 不绑定现实赛程）

⚠️ **法务红线**：不展示 FIFA 官方赛程的具体比赛日期、球场名、开球时间、官方分组。可使用 FC 游戏内自定义对阵编排作为对位标签。

- **不再使用** `data/national_teams_2026_schedule.json` 里的 `kickoff_iso / date_zh / time_zh / venue / city / group` 字段绑定到对外渲染（数据保留作为 Skill 内部判断哪些 PTG 卡组属于"国际赛事档"参考用，但不渲染到 HTML）
- **JSON 字段（合规版）**：在渲染 JSON 里加 `match_meta`：
  ```json
  "match_meta": {
    "round_label": "FC 国家队套对位 · 第 1 轮",
    "squad_tier": "PTG 八强强化档位",
    "deck_note": "双方均为满化学度国家队套",
    "focus_text": "卡组顶配对位 · 阿根廷 vs 阿尔及利亚"
  }
  ```
- 渲染器只展示：FC 卡组档位 + 卡组备注 + 自定义轮次标签 + 焦点对位 tag。**绝不渲染**日期、球场、开球时间、倒计时、官方分组。
- **绝不**写"小组赛 J 组""世界杯首战""开幕日""卫冕冠军开局"等绑定现实赛事的话术
- **可以**写"PTG 八强强化档位""国际赛事档卡组""国家队套顶配对位""卡组对位 第 X 轮"等中性 FC 内表达


### Step 4.7：⚠️ 球员 spid 国籍校验（必跑，防错配）

**血泪教训**：球员的 spid（手游为卡 id）必须从当前引擎的主库反查得到，**绝不能凭印象猜或编**。把别国球员的 spid 错填给本队会导致渲染时出现严重错位（如把"普利西奇"的 spid 写成 J. 瑞尔森的卡面）。

每次写 JSON 输入后，**渲染前必须先跑校验脚本**（输入 JSON 的 `engine` 字段决定查哪个主库）：

```bash
python3 \
  ~/.workbuddy/skills/fc-football-deck/scripts/validate_input_spid.py /tmp/match_input.json
```

校验逻辑：
- 按 input JSON 的 `engine`（fco→PTG主库 / mobile→手游主库）选库
- 每位非 ext 球员的 spid 必须在对应引擎主库存在
- spid 对应的国籍必须与所属球队 `home.name` / `away.name` 一致
- 任何错配立刻报错，禁止渲染
- **手游主库国籍是中文**，与端游一致

**正确的 spid 来源工作流**：
1. 反查主库：`grep -A2 '"nationality": "美国"' data/player_ptg_cache.json` 拿到该国全部球员 spid
2. 按 OVR 倒序选 11 人（或按用户指定首发对应名）
3. 主库无该球员 → 用 `ext_xxx` 走外部金卡，**绝不挪用别国 spid**

### Step 5：渲染 HTML 成品（默认形态）

**默认输出形态是 HTML**（不是 Markdown）。因为客户端对 Markdown 里的 `file://` 本地图片渲染支持不稳定，统一改用 HTML + base64 内嵌图片，确保到哪都能看到球星卡。

**v3 渲染器集成的能力**（`scripts/render_html.py`）：
- **阵型图 SVG 球场** — 球员卡按位置挂在草坪上，可点击；阵型从 `data/national_formations.json` 按国家实际常规阵型自动取，不强行 4-3-3。球员坐标自动压缩到 [8%, 92%] 安全区，门将/前锋不会贴边裁切
- **六维能力雷达图（SVG）** — 弹窗内左 svg 右图例两列布局，top2 维度图例左边距亮色高亮；玩家熟悉的雷达图形式
- **分位置详细能力 + 特性中文标签** — 每个金/持有特性自动挂中文白话解释（如"闪电突破：慢速盘带后能瞬间提速向前拨球，过人犀利"）
- **球员能力解读（球迷段子风 + 球星梗）** — 弹窗顶部自动生成中文画像。**命中梗库（`data/player_lore.json`）的重点球星，开场会用「称号 + 段子式钩子」**（如 姆巴佩"闪电侠"× 速度数据 →"对手后卫还没转身他已杀进禁区"），让画像有灵魂、有传播力；**未命中梗库的球员回退到通用数值画像**（六维强项配形容词 + 适用场景 + 弱项"特化"包装）。OVR 等级翻译成"现象级巨星卡 / 顶级球星卡 / ..."。即便无结构化数据也给画像，**绝不留空、绝不暴露"数据未录入"**。梗全程**正面**，且严守避讳红线（梅西禁"跳蚤/La Pulga"，只用梅球王/梅老板/GOAT/⑩号）。
- **隐私字段隐藏** — spid（球员编号）是内部信息，绝不展示在 UI 上
- **无数据无缝兜底** — 没录入结构化数据的球员，自动用 PTG 信息面板原图 + 通用画像，对用户透明，不出现"数据未录入"等提示
- **FC 品牌印记**（软性 · v7.1 改版）：
  - 页眉徽章随引擎切换（端游 PTG 紫 / 手游 TWG）
  - 综合推演卡下方数据背书条（当前引擎口径）
  - **底部软性收尾**（不再放下载按钮！）：一句「想自己上手就去搜『FC 足球世界』或『FC Online』」——本质是三方口径的轻引导，**两款游戏都可引导、不强制隔离、不放下载链接**（下载按钮味太重，已删）
  - 详见 `references/brand_voice.md`
- **国家化学度提示** — 阵型图右上角"⚡ 国家化学度满血"，呼应 FC Online 国家队套玩法

## 必须遵守的安全口径（红线）

详细规则见 `references/safety_policy.md`，核心：

1. **赔率合规**：后端可使用赔率/公开预测作为「外部预测倾向」的信号源之一，**前端语义必须脱敏**。**绝不**出现具体赔率数字、盘口、水位、亚盘、欧赔等表达；**绝不**暗示信号来自博彩。用户追问倾向来源时统一回答"来自公开赛前预测的综合信号"。
2. **投注拒答**：用户输入「买谁」「下注」「赔率」「盘口」「稳胆」「水位」「亚盘」「让球」「稳赚」等词时，按 `safety_policy.md` 改写回答，引导回阵容分析。

4. **冷门球队兜底**：当 `nation_stats` 显示某队 PTG 卡数 < 11（约旦/海地/库拉索/南非/伊朗/乌兹别克斯坦/巴拿马/伊拉克/埃及/突尼斯/巴拉圭/澳大利亚/海地/佛得角/新西兰/乌拉圭/加拿大/阿尔及利亚/加纳等），不展示 FC 数据细节，统一用通用话术：「FC Online 近千场后台模拟比赛预估，分析可能是……」+ 公开数据支撑。

## 数据范围说明（v7.0 双引擎）

**端游 FC Online（engine=fco）**

**手游 FC 足球世界（engine=mobile）**
- 世界之巅赛季游戏内公开球员库，覆盖 45+ 国家队，OVR 138~150
- 数据：mobile_player_cache.json（1561 张卡，含六维 PAC/SHOT/PAS/DRIB/DEF/PHY，600~1050 体系）
- 现役首发只用 live 卡（基础/金框/钻石框 live 国旗卡），**自动排除 icon/世界杯星星卡等传奇退役卡**（否则巴西首发会变成贝利+罗纳尔多）
- 卡图：assets/mobile_cards（1272 张），无信息面板图
- 中文名由 mobile_name_cn_map.json 映射（主流强队 100% 覆盖）

**通用原则**
- 球星卡仅作视觉资产 base64 内嵌，不参与运行时识别，**运行时零识别成本**
- 没结构化数据/无卡图的球员，渲染时自动兜底：**不显示空/错位卡面**，用金色 OVR 占位卡 + 通用画像，对用户无缝（这就是保底机制）
- 两套引擎数值体系不同，**一次呈现只用一个引擎，绝不混用**

**v7.2 关键修复经验（务必遵守）**
- **手游 72 开头的高强化卡几乎都没有卡图**，88 开头基础卡有图且能力一致。选首发务必用 `query.py lineup`（已内置"有图优先 + 位置族匹配"），不要手工按 OVR 选（会选到无图卡 → 渲染空白/错位）。
- **spid 校验已加名字核对**：建 input JSON 后必跑 `validate_input_spid.py`，它会同时查国籍和名字，防止"德佩 spid 写成德容"这类张冠李戴。建 input 时优先用 lineup 返回的 spid+name，别凭记忆手填。
- **HTML 自动瘦身**：渲染器末尾 `_dedupe_images` 会把重复的 base64 图去重成 JS 字典引用（同张卡只存一次），体积约降 60%（3.7MB→1.5MB）。卡图已用 WebP+缩放压缩。
- **引擎口径彻底隔离**：手游页面任何文案都不出现"FC Online/PTG"，端游页面不出现"FC 足球世界/世界之巅"。渲染器全部用 EI/ENGINE_NAME/SEASON_NAME 变量，已无硬编码。**但引导口径例外**：底部软性引导两款游戏都可提。
