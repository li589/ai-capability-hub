# 直播带货脚本工作台

把一份排品清单，变成主播能在镜头前照着念的一整场流程：分钟级流程表、每个主推品的讲解话术、可以直接照念的话术库、一遍合规检查，以及让这些东西在直播间里真的用得起来的话术卡和示范音。

## 适用范围与路线选择

这条路线交付的是：一份整场排期、每个商品的讲解话术、一套话术库、一遍合规检查，以及直播间真正会用到的产物。谁要开播卖货、需要眼前有词可念，就走这条。

要办的事不在这条路线上时，换一个工作流更合适。用商品图做直播间装修——背景图、贴片、预告封面——属于直播电商视觉类工作流。要的是一条录制好的短视频而不是一场直播，属于种草视频或商品视频类工作流。给剪好的片子配旁白，属于配音类工作流。

## 输入与默认值

两项硬性输入：本场的品类或主题，以及至少一个主推品，并带上它的日常价和直播价。

两个价格都要，因为这次的优惠是靠两者之间的差价来讲的。库存只在某个数字真的要画进卡片或者要在镜头前报出来时才需要：库存型逼单话术、憋单档位必须报出的固定放量数量，或者一条要报数量的示范音。倒计时卡上留的是空位，由场控现场填写，所以它不需要库存。这三项一次性一起问清楚，不要一项一项挤牙膏；库存暂时不明时，凭两个价格先往下走。

平台、本场目标、时长和谁出镜，对话里已经说过的就直接沿用。这些都没有说时，默认按四小时一场、一位主播加一位场控、达人带货形式，目标则按排品清单本身透出的意图来定。每一个默认值都在确认里点名说明，而不是拿去追问用户。

本场关于商品的所有说法都来自商家。价格、库存、规格、成分、资质、奖项、对比数据和优惠规则，都由商家提供。缺了哪一项，就绕开它把那一段写出来；绝不要编一个看起来合理的数字，因为最后在镜头前为这个数字负责的是商家。

## 标准流程

第 1 到第 5 步不花钱。四份书面产出获批之前，不会发生任何付费调用。

1. **定下本场框架。** 平台、目标、时长、出镜角色和排品顺序，见[排期规划](references/session-plan.md)。
2. **排出分钟级流程表。** 整场覆盖三个阶段，每个商品的档位都落在六段成交链路上。
3. **为每个主推品写讲解话术。** 七个步骤，按顺序来，见[讲解话术写法](references/talk-track.md)。
4. **写话术库。** 十二类主播可以照着念出来的话术，见[讲解话术写法](references/talk-track.md)。
5. **做一遍合规检查，并把四份产出一起交给用户确认。** 任何东西被生产出来之前，每一句话都先过一遍筛查——一句话在直播间里翻车的代价，远高于在这里重写一遍。
6. 读取实时的 `text_to_image` 与 `text_to_speech` 能力卡：调用 `beatra.models.list`；再调用 `beatra.voices.list` 选定音色。
7. **确认生产。** 展示要渲染哪些卡片、哪些句子会做成示范音、选定的可用音色、当前预估费用，以及每一次计划中的付费调用对应的稳定请求 ID。
8. 用 `beatra.images.generate` 渲染卡片，一张卡一次调用；用 `beatra.speech.synthesize` 合成示范音。每条示范音都读取实际返回的时长、大小和 MIME 类型。
9. 用 `beatra.tasks.get` 轮询每个任务直到终态，把全部产物一次性交付，并复核你确实能看到、能听到的部分。

## 需要确认的决定

花钱之前只确认一次：卡片集合和示范音放在一起确认，各自带上价格和请求 ID。这里没有第二道闸门，因为没有任何一件产物依赖另一件已付费产物。

以下情况也要问过用户，而不是自己拍板：单场超过六小时、主推品超过八个、商家尚未核实的价格或库存数字，以及卡片或示范音获批之后的任何改动。任何一个参数变了，都是新的付费工作，需要新的请求标识和重新确认。

用户要的某句话按原样过不了合规筛查时，给出最接近、并且能通过的写法，然后从这句继续往下推进。

## 执行

所有远程 Beatra 工具只通过本 Skill 随包的 `scripts/mcp_client.py` 调用：工具名作为命令行参数，参数以 JSON 从标准输入传入：

```text
printf '%s' '{"capability":"text_to_image"}' | python3 scripts/mcp_client.py call beatra.models.list
printf '%s' '{"capability":"text_to_speech"}' | python3 scripts/mcp_client.py call beatra.models.list
printf '%s' '{"language":"zh-CN"}' | python3 scripts/mcp_client.py call beatra.voices.list
```

不要配置或调用宿主 Beatra Connector，也不要使用 REST/OpenAPI 作为回退。每一个逻辑上的付费请求只给一个稳定且不透明的 `client_request_id`，并且只提交一次。

## 交付与复核

交付流程表、各商品的讲解话术、话术库、合规检查结果、渲染出来的卡片及其返回尺寸、示范音及其真实时长、每个 task ID、返回的 artifact 链接、解析后的模型，以及 `billing.net_charged_credits`。只报告任务确实返回的事实。

主播能看图、能播放音频时，逐张核对卡片上的数字与已获批的流程表是否一致，逐条确认示范音听得清、结尾收得干净。卡片上的文字是模型画出来的图，所以要把上面的数字回读一遍、对照来源；某个数字没画对、或者画得不清楚，就直说——最危险的恰恰是一个笔画清晰却写错的数字，而直播间里摆出一张价格错误的卡片，比没有这张卡片更糟。

哪些媒体细节没能真正检查到，就说明白，不要拿任务元数据去推断。

## 恢复

每个 task ID 立即记下来，并且只轮询这个任务。`queued` 和 `running` 都表示继续等。创建请求的响应丢了，只能用逐字节一致的冻结载荷、按同一个标识重新提交；task ID 丢了，就按对应能力列出任务，在任何重试之前先拿候选项和自己的记录逐一比对。重做其中一张卡片时，其余产物原样复用。`insufficient_balance` 表示这次没有扣费，充值之后可以原样重新提交同一个请求。

## 运行时与安全自动更新

随包客户端会在每个安装中静默检查是否有新版本，最多每 24 小时一次。发现更高版本时，不另行确认地自动安装。它只从本包、本渠道、本语言环境固定的 Beatra 官方发现地址与不可变 CDN 路径下载，在替换之前校验发现数据、压缩包、清单以及每个文件的大小和校验和，并且只替换本包拥有的文件。它会拒绝重定向、降级、与包名、渠道、语言环境或版本不匹配的数据、非预期的 URL、不安全的压缩包，以及任何落在归属目录之外的文件。

更新的检查、下载、校验、替换和回滚在失败时都不会中断流程：当前安装仍然可用，原本请求的命令会继续执行。更新失败绝不构成重试一次付费生成的理由。这个设置会在本安装的后续命令中持续生效。

```text
python3 scripts/mcp_client.py update --auto off
python3 scripts/mcp_client.py update --auto on
python3 scripts/mcp_client.py update --check
```

`--auto off` 会关闭静默检查，`--auto on` 会恢复静默检查，`--check` 会报告官方可用版本但不替换文件。参见[自动更新与安全](references/automatic-updates-and-safety.md)。
