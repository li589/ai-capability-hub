## 服务分层：免费 vs 付费

本技能采用**先尝后买**模式。每次交互先判断用户需求落在哪个层级：

### 🆓 免费层（始终可用，无需支付）

| 内容类型 | 示例 |
|---------|------|
| 方法论框架概述 | 六阶段总览、345法则简介、LPTC配比概念 |
| 判定与路由 | "这是否培训可解决？"、应进入哪个阶段 |
| 参数速查 | 关键参数默认值（含溯源标注） |
| 问题诊断摘要 | 指出问题可能出在哪个环节、给方向性建议 |
| 免费层预览 | 付费内容的框架版（无定制填充） |

### 💎 付费层（需通过 X402 支付后解锁）

| 内容类型 | 交付物 |
|---------|--------|
| **完整需求诊断报告** | 三层扫描结果 + BEI编码输出 + 优先级排序 + 断舍离判定 |
| **定制项目设计方案** | 345法则完整填充 + 三档预算方案 + 课纲破立练收 + 里程碑排期 |
| **课程开发完整输出** | 知识原子化脚本 + 数字人微课脚本 + 双审清单 |
| **学练考赛实施方案** | LPTC四阶完整配置 + 漏斗选拔规则 + 人群×阶段矩阵 |
| **ROI 计算与评估报告** | 带归因声明的ROI明细 + 柯氏四级完整 + 虚假好评检测结果 |
| **人才九宫格分析** | 绩效×潜力双维度落格 + 校准建议 + 异常检测 |
| **案例库深度匹配** | 24案例中与当前场景最匹配的3个 + 差异分析与适配建议 |
| **知识沉淀模板填充** | 基于当前项目的情境卡片（模式卡/避坑卡/资产卡）+ 三维标签 |

## 微信 X402 Agent Pay 集成

### 前置检查

在处理任何付费请求之前，检查当前 Agent 是否已安装 `weixinpay` 插件：

- ✅ 已安装：可进入付费流程
- ❌ 未安装：提示用户「当前 Agent 暂不支持微信支付付费能力」，仅提供免费层内容

### 付费交互流程

```
用户请求付费层内容
       │
       ▼
┌─────────────────────────────────────┐
│ ① Agent 先输出免费层预览（框架版）     │
│   末尾标注「💎 以下为深度定制内容」     │
│   询问用户是否继续解锁                │
└─────────────────────────────────────┘
       │ 用户确认「是/继续/解锁」
       ▼
┌─────────────────────────────────────┐
│ ② Agent 调用商户 API：               │
│   POST https://{商户域名}/api/resource │
│   Body: {"query":"用户的完整需求"}    │
└─────────────────────────────────────┘
       │
       ├─── 200 OK（已付过费）──→ ④ 直接输出完整内容
       │
       └─── 402 Payment Required
              │
              ▼
┌─────────────────────────────────────┐
│ ③ weixinpay 插件拦截 402，完成支付    │
│   Agent 收到支付成功通知              │
└─────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────┐
│ ④ Agent 携带 Header 重新请求：        │
│   X-Out-Trade-No: {订单号}           │
│   WeixinPay-Required: {payment_code} │
│   Body 与首次请求完全一致              │
└─────────────────────────────────────┘
       │
       ├─── 200 OK → ⑤ 输出完整付费内容
       ├─── "NOT_PAID" → 「支付处理中，请稍后重试」
       ├─── "REFUNDED" → 「服务异常已自动退款」
       └─── "FULFILL_AND_REFUND_FAILED" → 「请联系客服」
```

### 402 响应处理细则

收到 HTTP 402 时，从响应中提取：

```
Response Header:
  WeixinPay-Required: {payment_code}   ← 插件支付用
  X-Out-Trade-No: {out_trade_no}       ← 重试时原样携带

Response Body:
  "WeixinPay.prompt" → 展示给用户的支付引导语
  "amount"           → 展示金额（如 "0.01"）
  "description"      → 展示付费内容标题
```

**重要**：支付由 `weixinpay` 插件自动完成，Agent 不手动处理支付。Agent 只需：
1. 告知用户金额和内容描述
2. 等待插件返回支付结果
3. 支付成功后重新请求商户 API

### 支付失败 / 用户取消

- 用户取消支付 → 终止付费流程，回到免费层
- 支付超时 → 提示「支付超时，可稍后重试」
- 多次支付失败 → 建议检查微信支付状态或联系客服

## 阶段0：靶心战略

> 不是所有岗位都值得投入培训资源。

**七步推导链**：
```
战略定位 → 业务目标 → 业务模式 → 关键策略 → 关键岗位 → 靶心人才 → 靶心能力
```

**输出**：
1. 战略校准一句话模板：「通过{关键策略}，需要{靶心岗位}具备{靶心能力}，支撑{业务目标}在{时间}内实现」
2. 靶心能力清单（≤8项，每项标注 当前水平/目标水平/差距分/战略权重/可培训性）
3. 非靶心判定说明 + 资源倾斜建议（靶心项目占预算 60-80%）

**优先级总分** = 差距分 × 战略权重 × 可培训性系数（高=4 / 中=2 / 低=0.5）

> 🛑 **门控点**：靶心判定输出后，确认"这些岗位确实是战略关键吗？"再进入阶段1。

## 阶段1：需求分析

### 前置决策：是否培训可解决？

| 培训可解决 ✅ | 非培训解决 ❌ |
|-------------|-------------|
| 知识/技能不足、方法缺失 | 流程缺陷、激励不足、资源短缺、组织架构问题 |

判定句：「如果员工知道怎么做，问题会消失吗？」

### 三层扫描模型
组织层（战略解码）→ 岗位层（对标分析）→ 个人层（申报校验），三层交叉验证。

### 优先级公式
`差距分(1-5) × 战略权重(1-5) × 覆盖人数(1-5) × 紧迫度(1-5)`

### BEI 编码辅助
访谈 → 关键事件提取 → 行为动词编码 → 能力项归类 → 能力词典 → BARS 输出。
编码一致性 ≥ 85%，每岗位能力项 ≤ 12 个。

### 诊断决策引擎：资源断舍离矩阵
四象限决策（战略相关性 × 培训效果预期）→ 重点投入 / 换方案 / 移交业务 / 砍掉。
> 📄 完整四象限 + 执行规则 + 信号特征：`references/resource-triage-matrix.md`

> 🛑 **门控点**：需求诊断报告输出后，确认"优先级排序是否合理？砍掉的项目是否有遗漏？"再进入设计。

> 💎 **付费交付**：完整需求诊断报告 = 三层扫描详细数据表 + BEI编码输出（能力词典+BARS行为锚定）+ 断舍离四象限落位 + 优先级排序理由说明。

## 阶段2：项目设计

### 345 法则（元框架）

**3 原则**：对比驱动决策 / 体验驱动学习 / 输出倒逼内化

**4 思路**：完善认知结构 / 在解决问题中提升 / 共性个性兼顾 / 选育用留一体化

**5 主线**（每项目选 2-3 条）：
| 主线 | 工具 | 适用 |
|------|------|------|
| 认知线 | IDP + 360 + 测评 | 高潜/管理梯队 |
| 行动线 | 行动学习 + AAR + 路演 | 业务攻坚 |
| 辅导线 | 导师制 + 教练 + 月度对话 | 行为改变 |
| 学习线 | 课程 + 读书会 + 微学习 | 知识补缺 |
| 评估线 | 里程碑 checklist + 数据看板 | 所有项目 |

### 课纲设计：破·立·练·收 框架
- 破（认知重塑）→ 立+练（方法+实操交替，每模块讲→练→出闭环）→ 收（综合实战+成果展示）
- 实操环节占比 ≥ 50%
- 标题公式：《主题》—— 一句话价值承诺

### 预算优化
- 三档方案：保守/标准/激进
- ROAS 预估（行业经验，需组织校准）：
  | 类型 | 参考范围 |
  |------|:---:|
  | 销售技能 | 3.5-5.0 |
  | 技术认证 | 2.5-4.0 |
  | 管理能力 | 2.0-3.5 |
  | 合规 | 1.5-2.0 |
- 削减优先级：兴趣型 → 提升型 → 转型型 → 补缺型（最后砍）
- 上限冲突：单课 ≤ 30%，单部门 ≤ 50%

### 345 法则与阶段4 映射
- 3 原则 → §2.1 策略匹配
- 4 思路 → §2.2 课纲 + §2.5 学习体验
- 5 主线 → §4.7 学练考赛 + §4.8-4.10 高潜/梯队/继任

> 📄 345 法则完整模板：`references/talent-project-template-345.md`

> 🛑 **门控点**：方案输出后，确认"选择保守/标准/激进中的哪一档？预算是否通过？"再进入开发。

> 💎 **付费交付**：完整项目设计方案 = 345法则逐项填充 + 三档预算明细（粗到科目/细到人均）+ 课纲破立练收每模块标题+内容摘要+时长分配 + 里程碑T日倒排计划。

## 阶段3：课程开发（极速车间）

### 内容原子化
每个知识点 ≤ 7 分钟，结构：引入(30s) → 核心概念(2min) → 案例(2min) → 练习(2min) → 小结(30s)

### 生成式内容工厂管线
脚本生成 → 多模态组装（按内容类型自动选形式）→ 材料类型选择 → 输出

### 数字人微课
脚本（≤3min/原子）→ 虚拟人配置（形象/声音/背景/手势）→ 字幕+视觉增强 → 合成+质检

### 双审质控
一审（教学设计对齐） + 二审（内容合规），输出：通过✓ / 修改建议⚠️ / 阻断🚫

> 🛑 **门控点**：双审通过后，确认"内容是否对齐需求诊断？是否需要业务方试讲确认？"再进入实施。

> 💎 **付费交付**：完整课程包 = 含 5-10 个知识原子的教学脚本（每原子引入/概念/案例/练习/小结完整文本）+ 数字人微课逐字稿 + 配套双审清单。

## 阶段4：项目实施

### 全流程管控（T 日基准）
```
T-28d 需求确认 → T-21d 方案通过 → T-14d 讲师确认 → T-7d 学员通知
→ T-3d 设备测试 → T-1d 物料到位 → T日 执行 → T+1d 训后跟进
→ T+7d 评估回收 → T+30d 效果复查 → T+90d 复盘总结 → T+180d 衰减终测
```

### 学练考赛四阶闭环（核心）

```
学(Learn)≤10% → 练(Practice)40% → 考(Test)30% → 赛(Compete)+评(Check)20%
正向：以赛促考 → 以考促练 → 以练促学
逆向：学不足 → 倒逼练 → 练暴露 → 倒逼考 → 考发现 → 倒逼学（自动回流）
```

**赛的三个战略价值**：①展示压力倒逼行为改变 ②向管理层证明培训成果 ③赛即人才识别

**四阶质检门禁**：

| 阶段 | 通过标准 | 未通过动作 |
|------|---------|-----------|
| 学 | 知识测验≥80分 | 补充学习+重测(限1次) |
| 练 | 仿真≥3分(5分制) | 教练辅导+针对性复练 |
| 考 | ≥70分+行为指标过关 | 回退练，聚焦薄弱项 |
| 赛 | ≥75分或排名前50% | 加强练/换赛道/出池 |

> 📄 完整 LPTC 系统（三段论/四阶详解/漏斗层级/人群矩阵）：`references/lptc-system.md`

### 教练选拔标准（前置筛选门）
教练基因是"打过仗"——三硬指标（实战过 + 正在实战中 + 有复盘能力），一票否决（口才好没上过战场/脱离一线>24月/不能给亲历案例）。

### 高潜/梯队/继任者

| 领域 | 核心模型 | 关键指标 |
|------|---------|---------|
| 高潜 | 绩效(40%)×潜力(35%)×意愿(25%) | 池占比 5-15%，年出池率 15-25% |
| 管理梯队 | L1 新任 → L2 在岗 → L3 高阶 三级跃迁 | 每级 4-6 项关键能力 |
| 继任者 | 影响范围 × 替代难度 定位关键岗位 | 梯队覆盖率≥80%，板凳深度≥2人 |

### 产品化运营思维
人才项目 = 产品。三阶段（MVP验证→增长迭代→成熟运营），七大指标替代传统报表：完课率/留存率/NPS/行为转化率/业务反馈率/复购率/项目存活率。生命周期决策：该继续/迭代/还是下线？

> 🛑 **门控点**：T+7d 评估回收后，确认"是否需要调整后半程内容？出池学员是否重新分配？"再继续。

> 💎 **付费交付**：完整实施方案 = 学练考赛每阶段详细教案 + 漏斗选拔规则表 + 教练人选推荐理由 + 高潜/梯队/继任者配置 + 产品运营仪表盘指标初始值。

## 阶段5：项目评估（数据透镜）

### 柯氏四级

| 层级 | 评估内容 | 时机 | 核心指标 |
|------|---------|------|---------|
| L1 反应 | 学员满意度 | 培训结束时 | 满意度均分 / NPS |
| L2 学习 | 知识/技能掌握 | 培训前后 | 提升率 / 通过率 |
| L3 行为 | 工作行为改变 | 训后 1-3 月 | 行为改变率 |
| L4 结果 | 业务结果 | 训后 3-6 月 | 指标变化率 / ROI |

### ROI 计算
```
培训总成本 = 直接成本 + 间接成本(脱产薪资等) + 隐性成本(可选)
年度净收益 = (L3月均收益 + L4月均收益) × 持续月数 × 归因系数(默认60%，需按场景校准)
ROI = (净收益 - 总成本) / 总成本 × 100%
```

⚠️ **数值溯源**：所有默认值（ROI归因60%、持续月数等）均需加归因声明。详见 `references/WORKFLOW.md` 文末「默认值溯源表」。

### 虚假好评检测
惯性评分 SD < 0.3 → 🔴 | 全满分率 > 30% → 🔴 | L1 高 L2 低 → 🔴

### 人才九宫格
绩效 × 潜力双维度。格1>10%→标准偏松；格1+2+4>40%→收紧潜力定义；格9>5%→系统性问题。

### 人才密度量化

| 指数 | 公式 | 健康线 |
|------|------|:---:|
| 关键岗位密度 | 就绪后备数/岗位数 × 质量系数 | ≥1.2 |
| 梯队健康度 | 覆盖率+板凳深度+就绪度+流动性(百分制) | ≥75 |
| 离职风险 | (高风险R1×3 + 非R1岗位×1.5) / 总岗位 | ≤0.3 |

### 培训价值仪表盘
四大区域（培训效果/投入产出/人才资产/运营效率）→ 一页纸看板 + 自动叙事摘要。

### 组织知识沉淀

> 📄 完整卡片模板 + 标签体系 + 运维规则：`references/knowledge-card-templates.md`

> 💎 **付费交付**：完整评估报告 = ROI五步明细计算 + 柯氏四级L1-L4逐项数据 + 虚假好评检测报告 + 九宫格落位图（附校准建议）+ 人才密度三指数计算 + 情境卡片A/B/C初稿。

## 输出原则

1. **免费先尝**：任何付费内容前，先给免费预览，让用户判断价值
2. **诊断先行**：先判定是否培训可解决，再进入设计
3. **三档方案**：每次给保守/标准/激进至少两档可选
4. **数值可信度**：区分 行业基准 / 设计约束 / 经验估算，不做虚假精确
5. **产出物可用**：课纲拆到模块、预算细到科目、通知含模板
6. **画像收集**：首次互动自然了解 行业/规模/培训成熟度/预算量级，不轰炸
7. **产品视角**：不只问"这期做完没"，还问"用户留存率/复购率/该迭代还是下线"
8. **付费透明**：支付前明确告知金额和交付物清单；支付失败不丢上下文

## 边界条件与异常处理

### 用户输入不充分时
- 如果用户未提供行业/规模/培训成熟度，**不要停止**：基于常见假设继续，同时标注"假设条件"。
- 如果用户需求跨多个阶段，**先声明覆盖范围**，再依次展开，避免跳跃。
- 如果用户只说业务痛点（如"管理者不会带人"），**从阶段1判定句开始**，不要直接跳到方案。

### 引用文件缺失时
- 如果 `references/` 下某文件不可访问，**不要中断**：使用 SKILL.md 中的摘要版本继续。
- 如果摘要版本也不够，**降级为通用方法论**并告知用户"缺少详细参考，以下基于通用原则"。

### 数值/阈值冲突时
- 溯源表中 L3/L4 级别的参数仅为经验参考，**不应作为硬约束**。当与用户组织实际数据冲突时，优先用户数据。
- 所有 ROI 计算结果必须附带归因声明（如"本结果基于 60% 归因系数，实际需按场景校准"）。

### 语言边界
- 主语言为中文。如果用户输入为英文，仍以中文回复但保留英文专业术语。
- 所有打印输出（公式/表格/模板）使用中文，外文术语首次出现时标注原文。

### 无法覆盖的场景
- 如果用户需求不在六阶段覆盖范围内（如薪酬设计/劳动关系/招聘），明确告知"这超出我的专业范围"，并提供替代方向（如"建议咨询 HRBP 或专业顾问"）。

### 支付异常
- weixinpay 插件未安装 → 仅提供免费层，提示安装插件后可解锁付费
- 用户取消支付 → 保持上下文，回到免费层，用户可随时重新发起
- 支付超时 → 提示可稍后重试，保留已生成的 `out_trade_no`
- 查单返回 NOT_PAID → 等待 3-5 秒后重试一次，仍失败则提示用户
- 返回 REFUNDED → 告知用户已退款，建议检查服务状态
- 返回 FULFILL_AND_REFUND_FAILED → 告知用户并建议联系客服

## 商户服务端部署

如需部署付费能力对应的商户后端，参考 `mch-demo` 中的 Go / Java 示例。

### 接口规范

**端点**：`POST /api/resource`

**请求**：
```json
{
    "query": "用户完整需求描述（含组织上下文）"
}
```

**首次请求 → 返回 402**：
```json
{
    "code": "PAYMENT_REQUIRED",
    "message": "需要支付后才能获取完整内容",
    "WeixinPay": {
        "WeixinPay-Required": "{payment_code}",
        "prompt": "请将 WeixinPay-Required 的值作为 paymentCode 调用 weixinpay_pay"
    },
    "out_trade_no": "{32位唯一订单号}",
    "amount": "0.01",
    "currency": "CNY",
    "description": "人才培养深度咨询: {用户需求摘要}"
}
```

响应头：`WeixinPay-Required: {payment_code}` / `X-Out-Trade-No: {out_trade_no}`

**支付后重试 → 返回 200**：
```json
{
    "code": "SUCCESS",
    "message": "付费内容",
    "out_trade_no": "{订单号}",
    "transaction_id": "{微信交易号}",
    "content": "【付费内容】基于用户query生成的完整交付物",
    "already_fulfilled": false
}
```
