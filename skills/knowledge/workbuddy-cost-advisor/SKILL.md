# WorkBuddy 用量优化顾问

> 最后更新：2026-05-28 | 基于 WorkBuddy 当前模型列表（2026年5月）+ SDR 任务教训迭代

## 目标

在回应用户任务之前，先评估该任务的性质，选出消耗最低、效果达标的模型，并在必要时给出调用前提示。

---

## 不适用场景

以下情况**不主动触发**此 skill 的模型推荐，避免打断用户正常流程：

| 场景 | 原因 |
|------|------|
| 用户已明确指定模型且未询问成本优化 | 尊重用户选择，不强行改写 |
| 普通创作（写作/绘图/代码开发）中未提省钱 | 不因"描述任务需求"自动插入推荐 |
| 纯聊天、答疑、信息查询 | 无积分优化需求 |
| 用户正在使用特定连接器/本地工具完成任务 | 推荐模型会干扰现有工作流 |
| 紧急任务用户要求快速响应 | 不因推荐模型而延迟执行 |
| 模型列表或积分数据无法确认 | 只保守建议并注明"需核对当前 WorkBuddy 配置" |

---

## 触发条件

明确触发此 skill 的场景：

- 用户明确询问"用哪个模型"或要求推荐模型
- 用户表达节省积分、降低消耗的需求
- 用户上传图片或大文件且未指定模型
- 用户提到 AUTO/GLM-5v-Turbo 或积分消耗异常
- 多阶段串联任务可能产生高消耗时

## 快速判断流程

收到用户任务后，依次判断：

1. **是否涉及图片输入？**
   - 轻度图片 → `MiniMax-M2.5` 或 `MiniMax-M2.7`
   - 复杂多模态 → `GLM-5v-Turbo`（⚠️ 高消耗，慎用）
   - 否 → 继续步骤 2

2. **任务是否需要深度推理 / 复杂逻辑？**
   - 是 → `Hy3 preview` 或 `Hunyuan-2.0-Thinking`
   - 否 → 继续步骤 3

3. **任务是否需要代码生成 / 技术分析？**
   - 是 → `DeepSeek-V3.2`
   - 否 → 继续步骤 4

4. **是否是简单问答 / 信息提取 / 格式化？**
   - 是 → `GLM-4.7`（最省）或 `MiniMax-M2.7`
   - 否 → 继续步骤 5

5. **任务是否涉及超长上下文 / 长文档？**
   - 是 → `Kimi-K2.6` 或 `Kimi-K2.5`
   - 否 → 继续步骤 6

6. **任务是否是 Agent / 工具调用密集型？**
   - 是 → `GLM-5.0-Turbo`
   - 否 → 继续步骤 7

7. **以上均不匹配（兜底）**
   - 是 → `GLM-5.1`（通用首选，性价比均衡）

8. **避免 `AUTO` 自动路由**：积分消耗不可预测，手动指定模型始终更优。

## 高消耗场景警告规则

在以下情况，**必须在执行前主动提示用户风险**：

| 触发条件 | 提示内容 |
|---------|---------|
| 用户上传图片并提问 | "⚡ 图片任务优先用 MiniMax-M2.7，避免 GLM-5v-Turbo 高价多模态" |
| 任务上下文超长（估计 > 5000 tokens） | "⚡ 当前上下文较长，建议先总结压缩再提问，可节省约 30-50% 积分" |
| 用户使用 AUTO 模式 | "⚡ AUTO 自动路由积分不可控，建议手动指定模型" |
| 连续多轮对话超过 10 轮 | "⚡ 长对话积累了大量上下文，建议新开会话或总结精简，可节省积分" |
| 二进制文件读取失败（PPTX/PDF等） | "🛑 该文件必须用专门工具（python-pptx/pdf skill）读取，不得用 Read 重试！" |
| 任务涉及 >100KB 文件或多阶段 | "⚡ 大文件/多阶段任务禁止 AUTO，必须手动指定模型" |

## SDR 任务教训 — 必须遵守的 6 条铁律

> 来源：2026-05-28 "SDR名单批量打标及分层运营"任务复盘，单次任务异常消耗约 **780-870 积分**。

### 铁律 1：二进制文件读取熔断

**问题**：PPTX/PDF/图片等二进制文件，Read 工具无法解析时，仍消耗完整上下文的积分。SDR 任务中多次读取法马公司介绍 PPT 失败，每次消耗 ~16 积分（122K tokens），累计损耗 ~600 积分。

**规则**：
- 读取二进制文件（`.pptx`/`.docx`/`.pdf`/`.png`/`.jpg`）**必须先判断工具能力**，不要直接用 Read
- 遇到 **"Cannot display content of binary file"** 错误 → **立即标记该文件为不可读，禁止重试**
- 替代方案：pptx → 用 `python-pptx` 提取文本；docx → 用 `python-docx`；pdf → 用 `pdf` skill 或 `pypdf`
- **同一文件重试上限 = 1 次**

### 铁律 2：AUTO 模式强制拦截

**问题**：AUTO 自动路由在大文件/多阶段任务中会随机分配高消耗模型，积分完全不可控。

**规则**：
- 任务涉及以下任一条件 → **禁止 AUTO，必须手动指定模型**：
  - 文件 > 100KB
  - 预计工具调用 > 5 次
  - 多阶段串行任务（> 3 步）
  - 上下文估计 > 5000 tokens
- 违禁检测：任务开始前先检查当前模型，若是 AUTO → 强制提示切换

### 铁律 3：大文件任务模型锁定

**问题**：大文件 + AUTO 是最危险的积分组合。

**规则**：
- 涉及文件读写密集型任务 → 锁定 `GLM-5.0-Turbo`（Agent 优化，工具调用高效）
- 涉及代码/脚本生成 → 锁定 `DeepSeek-V3.2`
- 涉及超长上下文 → 锁定 `Kimi-K2.6`
- **不允许在大文件任务中切换模型**，锁定后全程使用

### 铁律 4：脚本迭代收敛提示

**问题**：SDR 任务中 tag 脚本从 v1 写到 v4，每次迭代消耗完整上下文。

**规则**：
- 同一脚本迭代 ≥ 2 个版本 → **第 3 次前必须暂停并确认**：
  - "该脚本已迭代 2 次（v1→v2），当前 v2 是否满足需求？是否需要继续优化？"
- 用户未明确回复前，不得生成 v3+
- 迭代目标不清晰时，先对齐需求再动手

### 铁律 5：工具输出过滤

**问题**：Glob/Grep/Bash 等工具的大量输出可能包含噪音数据，被注入上下文后产生隐性的 token 消耗。

**规则**：
- Glob 搜索前先限定目录范围，避免全盘扫描
- Grep 搜索大文件时指定 `head_limit`，避免返回几万行结果
- Bash 输出 > 5000 字符时，先截取关键部分再注入上下文
- 不再需要的中间文件/临时输出 → 及时清理，避免后续误读

### 铁律 6：失败重试熔断计数器

**问题**：SDR 任务中同一操作反复失败却未切换策略。

**规则**：
- 建立熔断计数器：
  - 同一工具对同一文件操作失败 **2 次** → 熔断，强制切换策略
  - 同一阶段任务整体失败 **3 次** → 暂停，提示用户确认方向
- 熔断后必须向用户报告：失败原因 + 已消耗积分 + 替代方案
- 熔断不是放弃，是切换到更低成本、更可靠的路径

### 6 条铁律优先级

| 优先级 | 铁律 | 触发条件 | 动作 |
|--------|------|---------|------|
| P0 | 铁律 1 | 二进制文件读取失败 | 立即熔断，切换工具 |
| P0 | 铁律 2 | 任务涉及大文件/多阶段 | 强制手动指定模型 |
| P1 | 铁律 3 | 大文件任务进行中 | 全程锁定模型不切换 |
| P1 | 铁律 6 | 同操作失败 2 次 | 熔断并报告 |
| P2 | 铁律 4 | 脚本迭代 ≥ 2 次 | 暂停确认再继续 |
| P2 | 铁律 5 | 工具输出 > 5000 字符 | 过滤/截断 |

## 每次任务开始时的标准提示格式

当识别到任务类型后，用以下格式输出一行建议（不要啰嗦，一行即可）：

```
💡 推荐 [模型名]，原因：[一句话说明]。[如有风险加一行警告]
```

示例：
- `💡 推荐 GLM-4.7，原因：纯文本问答，最省积分。`
- `💡 推荐 MiniMax-M2.7，原因：含图片输入，多模态性价比最优。`
- `💡 推荐 DeepSeek-V3.2，原因：代码生成任务，推理能力强。⚠️ 检测到上传了图片，但此任务主要是代码，建议剔除图片以节省积分。`
- `💡 推荐 Kimi-K2.6，原因：超长文档分析，Kimi 系列长上下文最优。`

## 附加优化原则

1. **批量任务合并**：多个同类小任务合并为一次请求，减少固定开销。
2. **避免重复确认**：不要问"你确定吗？"这类会消耗往返积分的对话。
3. **本地优先**：文件操作、代码补全等能本地执行的，不走模型调用。
4. **新开会话**：超过 15 轮的对话建议新开，避免携带过长历史上下文。
5. **手动指定模型 > AUTO**：AUTO 会自动选择高价模型，手动指定始终更省。
