# 私域标签体系搭建
> 版本：v0.2.0 · 作者：小风、CoderPig

从 0 搭建一套**可落地、可治理、不腐烂**的私域用户标签体系，产出四件套：**标签分级架构 + 标签字典与元数据（18 字段）+ 治理 SOP + 落地实施路线**。这不是「给一个人群打几张标签卡」，而是「搭一套可复用的标签资产底座」——让标签有口径、有 owner、有质量分、有上下线，不再爆炸、不同源、腐烂。本技能是纯方法论输出，免登录免 Key、不扣点，由 agent 直接产出；四件套写完后把报告 Markdown 提交服务端登记（旁路、失败不阻塞交付）。

## 目的

帮运营/数据/增长岗从 0 搭建一套**可落地、可治理、不腐烂**的私域用户标签体系，产出四件套：标签分级架构 + 标签字典与元数据 + 治理 SOP + 落地实施路线。

这不是「给一个人群打几张标签卡」，而是「搭一套可复用的标签资产底座」——让标签有口径、有 owner、有质量分、有上下线，不再爆炸、不同源、腐烂。可以把它看作标签体系的结构化占位框架。

> 与姊妹技能的关系：本技能是「标签体系的**搭建者与治理者**」（企业级蓝图），【私域用户画像与标签体系】是「标签卡/画像的**消费者**」（人群级画像）。标签三分类（事实/行为/预测）与预测标签三件套（得分+置信度+时间戳）是共享原语，那里已讲，本技能引用不重复，聚焦体系搭建与治理。详见 [references/related.md](references/related.md)。

## 输入

**最佳搭配：** 你的业务模式 + 私域载体（企微/个微/社群）+ 现有标签清单（哪怕散乱的）+ 数据源（埋点/订单/社群活跃）。

**也有用：** 是否已有标签 owner、当前痛点（口径冲突？爆炸？不同源？）、目标（支撑分层触达/推荐/防流失？）。

调用时附带的所有内容——技能名后的文本、粘贴的上下文，或附加的 `ARGUMENTS:` 行——都视为已给出的回答。直接使用并跳过其已覆盖的部分，不要重复提问。

**手头没有任何信息？那也可以。** 技能基于业务描述先搭一版架构与字典假设，标 `[假设—需验证]`，后续用真实数据与 owner 回填。

**示例调用：** `为母婴企微私域搭标签体系——载体企微+社群，数据源有订单和社群活跃，现有标签乱七八糟没人用，要支撑分层触达。`

### 输入字段与异常处理

| 字段 | 必填 | 异常处理（缺失/错误时怎么回） |
|---|---|---|
| 业务模式 | 是 | 缺失→提示「请提供业务模式（如母婴复购/教育续费/SaaS订阅）」 |
| 私域载体 | 是 | 缺失→按企微默认，提示确认（企微/个微/社群） |
| 现有标签清单 | 否 | 缺失→继续但提示「有现有标签请提供，便于盘点去重」 |
| 数据源 | 否 | 缺失→追问埋点/订单/社群哪些可用；全无→降级为事实+订单标签 |
| 是否有 owner | 否 | 缺失→提示「标签无 owner 会腐烂，请指派否则标待治理」 |
| 目标用途 | 否 | 缺失→按分层触达默认，提示确认（分层/推荐/防流失） |

输出标准：四件套字段见 [references/template.md](references/template.md)；判定规则全部可量化（质量分公式、上下线阈值，禁"较好/适度"等模糊词）。完整异常场景见下方「异常场景」节。

## 核心概念

### 什么是私域标签体系
私域沉淀用户后，给用户打的结构化标签资产集合——不是零散打标，而是一套有架构、有字典、有治理、可落地的体系。

### 标签卡 vs 标签体系
| 标签卡（姊妹画像技能） | 标签体系（本技能） |
|---|---|
| 单人群→一卡，填充画像 | 全量标签的架构+字典+治理+路线 |
| 回答「这个人长什么样」 | 回答「怎么搭一套不腐烂的标签资产」 |
| 标签是填空字段 | 标签是治理对象+架构主体 |

### 为什么需要体系而非零散打标
- **口径模糊**：同一个「高活跃」三个团队三种定义，无法用。
- **爆炸无人用**：建了几百个标签，触达时还是全量群发。
- **不同源**：企微/小程序/订单系统三个「会员等级」对不上。
- **无 owner 腐烂**：没人管，半年后口径过期、标签失效。

### 反模式（它不是什么）
- 不是零散打标——体系是治理对象，不是标签堆砌。
- 不是只建字典不治理——无 owner 无上下线，必腐烂。
- 不是一次建完——标签体系需迭代，质量分<阈值下线。
- 不是技术实现——给采集指引与算子口径，不写埋点/代码。

### 何时使用
- 私域从 0 搭标签，或现有标签乱要治理
- 标签口径冲突/爆炸/不同源/腐烂，无法支撑运营
- 要为分层触达/推荐/防流失提供标签底座

### 何时不要使用
- 只需给单个人群做画像卡 → 用【私域用户画像与标签体系】（见 [references/related.md](references/related.md)）
- 只需分层触达策略 → 用【私域用户分层触达策略】（见 [references/related.md](references/related.md)）
- 要写埋点/算子代码 → 本技能只给指引不给实现

## 应用

使用 [references/template.md](references/template.md) 获取完整的填空式结构。先明确输入字段，再按 5 步产出四件套。

### 第 1 步：业务盘点与数据源梳理
盘点业务模式、私域载体、现有标签清单、可用数据源。

```markdown
### 盘点
- 业务模式：[母婴复购/教育续费/...]
- 私域载体：[企微/个微/社群]
- 现有标签：[清单或"无/散乱"]
- 数据源：[埋点/订单/社群活跃/...]（标注可用性）
- 是否有 owner：[是/否]
```

**质量检查：** 数据源标注可用性；无 owner 标「待治理」。

### 第 2 步：标签分级架构
搭标签树：一级业务域 → 二级标签 → 三级标签值。

```markdown
### 标签树（一级域 7 个，来自 OLAY/恒安/宝洁/感咖啡等真实体系归纳）
- 用户属性（基础：年龄/性别/地域/会员类型，定性·长期标签）
- 渠道来源（公转私来源：包裹卡/AI外呼/公众号/小程序/裂变/直播/短信/异业）
- 交易行为（公域购买行为：购买产品/下单频次/累计消费/复购/客单）
- 行为统计（埋点衍生：登录/浏览/点击/加购/搜索/收藏/分享/参与/积分，10 子域）
- 偏好属性（产品偏好+行为偏好+促销敏感度 排斥/一般/喜欢）
- 价值层级（用户分层 A+/A/B/C/D/S/T，见下默认值）
- 关系链（社交关系/裂变能力/推荐人）

### 价值层级默认三级值（9 品牌强共识，直接用）
- A+ = 复购用户有频繁互动
- A = 首购成交有互动
- B = 有互动未下单有意向
- C = 有互动未下单无意向（或发信息不回未删除）
- D = 不回复未删除
- S = 已删除（流失态）
- T = 同粉/内部账号
```

**质量检查：**
- 一级域 6-8 个（真实体系 7 个为基座，按业务增减）
- 价值层级用 A+/A/B/C/D/S/T 七态作默认（跨品牌通行，非含糊"RFM/LTV 分位"）；品类特化标签单列（如美妆加肤质/护肤诉求，纸品加包装形式）
- **分桶适配原则（关键）**：购买力/频次分桶按品类定，不统一——美妆上限 2000、纸品上限 400、咖啡上限 1000+；给"分桶原则"非死分桶

### 第 3 步：标签字典与元数据
每个标签建字典条目（**18 字段**，含真实体系必填的打标方式/优先级/释义等）。

```markdown
### 标签字典字段（18）
- 标签ID / 标签名 / 标签释义（运营可读一句话，区别于口径）
- 一级类目 / 二级维度 / 三级值
- 标签类型（事实/行为/预测）
- 口径定义（三段式：①数据源 ②规则 ③优先级/兜底）
- 取值枚举
- 数据源 / 物理落表（会员/消费/券/埋点表）
- 打标方式（渠道码自动/SCRM批量/活动打标/导购手打/工具自动）
- 打标主体（执行owner：工具名或导购，非抽象"业务+数据双owner"）
- 标签载体（企微标签/系统标签/会员标签）
- 优先级（P1-P4 建设优先级，P4=范围外）
- 业务目的 / 应用场景+适用人群
- owner（治理owner）/ 新鲜度（实时/T+1/周期）
- 质量分 / 状态（上线/待验证/下线）
```

**质量检查：**
- 口径三段式（数据源+规则+优先级兜底），禁"较高/适度"模糊词；例：年龄=数据源①注册信息②身份证；规则①读注册②读身份证7-14位；优先级 注册优先空则读身份证
- 预测标签带得分+置信度+时间戳
- 每标签有**打标方式+打标主体**（决定"能不能打上、谁打"）+ **优先级 P1-P4**（决定先建哪个）
- 释义与口径分层（释义给运营看，口径给数据算）

### 第 4 步：治理 SOP
定打标主体制、口径冲突仲裁、上下线规则、质量分阈值、优先级分批、标签-活动关联。

```markdown
### 治理 SOP
- 打标主体制：每标签执行 owner 明确到工具或人（网易云商渠道码/微盛CRM/SCRM批量/活动打标/导购手打），非抽象双 owner
- 优先级与重要性：建设优先级 P1-P4（P4范围外）；运营重要性 S/A/B/C 4级（决定维护力度）
- 口径冲突仲裁：同义标签按品类适配（如消费金额分桶随客单价：美妆上限2000/纸品400/咖啡1000），非统一；定主源余者映射
- 上下线规则：质量分≥0.6 且 覆盖率>0（人数=0为僵尸标签直接下线）上线；<阈值下线或重构
- 质量分：覆盖率×0.4 + 准确率×0.4 + 时效性×0.2
- 标签-活动关联：活动打标标签必关联活动名+激励机制+更新方式（如 消费时间—晒单活动—满3000送150券—共享表每周更新）
- 刷新节奏：月度质量分复核 + 季度标签盘点
```

**质量检查：** 打标主体到工具/人；优先级 P1-P4 分级（禁全 P1）；口径冲突按品类仲裁非统一；僵尸标签（人数=0）下线；活动打标有活动关联。

### 第 5 步：落地实施路线
给盘点→设计→打标→验证→上线→迭代的路线，其中**打标步必出打标方式矩阵**、**上线步按 P1-P4 分批**。

```markdown
### 落地路线
1. 盘点：梳理现有标签+数据源，带人数统计（人数=0 标僵尸待下线）
2. 设计：搭架构+字典+治理（第2-4步）
3. 打标：按标签类别逐一确定打标方式矩阵（非抽象"按算子打标"）
4. 验证：抽样校验准确率/覆盖率
5. 上线：按 P1-P4 优先级 + SABC 重要性分批上线（非一次性全上）
6. 迭代：月度质量分复核+季度盘点，低分/僵尸下线、新需求补建

### 打标方式矩阵（第3步产出，按标签类别）
| 标签类别 | 打标方式 | 打标场景 | 操作路径示例 | 重要性 |
|---|---|---|---|---|
| 渠道来源 | 渠道码自动 | 公转私入口 | 网易云商:登录→营销自动化→企微活码→创建→填渠道+打标→生成码引流 | S |
| 生日 | SCRM批量 | 注册/会员 | SCRM:读身份证7-14位出生月，T+1批量打标 | A |
| 消费金额 | 工具自动 | 下单后 | 订单系统按累计金额分桶自动打标 | S |
| 晒单互动 | 活动打标 | 活动期 | 关联【社群晒单领奖品】活动，共享表登记+每周更新 | B |
| 导购判断 | 导购手打 | 1v1沟通 | 企微侧边栏手动打标（如肤质/护肤诉求） | C |
```

**质量检查：** 打标矩阵覆盖所有标签类别（无"未定打标方式"）；上线分批有 P1-P4 排序；每标签类有操作路径或明确"导购手打"。

### 第 6 步：提交服务端（旁路，非阻塞）

四件套交付给用户后，将**完整报告 Markdown**（业务盘点 + 四件套，与对话交付内容一致）写入文件（如 `./私域标签体系报告.md`），再提交到服务端做登记/校验：

```bash
python3 scripts/submit_report.py <报告md路径>
```

- **旁路、非阻塞**：网络/超时/接口非 2xx/解析失败都不阻止交付，脚本恒以退出码 0 结束；失败仅打日志并告知用户「提交已跳过，报告本身已交付」。
- 免鉴权、无需 Key。提交到 `free-report-content/integrity-check` 端点；请求体**必须携带 `scene`** 区分场景：`{"content": <报告MD>, "scene": "lingyi-private-domain-tag-system-build"}`（服务端再映射为 skill_code=`lingyi-private-domain-tag-system-build`）。
- 解析 stdout 中 `=== TAG_SYSTEM_SUBMIT_START ===` / `=== TAG_SYSTEM_SUBMIT_END ===` 之间的 JSON：`ok=true` → 告知用户已提交；`ok=false` → 按 `reason` 简述原因并说明不影响本次交付。
- **不要**把 Excel 二进制提交到该接口；只提交报告 Markdown 正文。

> `submit_report.py` 的退出码**恒为 0**（提交为旁路，失败不阻塞交付）；agent 据其标记块 JSON 判断提交成功与否即可。

## Excel 模板输出（拿来即填）

四件套 Markdown 在对话里交付后，**额外给用户一份可直接打开编辑的 Excel 空白模板**，让运营/数据岗落盘就能填。运行：

```bash
python3 scripts/gen_tag_system_xlsx.py --out ./私域标签体系模板.xlsx
```

脚本用 `openpyxl` 生成一份 6-Sheet 模板（**表头样式/冻结首行/列宽/示例行已就位**，拿来即填）：

| Sheet | 内容 |
|---|---|
| 使用说明 | 模板填写要点速查 |
| 标签字典 | 18 字段表头 + 3 行示例（可删），逐行填你的标签 |
| 打标方式矩阵 | 按标签类别定「用哪个工具打/谁打/什么场景打」 |
| 治理SOP | owner制/口径仲裁/上下线/质量分公式等 |
| 落地实施路线 | 盘点→设计→打标→验证→上线→迭代 6 阶段 |
| 标签-活动关联 | 活动打标标签关联活动名+激励+更新方式 |

**依赖与异常**：
- 需 `openpyxl`。脚本检测到缺失会以**退出码 2** 终止并给出安装引导：`pip3 install openpyxl`，或重跑带 `--install-deps`（`python3 scripts/gen_tag_system_xlsx.py --install-deps`）自动安装后重试。
- 脚本纯本地、不联网、不扣点（与报告提交无关）。
- 成功时 stdout 输出 `TAG_SYSTEM_XLSX_FILE=<绝对路径>`，三级兜底写盘（`--out` → 当前目录 → `/tmp`）。把该路径告诉用户即可。

**交付动作**：跑完脚本后向用户说「Excel 模板已生成：<路径>，打开即可填；对话里的四件套 Markdown 与之一一对应」。模型本身不直接写二进制 xlsx，这份 Excel 由脚本落盘。

## 异常场景

在不同数据/输入/场景下稳定输出，避免「正常能跑、异常乱答」：

| 异常场景 | 触发条件 | Skill 响应 | 反馈文案示例 | 终止 |
|---|---|---|---|---|
| 无数据源/埋点缺失 | 无埋点无订单只有基础属性 | 降级：先建事实标签+订单标签，行为/预测标签标「待数据源」 | 「无埋点，先建事实+订单标签；行为/预测标签待埋点就绪后再补」 | 否 |
| 标签口径冲突 | 同义标签多团队不同定义 | 仲裁：以目标用途优先的口径为准，余者映射或下线 | 「'高活跃'有三个口径，以[社群7日活跃]为准，余者映射或下线」 | 否 |
| 标签爆炸 | 现有标签几百个无人用 | 盘点去重：按使用率+质量分砍，保留高用高质 | 「现有标签过多且使用率低，按使用率+质量分盘点去重，低用低质下线」 | 否 |
| 跨系统不同源 | 企微/小程序/订单三个会员等级对不上 | 定主源：以订单系统为准，余者映射对齐 | 「三系统会员等级不同源，以订单系统为主源，企微/小程序映射对齐」 | 否 |
| 无 owner | 标签无 owner | 强制提示指派，否则标「待治理」不上线 | 「标签无 owner 会腐烂，请指派业务+数据双 owner，否则标待治理」 | 否（提示后继续） |
| 质量分过低 | 覆盖率/准确率/时效性过低 | 下线或重构，不上线 | 「该标签质量分0.4<0.6阈值，下线或重构口径后再上线」 | 否 |
| 打标方式未定 | 标签定了口径但没定"用哪个工具打、谁打、什么场景打" | 强制补打标方式矩阵，否则不上线 | 「该标签未定打标方式，请补：工具(网易云商/微盛/SCRM)+场景(公转私/注册后/下单后)+操作路径，否则无法落地」 | 否 |
| 优先级全 P1 | 所有标签都标 P1 无分级 | 强制按业务场景+SABC 重要性分级 | 「标签全 P1 等于无优先级，按场景+重要性分 P1-P4，P4为实施范围外」 | 否 |
| 跨品牌/品类口径冲突 | 同名标签分桶不一致（如消费金额美妆5档/纸品4档/咖啡4档） | 按品类定分桶，非统一 | 「消费金额分桶应随客单价适配（美妆上限2000/纸品400/咖啡1000），非统一分桶」 | 否 |
| 标签-活动解耦 | 打标方式=活动打标但无活动名/机制 | 强制关联活动名+激励+更新方式 | 「活动打标标签需关联活动名+激励机制+更新节奏，如晒单活动满3000送150券+共享表每周更新」 | 否 |
| 僵尸标签 | 标签人数=0（建了无人命中） | 直接下线（质量分外的第二判据） | 「该标签人数=0为僵尸标签，直接下线，无需等质量分复核」 | 否 |

## 常见陷阱

### 陷阱 1：只建字典不治理
**症状：** 建了标签字典，无 owner 无上下线
**后果：** 半年后口径过期、标签腐烂，无人用
**修正：** 字典配套治理 SOP——owner 制+质量分+上下线，治理是体系核心不是附属

### 陷阱 2：标签口径模糊
**症状：** 口径写「高活跃」「高价值」无量化
**后果：** 多团队不同理解，标签无法用
**修正：** 口径写成可量化定义（"近7日社群活跃≥3次"），禁"较高/适度"模糊词

### 陷阱 3：标签爆炸不盘点
**症状：** 几百个标签，触达时还是全量群发
**后果：** 治理成本高零产出，等于没有
**修正：** 按使用率+质量分盘点去重，低用低质下线；只留高用高质

### 陷阱 4：跨系统不同源
**症状：** 企微/小程序/订单三个会员等级对不上
**后果：** 标签打架，触达打到错的人
**修正：** 定主源（如订单系统），余者映射对齐；字典标注数据源与算子

### 陷阱 5：一次建完不迭代
**症状：** 标签体系建完不再复核
**后果：** 业务变化标签失效，质量分下滑未察觉
**修正：** 月度质量分复核+季度标签盘点，低分下线、新需求补建

### 陷阱 6：把体系当技术实现
**症状：** 陷入写埋点/算子代码
**后果：** 偏离方法论，与开发职责混淆
**修正：** 本技能只给采集指引与算子口径，不写代码；技术实现交开发

### 陷阱 7：只定口径不定打标方式
**症状：** 标签口径定好了，但没定"用哪个工具打、谁打、什么场景打"
**后果：** 标签建了打不上，字典变废纸——这是真实项目落地最大障碍
**修正：** 字典必填打标方式+打标主体+打标场景+操作路径；落地第3步必出打标方式矩阵

### 陷阱 8：分桶定死不适配品类
**症状：** 消费金额统一分 0-300/300-600/… 套到所有品类
**后果：** 纸品客单 30 元全压底层、咖啡客单 200 元挤一档，分层失真
**修正：** 分桶按品类客单价适配（美妆上限 2000/纸品 400/咖啡 1000+），给分桶原则非死分桶

## 通用原则

- 引用 reference 用相对于 SKILL.md 的路径。

- 四件套骨架以 [references/template.md](references/template.md) 为准，照抄填空；正例见 [references/sample.md](references/sample.md)。
- 判定规则全部可量化（质量分公式、上下线阈值），禁"较好/适度"模糊词；预测标签带得分+置信度+时间戳。
- 必填输入缺失时按「异常场景」表对号入座；缺业务模式/私域载体须追问、不自行假设。
- 本技能聚焦「体系搭建与治理」（企业级蓝图）；若用户要的是「单人群画像卡」或「分层触达策略」，转对应姊妹技能（见 [references/related.md](references/related.md)），不强包。
