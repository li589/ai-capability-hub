# 信息收集与交付约定

## 待检字段

| 字段 | 必填 | 示例 | CLI |
|------|------|------|-----|
| 选题/话题（topic） | 是 | 「夏日油皮防晒怎么选」 | `--text` |
| 正文字数（word_count） | 是 | 800（100–50000） | `--word-count` |
| 产品名称 | 是 | 「XX 清爽防晒霜」 | `--product-name` |
| 产品卖点（≥1） | 是 | 「SPF50+ 不油腻」 | `--selling-points`（可多次） |
| 目标受众描述 | 是 | 「25–35 岁油皮职场女性」 | `--audience-desc` |
| 受众痛点（≥1） | 是 | 「出油脱妆快」 | `--pain-points`（可多次） |
| 内容形式 | 否 | 贴图号（默认）/公众号 | `--content-format` |
| 封面比例 | 否 | 3:4（贴图号默认） | `--cover-ratio` |
| 配图比例 | 否 | 3:4（贴图号默认） | `--body-ratio` |
| 内容调性 | 否 | 知识型等（需 `--fetch-config` 拉实时枚举） | `--tone` |
| 主图/封面数量 | 否 | 1（1–5） | `--main-image-count` |
| 正文配图数量 | 否 | 1（1–5） | `--inset-image-count` |
| 候选标题数量 | 否 | 3（1–5） | `--title-count` |
| 产品价格 | 否 | 99（≥0） | `--product-price` |
| 价格带 / 决策类型 | 否 | mid / considered | `--price-band` / `--decision-type` |
| 受众年龄段 / 性别 | 否 | 25-35 / female | `--audience-age` / `--audience-gender` |

> 可选字段「可引导但不强制、缺省不传」走后端默认。**禁止发送** `scene`/`account_id`/`*_image_quality`/`*_image_size`（脚本不会构造这些，夹带会被服务端 422）。

## 收集流程

1. 触发 skill 后先判断必填输入是否齐全（六项必填）。
2. **必填齐全** → 直接执行（默认参数；内容形式缺省走贴图号）。
3. **有缺失** → 一次性追问缺失项（只问 1 轮）。话术示例：
   > 技能已就绪 ✅ 帮你生成贴图号爆款图文。方便补我几条信息就能开始：
   > 1. **选题/话题**——想写什么主题（默认会据此生成标题与正文）
   > 2. **正文字数**——想多长（100–50000，常见 600–1200）
   > 3. **产品名称 + 至少 1 条卖点**——推广什么、亮点是什么
   > 4. **目标受众 + 至少 1 条痛点**——写给谁、他们愁什么
   > 不指定内容形式/比例/调性也行，我用默认（贴图号、3:4 比例）。
4. **仍不给** → 用默认继续，不阻塞。

要点：一次问清，不挤牙膏；不展示技术字段名（如不出现 `xiaolvshu`/`image_message`/`knowledge`，用「贴图号/公众号」「知识型」等自然语言）。

## 调用与重试

- **主路径（异步）**：`POST /api/v1/content/article-generation` 立即拿 `task_id` → `GET /{id}` 轮询 → `completed` 交付 `data.markdown`。
- **拆分轮询（WorkBuddy/Web 防会话中断，推荐）**：
  - 创建：`python3 scripts/article_generation.py --text "<选题>" --word-count 800 --product-name "..." --selling-points "..." --audience-desc "..." --pain-points "..." --only-create`（退出码 0，拿 task_id）
  - 轮询：`python3 scripts/article_generation.py --poll-task <task_id> --text "<同上>" --out ...`（退出码 13 仍运行，再跑一次；退出码 0 交付报告）
  - ⚠️ `--poll-task` 必须带 `--text`（与创建时相同），否则报告标题退化为「任务 xxx」。
- **调性枚举**：用户要选内容调性时，先 `python3 scripts/article_generation.py --fetch-config` 拉取实时 `tone` 枚举展示，选定后以 `--tone` 传入创建。`--fetch-config` 不创建任务、不扣点。
- **默认报告文件**：未传 `--out` 时，脚本自动写当前目录的 `爆款图文-<task_id>.md`。
- **实扣字段**：`data.total_points`（整数，终态 `completed` 后返回）。
- **进度**：脚本 stderr 周期输出，用户中途问「跑到哪了」时读 stderr 最新行转述（status / 当前阶段 / progress_message / 已用时 / task_id），不要说「查不了」。
- **失败重试（偏差）**：本 API **无 `/retry` 接口**。若输出含 `ARTICLE_GEN_TASK_ID` 或 stderr 含 `task_id=`，用户同意后用 `--retry-task <旧id> --text <选题> <业务参数> --out ...`——脚本会用相同参数**重新创建新任务**（新 task_id、**独立扣费**）。须重供 `--text` 与全部业务参数以重建请求体。
- **无幂等（偏差）**：本 API 无幂等机制（文档无 `idempotency` 字段，§3.2 禁未声明字段），脚本不发幂等头、不注入 body、无 `--idempotency-key`。**重复提交会新建任务、独立计费**——故同一意图不要重复点「再提交」，需重新生成时再调用创建；用户说「刚才那次再提交」时先确认是否真的要新建一次（会再扣费）。

## 交互节奏

- **收集**：最多 1 轮追问，之后用默认继续，不让用户反复等待。
- **扣点确认（硬性，跳过不得）**：跑脚本**前**必须告知「本次任务预计扣点 60 点起步，最终以服务端实际扣除为准，是否继续？」，用户**明确确认**后才跑脚本。重试时如实说明「重新提交会再计费」。
- **速度差异**：说明本次大约耗时（如「全量约 1–2 分钟，期间 stderr 会有进度」）。用户问进度时转述 stderr，勿空等不回。
- **交付**：报告 MD 一次性渲染给用户（务必把分隔符之间的 Markdown 真正渲染出来，不能只甩文件路径或贴带 `\n` 的原始文本）。后端渲染的封面图/配图/正文原样呈现，**不要本地改写、总结或重排**；后端 `markdown` 已自带一级标题，脚本不再重复加标题，你也不用补。
- **成功后**：告知实际扣除点数（如「本次实际扣除 15 点」）+ 报告查看方式（已渲染在上方 + 已存为 MD 文件）。
- **失败后**：告知「因网络原因本次任务执行失败，相应点数已返还」；有 task_id 时询问是否用 `--retry-task` 重新创建（独立扣费）。
- **交付后**：主动询问是否需要后续动作（如「换一种内容调性再生一版」「某条卖点再强化」「生成公众号版本」）。
