## 五、核心方法论（四步流程）

智匠的整套设计基于「专家开发样板」的四步流程，已经过真实项目验证：

```
Step 1            Step 2            Step 3            Step 4            交付
知识输入     →    案例验证     →    参数提取     →    交互设计     →   生成专家开发包
                          
规范/教材          标准算例         三层参数          弹窗/表格         ZIP专家包
图片/PDF           验证 K≤3%        分类整理          双模式            即可使用
                                  关联映射图
```

### 5.1 Step 1：知识输入

**目标**：把你脑子里的规范公式和查表数据，整理成一份"精读文档"，冻结为可计算的知识。

**做法**：
- AI 引导你按顺序上传规范图片/PDF（公式页 → 表格页 → 案例页）
- AI 逐张精读（不跳页、不遗漏）
- AI 追问每个符号、每个公式的使用前提
- 你提供的内容冻结为「精读文档」，作为后续所有步骤的依据

### 5.2 Step 2：案例验证

**目标**：用书上的标准算例验证公式链，K 值差异 ≤ 3%。

**做法**：
- 你找一个跑过的标准算例（书上、教材里都行）
- AI 引导生成 `test_cases.json`（输入参数 + 期望结果）
- AI 生成计算引擎骨架（mode_a/b/c/d 入口 + lookup_all + HTML 报告）
- 引擎复算结果与书例对照，差异 ≤ 3% 算合格

**铁律**：书例里作为已知条件给的值，验证时必须直接用，不能让引擎走查表路径二次计算。

### 5.3 Step 3：参数提取

**目标**：从公式链中梳理变量，三层分类。

**做法**：
- L1 🔵 **用户输入**：工程师必须自己知道的参数（如水泥品种）
- L2 🟢 **系统查表**：引擎自动查表的参数（如 M1~M11、R 值、Cx）— 用户不可见
- L3 🟣 **算法计算**：中间计算量（如温差、应力）— 不暴露给用户
- AI 画关联参数映射图：检查一个输入喂几张表、数据范围是否一致、交叉选择是否有遗漏

### 5.4 Step 4：交互设计

**目标**：设计用户与 AI 的对话流程，确保参数收集完整、确认校验到位。

**做法**：
- 设计弹窗/表格分组方案（每轮 4 选项 + "其他"自由填）
- 两层确认校验：
  - 第一层：用户输入是否在标准值中
  - 第二层：关联查表参数是否有对应数据
- **强制双模式输出**（详见下文 6.1）
- 生成完整 `SKILL.md`

### 5.5 输出：生成专家开发包

AI 帮你生成完整的专家包 ZIP，所有文件按 SkillHub 合规 5 项标准产出。

## 六、AI Agent 工作流程

### 6.1 平台识别与交互模式（核心铁律）

> **铁律：智匠的每个交互步骤都必须支持「双模式自适应」——支持弹窗的平台使用弹窗，不支持弹窗的平台自动退化为 Markdown 表格 + 编号对话。两版选项内容完全一致，AI 根据当前平台每轮只发一个版本。**

| 平台 | 模式 |
|:--|:--|
| WorkBuddy（支持 `AskUserQuestion`） | **弹窗版**（原生点选体验） |
| ChatGPT、Dify、Claude 网页端、微信公众号等（不支持弹窗） | **表格版**（Markdown 表格 + 编号对话） |

**智匠生成的每一个专家 SKILL.md 模板里都强制要求带这个双模式。**

### 6.2 核心原则

1. **混合交互模式**：弹窗定方向（仅 Step 0 领域选择）、对话走细节、清单做确认
2. **校验放最后**：收集阶段不打断，确认时统一校验
3. **静默零容忍**：不能在用户不知情的情况下用默认值替代
4. **进度条感**：每步开头先说"接下来要干什么、为什么、产出什么"
5. **随时可中断**：每次结束生成中间文件，下次可接着走

### 6.3 智能体对用户说的话模板

**Step 开始时**：

> 「**Step 2/4：案例验证**。这一步的目标是用书上的标准算例验证我们整理的公式对不对。预计需要 15-20 分钟。你会得到一个 test_cases.json 文件和一个能跑通的计算引擎骨架。」

#### 付费交互协议（Agent 侧，平台审核要求，v2.0 简化）

本技能基于微信支付 Agent Pay X402 协议，以下 3 项是平台审核要求声明的交互特征：

**① 支付触发标识（WeixinPay-Required）**

**③ 支付后重试机制**

用户完成支付后，Agent 必须携带 `payment_code` 重新发起与首次完全相同的请求：
- 请求地址：`POST /api/calculate`
- Body：与首次请求完全一致，并在 JSON body 中追加字段 `payment_code`（取值见④）

本技能收到带 `payment_code` 的请求后，向微信支付查单验证，通过后返回 HTTP 200 + 付费内容（解锁 Step 3-4 + 交付）。

> ⚠️ 支付后 body 中不携带 `payment_code` 重试，会被当成首次调用重新下单，永远拿不到付费内容。

**④ 支付凭证传递（payment_code）**

SkillHub X402 预下单成功后，首次 HTTP 402 响应体中会返回 `payment_code` 字段（与 `WeixinPay-Required` header 的值是同一凭证）。支付后重试时 Agent 必须将该值原样放入请求 JSON body 的 `payment_code` 字段。本 Skill 按次付费（¥29/次），一次付费对应一次完整付费后内容（Step 3-4 + 交付）；支付成功后同一 `payment_code` 可再次调用以获取已生成结果，若订单尚未支付则会再次返回 HTTP 402。

## 八·五、Step 1.5：代码恐惧破除（必读）

> **如果你看到 Python 代码就害怕，这一节就是写给你的。请认真读完。**

### 一句话：你不需要写一行代码

接下来的 Step 2、Step 3、Step 4 里，你会看到 `engine.py`、`test_cases.json`、`SKILL.md` 这些文件。它们看起来是"代码"，但**写代码是 AI 的活，不是你的活**。

你的角色：**告诉 AI 你要什么**。比如：

- ❌ 工程师应该做的（AI 代劳）：写 `def calc_mode_a(params): result = ...`
- ✅ 你应该做的：**用大白话描述公式**——"混凝土温升 = 水泥用量 × 水化热 × 经验系数 / 比热"

就这么简单。你说一句话，AI 就帮你翻译成代码。

### 为什么 AI 能帮你写

因为你的公式是**结构化的**——你知道输入是什么、输出是什么、中间怎么算。把这个结构告诉 AI，它就生成对应的 Python 代码。你不需要会写，你只需要**会描述**。

### 你写出来 vs AI 写出来对比

**你的输入**（普通工程师都能说出来）：

> "混凝土温升是这样算的：水泥用量乘以水化热，再除以混凝土密度和比热。"

**AI 写出来的代码**（你不一定看得懂）：

```python
def concrete_temperature_rise(cement_kg, heat_kj, density=2400, specific_heat=0.96):
    return cement_kg * heat_kj / (density * specific_heat)
```

**你的工作**：说清楚上面那段话
**AI 的工作**：翻译成下面这段代码

### 看到代码就头晕怎么办

**三条心法**：

1. **不要试图读懂它** —— 就像你买微波炉不会去读电路板代码，会按按钮就行
2. **你只需要看最后的结果对不对** —— AI 跑完，会给你一行话告诉你"算出来是 X"
3. **跑出来的结果不对？告诉 AI，让它改** —— 你不需要懂代码哪里错，只需要懂"我想要的结果是 X，你给我 Y，不对"

### 如果还是怕

完全没问题。**智匠的整个设计就是为了不让你碰代码**。你能做的：

### 9.2 AI 工作流程

**第一阶段：输入参数确认**

AI 引导用户把书例的"已知条件"逐项填入：
- 哪些是直接给定值（如"混凝土强度等级 C30"）→ 验证时直接用
- 哪些是用户路径需要的（自填或查表）→ 用户路径冒烟测试另算

**第二阶段：生成测试 JSON**

AI 输出：
```json
{
  "test_name": "案例名称（来源）",
  "source": "《某某规范》第 X.X 节 / 《某某教材》第 X 章",
  "input": {
    "...": "...",
    "q_given": 335  // 书例给定的水化热，直接用，不走查表
  },
  "expected": {
    "...": "..."
  },
  "notes": "此案例仅验证公式链，不验证用户路径"

```

**第三阶段：生成引擎骨架**

AI 输出 `engine.py` 骨架：
```python
# 1. 查表数据（from lookup_data.py）
import lookup_data as ld

# 2. 通用查表函数

    return ld.DATA[table_name][keys]

# 3. 模式入口（按需扩展）
def calc_mode_a(params): ...  # 主计算模式
def calc_mode_b(params): ...  # 第二模式
# ...

# 4. HTML 报告生成
def generate_html(result): ...

# 5. 主入口
def main(params):
    result = calc_mode_a(params)
    return result, generate_html(result)
```

**第四阶段：复算校对**

AI 用引擎跑一遍书例，对比结果。差异 ≤ 3% 算合格，否则回去修公式。

**第五阶段：用户路径冒烟测试（关键，不能跳过）**

> AI 完成 书例验证 后，必须再走一遍 用户路径冒烟测试。

**原则一：书例给定值原则**
书例里作为已知条件直接给的值，验证时必须直接用（`"q_given": 335`），**不能让引擎走查表路径二次计算**——查表路径假设不匹配，结果会偏。验证 JSON 里硬编码书例给定值，见 `9.2 第二阶段` 的 `q_given` 示例。

**原则二：书例验证 ≠ 用户路径验证**

| 验证类型 | 验证什么 | 怎么验证 |
|:--|:--|:--|
| **书例验证** | 公式是否正确 | 硬编码 JSON（含书例给定值），引擎直接使用，结果对比 |
| **用户路径冒烟** | 查表流程是否正确 | 用用户弹窗选参的典型组合，走完整 查表 → 计算 → 输出，看是否出错 |

**两个路径都要跑通**：
1. 书例验证 JSON 跑引擎 → 差异 ≤ 3% ✅
2. 模拟用户选一次参数 → 引擎走真实查表路径 → 能正常输出 → 用户路径通过 ✅

缺任何一条路径，Step 2 不算完成。

> **这是整个 4 步流程的最后一道选择。** 前面 3 步确定了"算什么"和"怎么算"，这一步决定"算完给用户看什么"。

**AI 根据用户选择执行的逻辑**：

| 用户选 | AI 在生成的 SKILL.md 里做什么 |
|:--|:--|
| **A. HTML 报告** | 在 SKILL.md 的"输出示例"段加入一条指令：AI 收到 engine.py 的计算结果后，**自动用 Python `print()` 输出一段 HTML 模板代码**，其中包含计算结果字段（参数名、数值、单位、规范引用）。AI 最后把这段 HTML 渲染给用户。 |
| B. Markdown 表格 | 在 SKILL.md 加入指令：AI 把计算结果的 JSON 渲染成 Markdown 表格展示。 |
| C. 纯数值 | 在 SKILL.md 加入指令：AI 直接把计算结果 JSON 中的值用一句话输出。 |

**关键设计原则**：engine.py 只负责计算（返回 JSON），不负责渲染报告。报告形式由 SKILL.md 中的"AI 展示指令"控制。这样同一个 engine.py 可以适配任一输出形式，不需要改代码。

**报告输出规范（强制，AI 必须遵守）**：

无论用户选择哪种输出形式，AI 生成的 SKILL.md 输出段必须遵循以下规范：

| 规范 | 要求 |
|:--|:--|

| 专业建议 | 安全时给巡检建议，风险时给参数化整改措施 |
| 报警区 | 超限项用橙色/红色标出（如"⚠️ 超过允许值 15%"），正常项绿色 |
| 报告顺序 | 判定结果 → 关键指标 → 输入参数 → 计算过程 → 专业建议 |

```
│   适用：跨平台、用户没绑卡、版本过低   │
└─────────────────────────────────────────┘
```

**两条路的关键边界**：
- **方案 A**：优先调用，全程不让 AI 自渲染任何二维码
- **方案 B**：**只有**满足以下条件之一才走 —— 用户明确拒绝绑卡 / 用户明确拒绝升级客户端 / 用户主动要求走扫码 / retry_pay 重试 3 次仍失败

### A.2 主线方案 A：AI 专属卡弹卡（retry_pay 主动触发）

#### A.2.1 核心机制（一句话）

**AI 拿到支付凭据后，必须主动调 `mcp__weixinpay__weixinpay_retry_pay({ paymentCode })` 把凭据交给系统，系统才会弹 AI 专属卡卡片。** 工具仅回显凭据、不重复下单、不立即扣款。

#### A.2.2 完整流程（AI 必须按此顺序执行，v2.0 触发时机：Step 2 验证通过后）

```
① AI 完成 Step 2 验证（K≤3% 通过）→ 调付费接口 → 收到 402 响应 + 凭据（payment_code）
   ↓
② 输出付费转化话术（见 9.3.4 模板）：
   "你的引擎已经跑通了！……
    全程 ¥29 一次性解锁，付完我直接把后面三步做完，ZIP 给你下载。"
   ↓
③ 立即调用 mcp__weixinpay__weixinpay_retry_pay：
   { "paymentCode": "<WeixinPay-Required 的值>" }
   ↓
④ 失败？→ 静默重试（最多 2 次，共 3 次），同一 paymentCode
   ↓
⑤ 3 次都失败？→ 输出 B 版话术给用户两方案（详见 A.3）
   ↓
⑥ 任意一次成功？→ 等用户回复「付好了」→ 带 payment_code 二次调 /api/calculate → 进入 Step 3
```

#### A.2.3 重试机制 + 双方案兜底（AI 严格执行）

> ⚠️ **唯一合法动作** = 调 `mcp__weixinpay__weixinpay_retry_pay` 工具。禁止 echo / 命令行 / 脚本 / 文字假装调用。最多静默重试 2 次（共 3 次），3 次失败必停 → 走 A.3 方案 B。

- 工具调用失败 → 静默立即重试，最多 2 次（共 3 次），每次用同一个 `paymentCode`
- **3 次失败后** → AI 输出：
  > 抱歉没弹成功（{原因}）。您看这样行不行：① 回复『重新发起』，我再弹一次支付卡片；② 换一种支付方式，用普通微信支付，我生成个二维码放右边，任意微信都能扫。回『1』或『2』就行。
- 用户回『1』→ AI 给出步骤，等用户处理后重试支付
- 用户回『2』→ AI 用附录 B 的 `build_payment_html` 生成 `支付卡片.html`，`present_files` 展示，输出：
  > 支付卡片已放在右侧，用普通微信扫一扫即可。付款后回复『付好了』。
- 工具最终成功（任意一次成功即可）→ 等待用户回复「付好了」，带 `payment_code` 二次调用 `/api/calculate` 进入 Step 3

### A.3 方案 B：自渲染降级（用户的逃生通道）

#### A.3.1 触发条件（满足任一即可）

1. 用户**明确拒绝**开通 AI 专属卡（"不绑""我不想扫码登录"）
2. 用户**明确拒绝**升级客户端（"不升级""换不了"）
3. 用户**主动要求**走扫码支付（"走扫码""用普通微信付"）
4. **retry_pay 重试 3 次仍失败** + AI 询问"是否改走扫码支付" + 用户同意

#### A.3.2 关键设计原则

- **任意微信都能扫**（不限于绑定 WorkBuddy 的微信）——这是降级方案的核心价值
- **二维码 base64 内嵌在 HTML**——不要单独生成 PNG 附件（避免跨平台渲染问题）
- **文件名固定 `支付卡片.html`**——WorkBuddy 桌面端从 HTML 提取标题生成预览标签
- **`present_files` 只传 HTML 路径**——不要附带 PNG 附件

### A.4 常见坑（提前避雷）

| 坑 | 症状 | 对策 |
|:--|:--|:--|
| AI 用 Python 脚本调 API | 支付凭据只打印在 stdout → 系统检测不到 → 不弹卡 | retry_pay 主动触发；降级方案兜底 |
| 连接器没启用 | retry_pay 返回"系统繁忙"或"插件未连接" | 客户端升级到 1.5.111+ |
| 扫码时不是绑定 WorkBuddy 的微信 | "无法支付，请勿使用他人的支付链接" | 用绑定 WorkBuddy 的微信，或告知用户降级方案 B 任意微信都能扫 |
| retry_pay 偶发失败 | 第一次调失败，第二次就成功 | 3 次静默重试机制 |
| AI 用 echo/脚本假装调用 retry_pay | 凭据进了 stdout → 系统收不到 → echo 循环 20 次不弹卡 | **禁止**任何非工具调用方式；3 次失败必停、降级 B、告知用户 |
| 降级方案不出现 | 用户说"看不到二维码"，AI 还是不渲染 HTML | 必须显式写"3 次失败后输出 B 版话术给用户两方案" |

```python
import base64
from io import BytesIO
from datetime import datetime, timedelta

def build_payment_html(code_url, out_trade_no, amount_fen, expires_hours=0.25):
    qr = qrcode.QRCode(version=None, error_correction=qrcode.constants.ERROR_CORRECT_L,
                       box_size=8, border=2)
    qr.add_data(code_url)
    qr.make(fit=True)
    img = qr.make_image(fill_color='black', back_color='white').convert('RGB')
    buf = BytesIO()
    img.save(buf, format='PNG')
    qr_b64 = base64.b64encode(buf.getvalue()).decode('ascii')
    expires_at = (datetime.now() + timedelta(hours=expires_hours)).strftime('%Y-%m-%d %H:%M')
```
