# 增值税税负分析

根据单一纳税主体一个或多个期间的增值税申报与经营数据，形成可复核的税负分析。目标用户为企业财务、税务专员、代账人员和税务管理人员。把“指标计算”“数据异常”“业务解释”和“政策判断”分开陈述；税负高低只是一项分析信号，不得据此认定违法或税务机关风险等级。

## 能力边界

- 计算一般计税、简易计税、综合申报和实缴口径的增值税税负；执行环比、同比或指定期间比较。
- 校验销售额、销项税额、进项抵扣、进项转出、期初/期末留抵、简易计税税额、减免、加计抵减、预缴、应纳和实缴数据。
- 按销售结构、销项、进项、留抵、进项转出、简易计税、减免和预缴等因素解释变化。
- 不代替申报，不写入电子税务局、ERP 或财务系统，不自动修改用户文件；默认仅处理用户主动提供的数据。
- 不系统匹配优惠资格；此类请求转交 `match-vat-incentives`。泛政策问答转交 `tax-policy-qa`。
- 不对出口退免税、进口环节、复杂跨境或集团交易作确定结论。没有可靠同口径数据时，不提供行业平均税负或“预警线”。
- 拒绝虚增进项、延迟确认收入、拆分交易、虚假申报等违法降税要求；转为提供数据复核、更正申报和合规咨询方向。

## 输入与前置条件

最低输入为分析期间、纳税人类型、不含税应税销售额，以及当期应纳增值税额或足以推导该金额的数据。还要识别用户目标：单期测算、多期比较、波动归因或异常检查。完整字段、单位和空值规则见 [输入数据模型](references/input-schema.md)。

未知字段保持未知，不得以零代替；只有用户明确表示“本期无该事项”时才记为零。一次最多优先追问 3 个会改变结论的关键字段。信息不足但仍可计算部分指标时，明确分析范围和假设后继续；分母为零或期间口径不一致时，不计算税负率。

## 执行步骤

1. **确认分析单元。** 锁定一个纳税主体、期间范围、纳税人类型和对比基准。发现多个主体时分别分析，不合并计算。
2. **声明计算口径。** 阅读 [计算口径](references/calculation-rules.md)，明确分子、分母、含税/不含税、元/万元、月/季/年，以及一般计税、简易计税、预缴、留抵退税是否纳入。默认以“申报应纳增值税额 ÷ 不含税应税销售额”为综合税负率；应纳与实缴必须分列。
3. **标准化数据。** 保留原始值，统一期间、单位、正负号和精度。不得静默修改异常数据。含税销售额只有在税率或征收率明确时才能换算。
4. **执行质量检查。** 按 [勾稽与校验规则](references/reconciliation-rules.md) 检查必填项、合计关系、留抵连续性、计算关系、重复期间、负数和异常空值。重大勾稽差异未解释前，结论标记为“数据异常”，不得给出确定性业务归因。
5. **计算指标。** 数据为结构化 JSON 且需要重复、批量或高精度计算时，运行 `scripts/analyze_vat_burden.py`；调用方式和返回字段见脚本帮助及输入模型。简单单期数据可直接计算，但必须展示公式、代入值、结果和四舍五入规则。
6. **比较并归因。** 多期数据按 [诊断规则](references/diagnostic-rules.md) 计算税负率变动、应纳税额变动及组成项目差额。把数值证据与用户提供的业务背景对应；缺少背景时只列“可能原因”和所需证据，不写成事实。
7. **生成结果。** 严格使用 [输出模板](references/output-template.md)。每项异常按“现象 → 数值证据 → 可能原因 → 尚缺信息 → 建议核查动作”书写，结论状态只使用“数据异常”“波动需要解释”“政策适用待核验”“暂未发现明显异常”。
8. **复核交付。** 检查公式、单位、期间、口径、合计关系、结论强度和限制说明。涉及会变化的政策、税率、资格或办理规则时，只访问财政部和国家税务总局官网核验，并紧邻结论引用；核验失败则标记“政策适用待核验”。

## 输出与质量要求

先给结论摘要，再给分析口径、核心指标、勾稽结果、波动拆解、异常、待核实事项、合规建议和限制。所有百分比默认保留 2 位小数，金额保留 2 位小数；内部计算不得提前舍入。不得把示例计算表述为申报结果，不得把相关性表述为因果关系。重大金额、税务争议、复杂资格或地方执行口径只提供初步分析，并建议用户向主管税务机关或具备资质的专业人士确认。

## 权限与安全

本技能的脚本仅读取用户指定的本地 JSON 文件并向标准输出返回 JSON；不联网、不写文件、不删除或覆盖数据、不调用外部 API。不得把用户数据写入 `references/`、测试样例或公共位置，不索取账号、密码、令牌、完整身份证号或无关交易明细。未来如增加文件写回、系统接口或外部传输，必须另行声明目标、影响、凭据注入方式，并在执行前取得用户确认。

开发和回归验证时，使用 [测试案例](references/test-cases.md) 覆盖正常、边界、失败、违规和超范围场景。典型使用与预期产出见 [Playbook 案例](references/playbook-example.md)。
