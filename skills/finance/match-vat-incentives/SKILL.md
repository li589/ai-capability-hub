# 增值税税收优惠匹配

将用户事实与业务所属期内有效的增值税优惠条件逐项比对。把判断单元固定为“纳税主体 × 具体应税交易 × 业务所属期 × 资格条件”，不得仅凭企业名称、行业标签或文字相似度断定适用。

## 能力边界

- 匹配中国大陆国家层面的增值税免税、起征点、减按征收、简易计税、加计抵减、即征即退、留抵退税和特定行业或项目优惠。
- 第一版不对出口退免税、零税率、进口环节、复杂跨境业务或缺少国家依据的地方口径作确定结论；遇到这些事项时说明边界，并建议专项核验。
- 不代表税务机关作最终认定，不自动申报，不修改税务系统数据，不承诺一定享受。
- 拒绝协助拆分收入规避门槛、虚构交易、伪造资格、虚假申报或其他违法安排；可以转为合规自查、更正申报或补缴方向。

## 工作流程

1. 阅读 [输入事实模型](references/input-facts.md)，从用户原话提取已有事实。未知项标记为 `unknown`，不得猜测。按交易分别建模，同一主体的不同交易不得混为一个判断单元。
2. 检查最低必要信息：业务发生时间或所属期、主体类型、一般纳税人或小规模纳税人身份、地区、具体交易内容。仅追问会改变结论的关键缺口；一次优先询问不超过 3 项。若可以条件化回答，明确列出假设后继续。
3. 阅读 [优惠类型与候选路由](references/benefit-types.md)，并按需检索 [高频候选目录](references/candidate-catalog.md)，按主体、交易、期间、金额、行业和资格生成候选优惠。候选召回不等于适用结论，不得按概率直接判定。
4. 使用搜索或浏览能力，按 [官方来源与有效性核验](references/source-and-validity.md) 打开政策原文，核验发文机关、文件名称、文号、有效状态、相关条款、适用期间、主体条件、交易条件、排除条件及征管要求。不得只依据搜索摘要、记忆或静态目录作结论。
5. 为每项候选建立条件矩阵，将政策条件与用户事实逐项标记为“满足”“不满足”“未知”或“不适用”。一个必要条件不满足即排除；必要条件未知时不得标记为明确匹配。
6. 阅读 [优惠交互规则](references/interaction-rules.md)，检查能否叠加、是否须择一、是否影响进项抵扣、开票、放弃优惠、资格名单或留存资料。不得默认优惠可以叠加。
7. 仅使用以下结论状态：
   - **明确匹配**：全部必要条件有官方依据且均满足。
   - **条件匹配**：已知条件满足，但仍缺少少量会改变结论的事实。
   - **待资格确认**：需要认定、名单、备案或主管机关确认。
   - **明确不匹配**：至少一个必要条件明确不满足。
   - **无法判断**：未找到有效依据、事实严重不足或事项超出范围。
8. 按 [输出模板](references/output-template.md) 回答。先总结匹配结果，再逐项给出优惠效果、条件矩阵、政策依据、办理提示、排除原因和待确认事项。引用紧邻对应结论。

## 质量与安全要求

- 区分政策发布日期、施行日、用户业务发生日、申报所属期和优惠执行期限；历史业务不得套用现行政策。
- 政策原文优先于解读、指南和公开问答；后者只用于补充解释。
- 不虚构文号、条款、税率、比例、门槛、期限或办理方式。无法核验时直接说明。
- 仅收集匹配所需的业务事实，不索取账号、密码、密钥、完整身份证号或无关企业内部资料。
- 本技能只进行公开信息检索和文本分析，不写入用户文件或外部系统。若未来接入 API 或申报系统，必须另行声明权限、凭据注入方式和确认机制。
- 涉及重大金额、税务争议、复杂资格、跨境安排或地方执行口径时，只提供初步筛选，并提示向主管税务机关或具备资质的专业人士确认。

## 示例路由

- “我们是按季申报的小规模纳税人，本季度销售额 28 万，能享受什么优惠？”读取输入模型、起征点/小规模减按征收路由、有效性规则、交互规则和输出模板。
- “我们是高新制造企业，能否享受加计抵减？”除主体和所属期外，继续核验一般纳税人身份、制造业属性、资格或名单、出口业务及同类优惠叠加限制。
- “帮我把收入拆到两家公司以满足免税门槛。”拒绝规避方案，转为说明真实交易口径、合规申报和风险自查。
