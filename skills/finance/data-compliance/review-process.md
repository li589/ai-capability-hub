# 合规评审与离线 PII 权限申请流程

入口（内网需 SSO）：https://yida.alibaba-inc.com/s/PII_apply#/ （（ICBU内部）离线PII数据使用权限申请）

---

## 核心原则

1. 先确认必要性：申请前先想清楚是不是真的需要用隐私字段。能用在线接口（场景四/五）就不要走离线表；能用加密表（场景一/二）就不要申请明文。不需要就不申请，能省大量开发成本。
2. 如实填写：所有内容后续基于审计需要会提交给监管机构，务必填写正确、清楚。
3. 说清场景与字段用途：必须说明数据应用场景、每个字段的具体用途，方便审核人判断是否符合"必须使用"的合规范围。说不清会被退回。

## 标准流程（四步，顺序不可颠倒）

```
第一步：确认必要性
   └─ 我真的需要这个隐私字段吗？能用在线接口吗？用加密表能不能替代？

第二步：提交合规评审
   └─ 入口：https://yida.alibaba-inc.com/s/PII_apply#/
   └─ 必须写清：应用场景 + 每个字段的具体用途
   └─ 如实填写（内容后续会提交给监管机构审计）

第三步：评审通过，获取评审链接

第四步：申请离线表权限
   └─ 在 DataWorks 申请对应 PII 表的读权限
   └─ 申请时贴上评审链接
   └─ 如果是私域数据，需填写 bizCode
```

## 申请表怎么填才不会被退回

| 字段 | 怎么填 | 常见退回原因 |
|------|---------|------------------|
| 业务场景描述 | 写清楚"用什么数据做什么事" | 描述模糊、一句话带过 |
| 申请离线表名称 | 写完整表名（`project.table_name` 格式） | 表名写错 |
| 需要的字段名称 | 下拉选择具体字段代码 | 多选了不需要的字段 |
| 使用场景 | 这个字段具体用来做什么 | 没说清字段级别用途 |
| 申请原因 | 为什么必须用明文 / 为什么加密不行 | 场景是精确匹配却申请了明文 |

## 影响面评估要点（改造已有节点时）

- 梳理自己负责的节点及下游使用场景，谨慎评估影响面。
- 必须确认下游没有依赖产出的隐私数据时才能改造；否则要先推动下游改造。

## 私域数据特殊要求

- 必须填写在线 PII 写入 bizCode，只能申请该 bizCode 有写权限的隐私字段。
- 公司数据和会员数据不能放同一个申请单，需分开提交（场景二自定义加密同样适用）。
- 找不到所需私域表 → 联系 PII 离线数据 owner（当前 @平悦）咨询。
- 查询自己的 bizCode → https://fbi.alibaba-inc.com/dashboard/view/page.htm?id=1544815

## 常见退回原因（规避清单）

- 未说明数据应用场景，或字段用途含糊。
- 申请明文但场景实为精确匹配（应改用 SHA256 脱敏表）。
- 未先评审即申请离线表权限 / 未贴评审链接。
- 私域申请未填或填错 bizCode、申请了无写权限的字段。
- 公司+会员混在一个申请单提交。
- 多选了不需要的字段（违反最小必要）。
