Feature Explainer

How Rate Limiting Works in This API

Token-bucket algorithm with per-tenant quotas and graceful degradation.

TL;DR

Every API request passes through a token-bucket rate limiter keyed by tenant ID. Each tenant gets a configurable burst capacity and steady refill rate. When the bucket is empty, requests receive a 429 Too Many Requests with a Retry-After header. Premium tiers get higher limits. The limiter runs as middleware before any business logic executes.

How It Works
Request Path (4 Steps)
1
Request arrives at API Gateway
▶
The gateway extracts the X-Tenant-ID header (or derives it from the API key). This becomes the rate-limit key. If no tenant ID is found, the request is rejected with 401 Unauthorized before reaching the limiter.
2
Token bucket check (Redis)
▶
The middleware calls EVALSHA on a Lua script in Redis that atomically: (a) refills tokens based on elapsed time since last request, (b) checks if ≥1 token is available, (c) decrements the counter. The bucket parameters come from config: burst=100, refill_rate=10/s for standard tier.
3
Decision: allow or throttle
▶
If tokens are available, the request proceeds to the handler. Response headers include X-RateLimit-Remaining and X-RateLimit-Reset. If the bucket is empty, a 429 response is returned immediately with Retry-After: {seconds} computed from the refill rate.
4
Graceful degradation mode
▶
If Redis is unreachable, the limiter falls back to an in-memory counter with a 2× conservative limit. A circuit breaker monitors Redis health and auto-recovers. During degradation, the X-RateLimit-Source: local header is set so clients can detect the fallback.

// middleware/rate_limit.go

func RateLimitMiddleware(cfg *RateLimitConfig) gin.HandlerFunc {
    return func(c *gin.Context) {
        tenantID := c.GetHeader("X-Tenant-ID")
        if tenantID == "" {
            c.AbortWithStatusJSON(401, ErrNoTenant)
            return
        }

        bucket := cfg.GetBucket(tenantID)
        allowed, remaining, resetAt := bucket.Allow()

        c.Header("X-RateLimit-Remaining",
            strconv.Itoa(remaining))
        c.Header("X-RateLimit-Reset",
            strconv.FormatInt(resetAt.Unix(), 10))

        if !allowed {
            retryAfter := time.Until(resetAt).Seconds()
            c.Header("Retry-After",
                strconv.Itoa(int(retryAfter)))
            c.AbortWithStatusJSON(429, ErrRateLimited)
            return
        }
        c.Next()
    }
}

Gotchas
Common Pitfalls

⚠️ Clock skew between Redis nodes

Token refill uses Redis server time (redis.time()), not client time. If your Redis cluster has clock drift >100ms, buckets may refill unevenly. Use NTP sync on all nodes.

⚠️ Burst ≠ sustained throughput

A burst of 100 means 100 requests can fire instantly, but the sustained rate is only refill_rate (10/s). Don't confuse burst capacity with steady-state QPS.

⚠️ Retry-After is approximate

The Retry-After header rounds up to the nearest second. Clients should add 100-500ms jitter to avoid thundering herd on retry.

FAQ
Frequently Asked Questions
Can I get a higher rate limit for my tenant?
Yes. Contact the platform team via #platform-eng on Lark. Premium tier provides 5× the default limits. Enterprise customers can request custom quotas via the admin console.
What happens during Redis failover?
The circuit breaker detects Redis unavailability within 3 failed health checks (~1.5s). It switches to local in-memory counting with 50% of the configured limit (conservative). When Redis recovers, the circuit breaker auto-resets after 5 consecutive successful checks.
Are WebSocket connections rate-limited?
WebSocket upgrades are rate-limited (counts as 1 request). Once connected, individual messages are not token-bucketed — they use a separate message-rate limiter with a sliding window of 60 messages/minute.
How do I monitor my usage?
Check the X-RateLimit-Remaining response header on every request. For dashboards, query the rate_limit_consumption metric in Grafana filtered by tenant_id. Alerts fire when remaining drops below 10% of burst.
