Pull Request #1247

Refactor event emitter to support typed payloads

by sarah.chen 14 files changed feat/typed-events → main
TL;DR

Replace the old EventEmitter (untyped any payloads) with a generic TypedEmitter<TEventMap>. Every emit and listener now enforces the correct payload shape at compile-time. Existing runtime behavior is unchanged — this is purely a type-safety lift, plus minor refactor to split the monolithic file into focused modules.

Motivation

Why this change?

Our current event system passes any for all payloads. In the last sprint alone, three bugs traced back to mismatched event payloads — a renamed field here, a missing property there. Each took 30+ minutes to reproduce because errors surfaced at runtime deep in listener chains.

By introducing a typed event map, TypeScript catches these issues at compile-time. IDE autocomplete also works now, showing exactly which events are available and what each payload looks like.

Behavior Change

Before → After

Before
emitter.on('user:login', (data: any) => { // no type checking — hope for the best console.log(data.userName); // typo! // should be data.username });
After
emitter.on('user:login', (data) => { // data is UserLoginPayload console.log(data.username); // ✓ console.log(data.userName); // ^^^^^^^^ TS error });

Review Guide

Focus your review

  • emitter.ts — generic constraint design Is the TypedEmitter<T extends EventMap> constraint flexible enough? Particularly the emit() overloads for events with optional payloads.
  • event-map.ts — payload shape decisions Some payloads are thin wrappers ({ id: string }). Should we future-proof with richer types, or keep them minimal and extend later?
  • session-manager.ts — field rename The refreshToken → refresh_token rename aligns with the API but is technically a breaking change for any consumer reading this off the event payload.
  • Test coverage Skim the new tests for gaps. Particularly interested in edge cases around .once() + .off() race conditions.
