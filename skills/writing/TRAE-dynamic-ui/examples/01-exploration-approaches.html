Three Ways to Implement Rate Limiting in Go

Comparing token bucket, sliding window, and leaky bucket for API gateway throttling at 10K req/s.

Token Bucket
golang.org/x/time/rate
func NewTokenBucket(rps int) *rate.Limiter { // refills rps tokens per second // burst = 2× steady-state return rate.NewLimiter( rate.Limit(rps), rps*2, ) } func Allow(ctx context.Context, limiter *rate.Limiter) bool { return limiter.Allow() }
Advantages
  • Stdlib-adjacent; widely understood
  • Allows controlled bursts above steady rate
  • O(1) per request, no sliding state
Drawbacks
  • Single-node only without Redis adapter
  • Burst budget can mask sudden spikes
Sliding Window Log
Redis ZRANGEBYSCORE
func SlidingWindowAllow( rdb *redis.Client, key string, limit int, window time.Duration, ) bool { now := time.Now().UnixMilli() pipe := rdb.Pipeline() pipe.ZRemRangeByScore(ctx, key, "0", fmt.Sprint(now-window.Milliseconds())) pipe.ZAdd(ctx, key, &redis.Z{ Score: float64(now), Member: now, }) cnt := pipe.ZCard(ctx, key) pipe.Exec(ctx) return cnt.Val() <= int64(limit) }
Advantages
  • Distributed across nodes via Redis
  • Exact per-window accuracy, no boundary issues
Drawbacks
  • O(n) memory per key per window
  • Redis round-trip adds ~1ms P50 latency
  • Sorted set grows large under heavy traffic
Leaky Bucket (GCRA)
Generic Cell Rate Algorithm
type LeakyBucket struct { mu sync.Mutex tat time.Time // theoretical arrival rate time.Duration max time.Duration } func (b *LeakyBucket) Allow() bool { b.mu.Lock() defer b.mu.Unlock() now := time.Now() tat := b.tat if now.After(tat) { tat = now } tat = tat.Add(b.rate) if tat.Sub(now) > b.max { return false } b.tat = tat return true }
Advantages
  • Smoothest output; no bursts at all
  • Only 2 values stored (TAT + rate)
  • Naturally maps to Redis EVAL
Drawbacks
  • No burst tolerance can frustrate users
  • Harder to reason about than token bucket
★
Recommendation

Start with Token Bucket, graduate to Sliding Window

For a single-binary API gateway, token bucket using golang.org/x/time/rate ships fastest with zero infrastructure. When you scale past 3 nodes, introduce the sliding window behind a Redis cluster — the 1ms latency is acceptable and you gain exact distributed counts. Reserve leaky bucket for bandwidth-shaping at the transport layer.
