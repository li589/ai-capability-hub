# 纸质表单电子化系统生成器｜用户操作说明

## 一句话用法

**上传：1 份业务提示词 + 对应业务资料 → 直接说“开始生成” → 等待系统自动完成 → 下载最终 ZIP。**

## 一、你只需要准备两样东西

### 1. 业务提示词

可以直接在对话框输入，也可以上传 TXT / DOCX / PDF。

建议只写业务目标，不要写技术实现。

推荐模板：

> 请把这批业务资料做成一个中文业务管理系统。
> 使用人员：[例如：车间人员、主管、运营]。
> 主要业务：[例如：点工、能源日报、盘点]。
> 希望解决：[例如：减少手工录入、自动计算、方便查询统计]。
> 要求尽量保留原表单填写习惯。
> 能从资料确认的规则直接采用，无法确认且会影响业务结果的规则再向我确认。
> 最终完成测试，并输出可以在 Windows 本地使用的完整 ZIP。

### 2. 对应业务资料

直接上传现有资料即可：

- Excel / XLSX
- CSV
- Word / DOCX
- PDF
- JSON / TXT
- ZIP
- 已有 Python / Web 源码
- 历史业务数据
- 原始表单模板

多个文件可以一次全部上传。无需自己整理字段、改文件名或选择处理脚本。

## 二、开始生成

上传完成后只需要发送：

> **开始生成系统。**

或者：

> **按照我的提示词和业务资料直接生成最终版本，自动测试并打包 ZIP。**

执行者会自动完成：

`提示词读取 → 文件识别 → 深度业务模型（对象/字段/公式/关系）→ 资料完整度检查 → system-spec → 自动业务模块生成 → 数据检查 → 测试 → 验收 → ZIP打包`

## 三、什么时候需要你确认？

正常情况下不需要操作。

只有出现以下情况才会询问你：

- 同一个字段在不同资料中含义冲突；
- 工时、金额、数量等计算规则无法确认；
- 审批顺序无法从资料确定；
- 用户权限无法确定；
- 唯一编号或历史数据迁移规则无法确定；
- 继续生成会导致业务口径被 AI 猜测。

如果资料能够证明规则，系统直接使用资料，不重复询问。

## 四、最终你会得到什么？

通常包括：

1. 可运行的业务系统；
2. 数据库及历史数据导入结果（如果提供了历史数据）；
3. Excel 导入导出；
4. 查询、统计、权限等业务功能（以提示词和资料为准）；
5. 测试与验收结果；
6. 使用说明；
7. 完整源码；
8. 最终 ZIP 交付包。

## 五、用户不需要做什么？

**不需要：**

- 学 Python；
- 打开命令行；
- 输入脚本参数；
- 选择 Python / SQLite / Flask；
- 自己判断业务类型；
- 自己写数据库；
- 自己制作网页；
- 自己运行测试脚本；
- 自己压缩 ZIP。

这些都由技能执行流程自动处理。

## 六、推荐的最简单提示词

如果你不想写复杂提示词，直接使用：

> **请根据我上传的业务资料，保留原来的业务填写习惯，自动分析业务规则并生成可实际使用的中文 Windows 本地业务系统。能确认的规则直接实现，无法确认且影响业务结果的地方再问我。自动完成数据检查、测试和验收，最后给我完整 ZIP 和使用说明。**

## 七、重要说明

技能会区分“已生成”和“已实际验证”。例如 EXE、断网、局域网、免 Python 等能力，只有达到对应验收证据后才能称为“已验证”。

用户无需理解这些技术细节；系统会在最终交付说明中直接告诉用户哪些已经验证、哪些需要在目标电脑上做最后一次实测。


## 八、2.7.0 的关键增强

1. **业务关系识别更强**：除字段名外，会结合样本值重合与候选唯一性识别“员工工号 ↔ 员工编号”这类不同名称的主从关系。
2. **录入更像真正业务系统**：自动生成日期、日期时间、布尔、枚举、数字等控件；服务器端统一做严格类型校验，非法数字不再原样落库。
3. **导入更安全**：CSV/XLSX 先逐行校验并给出错误行；存在错误行默认阻止提交。
4. **测试成为强制闭环**：新增真实运行级 `test`。严格验收必须看到真实 E2E 证据，不再出现“TEST_REPORT 未执行但 strict 通过”。
5. **已有系统可安全升级**：新增 `upgrade` 差异分析。新增表/字段可非破坏式升级；删除字段、改类型默认阻断，并始终输出升级副本而非改原项目。

对于唯一键、审批链、金额/工时正式公式等高风险规则，技能仍不会因为自动化更强而自行猜测。
