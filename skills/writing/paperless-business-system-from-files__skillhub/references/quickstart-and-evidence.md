# 快速上手与能力证据

## 1. 三种最常见说法

### 示例 A：Excel 做本地系统

用户：
> 把 `点工记录.xlsx` 做成 Windows 本地中文系统，保留字段，支持录入、查询、统计、Excel 导入导出，最后给我 ZIP。

执行：`analyze → 完善 system-spec → scaffold → 业务实现 → validate → package`。

验收重点：字段来源、工时公式、唯一键、权限、导入防重、备份恢复。没有证据的工时规则必须列待确认。

### 示例 B：已有系统升级

用户：
> 在不删除原数据库和历史数据的情况下，把新报表加入现有系统。

执行：只读盘点源码/数据库/迁移 → 建立旧字段到新字段映射 → 备份 → 幂等迁移 → 前后数据核对 → 验收。

禁止：先删除数据库再重建；用新表覆盖旧历史；把字段冲突静默处理。

### 示例 C：完整局域网包

用户：
> 做成完整局域网部署包，包含服务端和 Windows 填写客户端，断网环境也能使用。

执行：`portable_full + lan` → 生成服务端/客户端 → 验证本地依赖 → 静态验收 → 运行验收 → 目标机断网验收。

只有最后一步通过，才能写“目标机断网可用”。只有包内带 EXE/便携运行时并在目标机验证后，才能写“免 Python”。

## 3. 输出报告最小格式

每个交付包应能回答：

- **输入**：处理了哪些文件，哪些文件有问题？
- **识别**：识别到什么业务，证据是什么？
- **生成**：生成了哪些模块？
- **验证**：哪些是静态通过，哪些是运行通过？
- **限制**：哪些仍需用户/目标机确认？
- **恢复**：如果失败，从哪一步继续？

## 4. 非技术用户与技术人员的边界

非技术用户只上传资料并描述目标；执行者运行命令。
技术人员可以使用 `run_skill.py`，无需记忆多个脚本的参数组合。

当前默认工程底座是 Python + Flask/Jinja2 + SQLite，第一目标为 Windows 10/11。
这不是对未来技术栈的禁止，而是当前技能可直接生成、验收和交付的边界。
如果用户要求 iOS 原生、Android 原生、纯前端、非 Python 后端等，应先进入“重新设计生成底座”路径，不得把当前脚手架的结果包装成已经支持。
