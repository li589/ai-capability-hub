# 点工 / 考勤业务 Profile（仅在证据支持时加载）

## 识别信号

典型字段/词：点工、考勤、员工、姓名、工号、岗位、工种、排班、班时、出勤、正工、加班、生产工时、非生产工时、请假、打卡、借调、审核。

## 通用对象

按附件动态识别：员工、组织/线别、排班、班时规则、考勤周期、日点工、工时明细、打卡、请假、借调、审核、月度汇总、导出模板。

工号必须按文本处理并保留前导零。同名员工存在时不能只按姓名自动合并。

## 安阳 26～25 日 / V1.5 参考模式

只有当用户提示词或附件明确支持时，才采用以下模式：

- 考勤月：上月 26 日至本月 25 日；
- `生产正工时 = max(0, 正工时 - 非生产正工时)`；
- `生产加班 = max(0, 加班 - 非生产加班)`；
- 正工、加班、生产正工、生产加班由后端自动计算并锁定；
- 非生产正工不清零总加班，非生产加班不清零总正工；
- 启机/品切只记录时，不参与其他工时加减；
- 两级审核如附件要求，应由不同账号完成，二审字段权限按真实规则限制。

这不是所有点工系统的全球默认规则。如果其他用户附件采用自然月、三班制、不同公式或不同审核链，必须按其文件生成，不得强制套用安阳规则。

## Excel 结构识别

对于“每天一个工作表”的点工表，不得假设人员明细从固定行开始/结束。应依据姓名、工号、表头、合计/签核文本和公式区域联合识别，排除合计、说明、签字和隐藏历史区域。

Excel 中的公式要转换为后端 Python 规则；不得执行宏、外部链接或 `eval()`。断链 `#REF!` 只能作为冲突证据，不能作为唯一业务事实。

## V1.5.11 级完整部署包装（仅影响交付，不影响业务规则）

用户要求“像安阳 V1.5.11 一样的局域网完整包”时，使用 `portable_full`。这是部署包装参考，不代表可以继承安阳的考勤周期、工时公式或审核规则。

点工场景的 portable_full 通常应包含：完整服务端、Windows 填写客户端、可配置服务器地址/连接测试、局域网地址与端口辅助、点工/申请单正式电子模板区域、版本更新记录和根目录一键启停。macOS 客户端仅在用户要求或现有源码已有时保留/生成。

升级现有点工系统时，必须优先保留 SQLite 历史数据、审核锁定状态、迁移版本、模板、客户端和启停链；不得只复制页面或重建空数据库。
