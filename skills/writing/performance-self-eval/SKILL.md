# 绩效自评生成

从绩效考核文档中提取 KPI/OKR 内容，按通用结构化框架生成绩效自评评语（≤4000字），支持迭代修改。适用于任何岗位（研发、产品、运营、销售、职能等）和任何考核体系（纯 KPI / 纯 OKR / KPI+OKR）。

## 触发场景

用户提到以下关键词时激活本技能：绩效自评、写自评、performance self-eval、半年度总结、季度总结、考核自评、年终总结、自我评价、绩效考核评语。

## 工作流

### 第 1 步：输入获取

用户通常以两种方式提供考核信息：

- **文档输入**：提供绩效考核 PDF 文件路径。也可能提供 Word (.docx) 或其他格式。
- **文本输入**：直接粘贴 KPI/OKR 内容或描述考核指标。

如果用户未提供考核信息，主动询问："请提供你的绩效考核文档（PDF/Word）或直接粘贴 KPI/OKR 内容，我来帮你生成自评。"

### 第 2 步：文档提取与内容解析

**文档提取优先级：**

1. PDF 文件：使用 `pdf` skill 读取。若 skill 不可用或提取失败，回退到命令行工具 `pdftotext -enc UTF-8`（Windows Git Bash 环境通常可用）。若仍失败（如中文字符丢失），引导用户粘贴文本内容或提供截图。
2. Word 文件：使用 `docx` skill 读取。
3. 文本输入：直接进入解析阶段。

**解析要点——识别考核体系模式：**

从提取的文本中识别以下信息：

- **考核体系模式**：纯 KPI / 纯 OKR / KPI+OKR 并存
- **岗位信息**：姓名、部门、岗位、考核周期
- **指标列表**：每项指标的名称、描述、权重（如有）
- **OKR 结构**（如适用）：Objective 及其 Key Results

将识别结果简要展示给用户确认，例如："识别到 3 项 KPI（业务支撑 40%、平台化建设 30%、稳定性保障 30%），考核周期为 2026 年上半年。是否正确？"

### 第 3 步：框架确认

向用户展示默认自评框架（见下方），并询问是否有调整需求。常见问题包括：

- KPI 与 OKR 内容重叠 → 建议合并到指标段落，避免重复
- 用户希望聚焦特定方向（如突出某项能力或短板）
- 用户希望调整篇幅比例（如压缩某段落、扩展某段落）
- 用户不需要某些段落（如不需要"协作与业务价值"）

**必须在用户确认框架后再进入生成阶段。** 如果用户说"直接生成"或"不用调整"，使用默认框架即可。

### 第 4 步：评语生成

按确认后的框架生成自评评语，要求：

- 总字数不超过 4000 字
- 以纯文本形式直接输出，不生成文件
- 语言风格：专业务实，第一人称，适合提交给上级或 HR
- 严格基于用户提供的考核指标内容展开，不凭空编造项目或数据
- 对于用户未明确提及的工作细节，使用概括性表述而非捏造具体数字

### 第 5 步：迭代修改

生成后主动询问："如果需要调整，可以告诉我具体方向，比如：合并/拆分某些段落、聚焦特定不足方向、调整语气或篇幅、增删特定内容。"

常见迭代模式：

- 合并重叠内容（如 OKR 和 KPI 讲的是同一件事）
- 调整"不足"部分的聚焦点（从泛泛而谈改为具体业务痛点）
- 删除多余段落（如去掉自我介绍）
- 调整某一段的详细程度

## 默认自评框架

适用于任何岗位类型的 6 段式结构：

### 一、岗位定位与工作主线（~5% 篇幅）

简述岗位角色、核心职责方向、本周期工作主线。让评审者快速建立上下文。

**注意：不写自我介绍（姓名、工号、入职时间等）。** 如果需要提及姓名，在开篇自然带出即可，例如"上半年围绕 XX 主线展开工作"。

### 二、考核指标逐项回顾（~50% 篇幅，核心段落）

这是自评的主体，需要与实际工作产出严格对应。

**展开结构（每项指标）：** 指标描述 → 完成状态 → 关键成果（项目/交付物）→ 量化数据或业务价值。

**模式适配：**

- 纯 KPI：按 KPI-1、KPI-2... 逐项展开。
- 纯 OKR：按 Objective 分组，每个 Objective 下列出 Key Results 进展。
- KPI+OKR 并存：检查两者是否存在内容重叠。若重叠，合并到指标段落，以指标为主线叙述，避免重复；若不重叠，分别展开。

### 三、专业沉淀与能力成长（~15% 篇幅）

从专业方法论、实践积累、问题解决等维度提炼深度与成长性。

**注意：使用通用表述，不限定"技术"或"研发"视角。** 例如：

- 研发岗：架构设计、工程实践、技术选型
- 产品岗：需求分析、用户洞察、产品方法论
- 运营岗：运营策略、数据分析、流程优化
- 销售岗：客户管理、市场判断、谈判技巧

根据用户的岗位类型自动适配措辞。

### 四、协作与业务价值（~10% 篇幅）

跨团队/跨部门协作、对业务的实际支撑效果、产研/产销协同亮点。

### 五、不足与改进方向（~10% 篇幅）

坦诚反思当前短板，给出可落地的改进计划。

**核心原则：聚焦真实业务痛点，而非泛泛而谈。** 好的"不足"描述应该让评审者感受到自我驱动力和对业务方向的清晰判断。将"不足"与"未来方向"自然衔接，体现改进的可操作性。

### 六、总结（~10% 篇幅）

概括性收尾，呼应开篇的工作主线，点明整体评价。

## 写作规范

1. **以事实说话**：每个论点都要有对应的项目、数据或成果支撑，避免"认真负责""积极主动"等空泛描述。
2. **合并重叠内容**：当 KPI 与 OKR 覆盖相同工作时，合并叙述，不要重复讲同一件事。
3. **不足要真实**：不写"有时过于追求完美"这类伪缺点。写真正影响业务的短板，并给出改进方向。
4. **不写自我介绍**：姓名、部门、入职时间等信息不需要单独段落，如需提及则在开篇自然带出。
5. **字数控制**：总字数不超过 4000 字。如果用户要求更短，按用户要求调整。
6. **语言风格**：专业务实，第一人称。避免过度夸大，也避免过度谦虚。亮点要突出，不足要坦诚。
7. **岗位适配**：根据用户实际岗位调整用词和视角，不要把研发岗的写法套用到其他岗位。

## PDF 提取回退策略

PDF 提取中文内容时可能遇到字符丢失问题（尤其是嵌入式 CJK 字体的 PDF）。按以下顺序尝试：

1. **首选**：调用 `pdf` skill 提取（内部使用 pdfplumber，中文支持最好）。
2. **回退 1**：`pdftotext -enc UTF-8 <file> -`（Git Bash 环境下通常可用，注意必须带 `-enc UTF-8` 参数，否则中文字符会丢失）。
3. **回退 2**：使用 `yescan-ocr-qoder` skill 对 PDF 进行 OCR 识别（适用于扫描件或字体嵌入异常的 PDF）。
4. **最终回退**：引导用户直接粘贴考核内容，或提供截图。

## 迭代修改指南

生成初稿后，用户常见的修改需求和对应处理方式：

| 用户反馈 | 处理方式 |
|---|---|
| "OKR 和 KPI 讲的是一件事" | 合并到 KPI 段落，删除 OKR 独立段落 |
| "不足部分太泛了" | 追问用户具体的业务痛点，据此重写 |
| "不需要自我介绍" | 删除自我介绍段落，开篇直接进入岗位定位 |
| "某一段太长/太短" | 按用户要求调整篇幅比例 |
| "加一些 XX 方面的内容" | 在对应段落中补充，保持总字数不超标 |
| "语气太正式/太随意" | 调整整体语言风格 |
| "帮我精简一下" | 在保留核心事实的前提下压缩篇幅 |

## 输出格式要求

- 直接以文本形式输出评语，不生成文件（除非用户明确要求保存为文件）。
- 使用 Markdown 格式组织段落结构（标题 + 正文），方便用户复制。
- 如果用户要求保存为文件，使用 `docx` skill 生成 Word 文档。
