# 公益项目申报材料撰写

## 定位

申报材料被退回，很少是因为表格没填满，而是因为内容不合格：概要写成流水账、背景没数据、公益性说不清、目标写成活动清单而不是可验收的结果、预算和方案对不上。

这个 skill 站在**申请方**这边，做两件事：**把口语化的项目描述写成合格的申报语言**，以及**对照资助方要求诊断已写好的稿件**。

不同资助方对申请材料的叫法不一样（申请书、立项书、申报书、服务方案、Concept Note），内核是同一件事。名词对不上时查 [glossary.md](references/glossary.md)。

| 用户 | 场景 | 主要模式 |
|------|------|---------|
| 公益机构 / 申请方 | 向政府、基金会、企业申请资助 | 模式 A 从零撰写 + 提交前自检 |
| 资助方项目管理者 | 初审、辅导合作方改稿 | 模式 B 对标诊断 |

## 触发方式

```
帮我写项目申请书 / 立项书 / 申报材料 / 资助申请
帮我写项目概要 / 背景 / 公益属性 / 项目目标
我想申请 XX 的资助，帮我写一份（附申请指南）
这份申请书写得怎么样（附文件）
帮我按 XX 基金会的要求诊断这份申请书（附文件）
用这份方案材料写一份申请书（附方案/预算/PPT）
```

## 先选路径

**不要求用户先准备好任何东西。** 按手上有什么选路径：

| 你现在的状态 | 走哪条 |
|------------|-------|
| 只有一个想法，没材料、也不知道投给谁 | **快速通道**（下一节，3 个问题就能开始） |
| 有项目材料，知道投给谁 | **模式 A** 从零撰写 |
| 已经写了初稿，想知道行不行 | **模式 B** 对标诊断 |
| 金额小（如 10 万以内），或对方只要一张在线表单 / 2–5 页申请表 | **轻量路径**（见下文） |

## 快速通道

用户只说「我想申请个资助，帮我写」时，**不要先要申请指南**，先问三个问题：

```
1. 你想做什么事，帮助哪些人？（一句话就行）
2. 大概需要多少钱，做多长时间？
3. 打算投给谁？不确定的话，是政府部门、基金会、还是企业？
```

三个问题答完就能起草。**这三问覆盖了 Step 1「7 项必须信息」里的核心 4 项**（做什么帮谁 = 第 1、2 项，多少钱多久 = 第 4、5 项）；剩下 3 项（为什么做、谁来执行、预期成果）在起草过程中边写边补，不必一次问全。第 3 问只要知道**类型**，就能用 [funder-types.md](references/funder-types.md) 里对应类型的典型要求起草，不必等到拿到申请指南。连类型都不确定的，用通用基线起草，同时告诉用户这份稿子可以先用来内部对齐和对外沟通，正式提交前再按对方要求调整。

看到「立项书 / Concept Note / Logframe / 管理费」这类不认识的词，先查 [glossary.md](references/glossary.md)。

**核心态度**：先出一份能看的东西，再逐步补精确。卡在信息收集阶段是这类工作最大的浪费。

## 三份档案

**通用层（skill 内置，对所有资助方一致）**
项目设计逻辑（为什么做、帮谁、在哪、多久、怎么做）、写作质量标准、目标的可量化与可验收规则、预算编制原则、公益合规底线、审查视角。

**资助方档案（钱从哪来，一个资助方一份）**
文书名称与章节结构、目标范式、执行周期上限、管理费上限、分类选项、附件清单、禁忌表述、评审关注点与高频退回原因、提交渠道。

**我方机构档案（你是谁，一个机构一份，长期复用）**
机构基本信息、资质与合规状态、财务基础数据、团队、往期项目库、可复用的机构介绍段落、常备附件清单。见 [applicant-profile-template.md](references/applicant-profile-template.md)。

第三份是省时间的关键。没有它，每写一份材料都要重新问一遍机构介绍、团队、审计报告。**发现用户还没有这份档案时，主动建议建一份**，并把这次收集到的机构信息整理成初版交给用户保存。

### 硬规则：不许猜阈值

涉及**具体数字门槛和分类选项**的内容（周期上限、管理费比例、金额阈值、分类该选哪个、附件要哪几份），只能来自资助方档案或用户提供的官方文件。**档案里没有、用户也没说的，标注【需向资助方确认】，禁止按别家的经验填。**

[funder-types.md](references/funder-types.md) 里的数字是**行业常见做法，不是任何一家的规定**，引用时必须标注为按类型推断、待核对。填错阈值比留空的代价大得多。

## 两种工作模式

| 模式 | 场景 | 流程 |
|------|------|------|
| **A 从零撰写** | 只有口头描述、零散材料或一份方案 | Step 0 → 1 → 2 → 3 → 4 → 5 |
| **B 对标诊断** | 已有初稿，要查缺补漏和改写 | Step 0 → B1 → B2 → B3 → B4 → B5 |

---

## Step 0：搞清楚要投给谁

章节结构和硬性门槛全由资助方决定，所以先定这个。**但不要因为信息不全就停下来。** 四种情况都能往下走：

**情况一：已有该资助方的档案** — 读 `references/funder-<简称>.md` 或用户自己维护的档案，进入 Step 1 / B1。

**情况二：有官方文件**（申请指南、申报通知、空白模板、往年获资助项目公示）
按 [funder-profile-template.md](references/funder-profile-template.md) 的九项结构抽取，生成档案草稿。每项标来源等级：

- `【指南明确】` 官方文件里有原话
- `【推断】` 从模板结构或往年案例反推
- `【未知】` 文件里查不到

把 `【推断】` 和 `【未知】` 集中列出来请用户确认，确认后落成档案文件再继续。

**情况三：只知道资助方类型**（最常见）
用 [funder-types.md](references/funder-types.md) 里对应类型的典型要求起草。**直接开始写，不要求用户先去找指南。** 交付时声明：

```
ℹ️ 本稿按「<类型>」的常见要求起草，尚未核对 <资助方> 的官方申请指南。
提交前请核对这四项（填错的代价比留空大）：
- 管理费上限与分母口径
- 执行周期上限
- 分类选项的原文表述
- 附件清单与触发条件
```

**情况四：完全不知道投给谁** — 用通用基线起草，见 [funder-profile-template.md](references/funder-profile-template.md) 的「通用基线」一节。这种稿子的用途是内部对齐和对外初步沟通，声明清楚即可，不影响先动手。

## 轻量路径：小额与表单式申请

金额小（如 10 万以内）、或对方只要在线表单 / 2–5 页申请表时，**不要套完整结构**。社区基金会、街道微创投、小额资助的评委多数是社区代表，长篇专业稿反而不利。

轻量路径只做四步：

| 步 | 做什么 |
|----|-------|
| 1 | 问清对方的**字段清单和字数限制**（有表单就让用户把字段名贴出来） |
| 2 | 按字段逐条产出，**一次到位符合字数上限**，不要先写超长再砍 |
| 3 | 只跑三条检查：目标可量化、金额一致、预算与活动对得上 |
| 4 | 交付时附一句提醒：证书有效期、票据留存方式 |

**必须保住的**：目标可量化、预算有测算依据、受益人数前后一致。这三条无论篇幅多短都不能省。

**可以省的**：变革理论论证、多层成效指标、详细风险矩阵、可持续性专章。

语言要能让非专业评委看懂，避免行业术语。有路演环节的，额外给一段 3 分钟口头版本。

**给用户一份可对照的成品**：不确定轻量路径写出来长什么样时，可参照 [examples/lightweight-proposal-sample.md](examples/lightweight-proposal-sample.md)——一份 5 万元社区助餐项目的完整两页纸小样，从三问输入到成稿全展示，直接套结构即可。

## 模式 A：从零撰写

### Step 1：收集项目信息

**顺序很重要，能省大量重复劳动**：

1. **先查我方机构档案** — 有的话，机构介绍、团队、资质、财务、往期成果直接调用，一个都不用问
2. **再解析用户提供的材料** — 方案 PPT、预算草稿、往年结项报告都行
3. **最后只问真正缺的**

没有材料就分 3 轮问，每轮 1–2 题，不要一次抛十几个问题。

**必须信息（7 项，缺了写不出来）**

| # | 信息 | 用在哪 |
|---|------|--------|
| 1 | 做什么（一句话核心活动） | 概要、What |
| 2 | 帮助谁、多少人 | 概要、Who |
| 3 | 为什么要做 | Why |
| 4 | 预算多少 | 概要、预算 |
| 5 | 做多长时间 | When |
| 6 | 谁来执行 | 概要、团队 |
| 7 | 预期成果（2–3 个） | 目标章节 |

**有更好（缺了能写但打折扣）**：问题严重性数据、公益性怎么体现、与同类项目的差异、时间安排、已有成果、可能的困难、具体实施地点、项目结束后成果怎么持续。

7 项齐了就进 Step 2。缺项追问一次，仍不清楚就标 `【待补充】` 继续写，**不要卡住流程**。「有更好」的项不主动追问，靠 Step 3 的预检报告自然引导补充。

### Step 2：生成初稿

按资助方档案的章节顺序生成。模块规则见 [writing-rules.md](references/writing-rules.md)，目标章节见 [goal-frameworks.md](references/goal-frameworks.md)，预算见 [budget-and-compliance.md](references/budget-and-compliance.md)。

速查：

| 模块 | 一句话要求 |
|------|-----------|
| 项目概要 | 6 要素公式：预算 + 谁执行 + 做什么 + 受益群体规模 + 目的 + 进展/影响 |
| 为什么做 | 三层：问题（**必须有数据**）→ 为什么现在做 → 本项目填补什么缺口 |
| 帮助谁 | 具体群体 + 规模数字 + **为什么选这个群体** |
| 在哪做 | 具体到区域 + **为什么选这里** |
| 做多久 | 精确起止 + 分阶段 + 拨付节奏；超过周期上限须附合理性说明 |
| 怎么做 | 按板块讲核心活动，方向与目标章节一致、粒度更粗 |
| 公益属性与社会价值 | 公益属性（资金用途/服务性质/面向对象/公平性）+ 社会价值分三层（个体→群体→社会） |
| 可持续性 | 成果持续 / 模式可复制 / 资金可持续，至少覆盖 2 个 |
| 项目目标 | 按档案指定的范式写；无论哪种范式都要有**产出层**，尽量有**成效层** |
| 实施方案与预算 | 方案 → 产出 → 验收标准 → 金额，四列必须对得上 |
| 团队与风险 | 每人岗位职责分工；风险写「风险描述 + 应对措施」 |

写作禁忌表统一在 [writing-rules.md](references/writing-rules.md) 的「通用写作禁忌」一节，起草时对照一遍。三条最致命的：**不可量化的空话**（提升影响力、推动发展）、**绝对化承诺**（免费、无偿、不收取任何费用）、**把活动当目标**（开展 20 场活动）。

### Step 3：合规预检

按 [review-checklists.md](references/review-checklists.md) 跑三组检查：模块专项、目标质量评分、跨模块一致性。

跨模块一致性最容易出问题，必查这 6 条：金额一致、受益人数一致、问题对应（背景的问题 = 公益属性要解决的问题 = 目标要解决的问题）、时间一致、区域一致、概要承诺的产出在目标里都有对应。

输出格式：

```
📋 合规预检报告

【项目概要】 ✅
【为什么做】 ⚠️ 缺数据支撑
【项目目标】 ⚠️ 15/20 分，KR2 不可验收
...
【跨模块一致性】 ⚠️
  ✅ 金额一致：概要 200 万 = 预算合计 200 万
  ⚠️ 人数不一致：概要写 3000 人，目标章节未出现受益人数
【需向资助方确认】
  · 管理费上限（按类型推断为 10%，未核对官方文件）
```

### Step 4：审查员模式

切换成**持怀疑态度的评审专家**重看一遍，专找预检规则查不出来的问题：

1. 模糊表述、有断言但没证据的地方
2. 模块之间的矛盾
3. 夸大的措辞
4. 目标是否真能验收 —— 验收人拿着这条能判断「做到了还是没做到」吗
5. 周期合理性 —— 超期理由站得住吗
6. 预算与叙述是否匹配 —— 方案里没提的活动，预算里却有钱

能直接改的改掉并标注，需要用户判断的列进待确认清单。

### Step 5：交付

一次输出四份：完整申报材料正文、合规预检报告、审查员意见、待确认清单。

**正文里不出现检查过程**（评分、检查项、规则编号只放在预检报告里）。

交付后按下面的「输出与落地」处理格式问题。

## 模式 B：对标诊断

用户已有初稿，先查「有没有写」，再查「写得对不对」。

### Step B1：结构映射

把稿件内容映射到资助方档案的章节结构，每章标 `✅ 已有 / ⚠️ 部分有 / ❌ 缺失`。

按**语义**识别，不要求用词一致（「项目背景」就是「为什么做」，「实施区域」就是「在哪做」）；多个模块混写的标「混合」并拆开；稿件里有但档案不要求的多余章节也标出来。

### Step B2：对标差异报告

逐项对照档案要求，每条差异写四段：

```
【帮助谁 — 整章缺失】❌
  资助方要求：独立章节写明受益人是谁、多少人、为什么选这个群体
  稿件现状：受益人信息散落在概要和方案里，没有独立论述
  影响：评审人无法快速判断服务对象和选择依据
  建议：提取现有内容扩写为独立章节，补充选择原因
```

总览用达标率表格：模块 / 达标项数 / 状态 / 主要差异。

**用类型档案诊断时**，差异要区分「肯定不合格」（如目标不可量化，任何资助方都不接受）和「按类型推断可能不符」（如周期超 1 年，需核对该方是否允许）。不要把推断说成要求。

### Step B3：内容质量诊断

对已写的部分跑 Step 3 的全套规则。重点找**写了但写得不好**的：虚话、绝对化表述、活动型目标、主体混同、无验收标准。

### Step B4：审查员模式

同 Step 4。

### Step B5：输出优化版

改写四原则：

- 写得好的 → **保留原文不动**
- 缺失的章节 → 按模式 A 规则补写，需要用户信息的标 `【待补充】`
- 写得不好的 → 给「原文 → 建议 → 理由」三段对比，用户确认后再替换
- 结构不对的 → 按档案结构重排，**内容不丢，只调位置**

## 输出与落地

写完的稿子要能真正交出去。默认输出 Markdown，再按提交方式转换。

| 提交方式 | 怎么处理 |
|---------|---------|
| **对方给了 Word / Excel 空白模板** | **不要自由输出。** 请用户把模板的字段名和字数限制贴出来，按字段逐条产出，用户复制填格 |
| **要交 Word 文档** | 装了 pandoc 的用 `pandoc 稿件.md -o 稿件.docx`；没装就直接复制 Markdown 粘进 Word，标题和表格多数能保留，再手工调格式 |
| **在线文档**（飞书、腾讯文档、Google Docs 等） | 多数支持粘贴 Markdown 自动转换；表格粘贴后常需重排列宽 |
| **在线表单 / 网页文本框** | 去掉所有 Markdown 标记（`#`、`**`、`|`），改成纯文本；表格改成分行列举；**先问清每个字段的字数上限** |
| **要交 PDF** | 先转 Word 调好格式再导出，不要直接从 Markdown 转，分页会乱 |

**字数限制优先于表达完整性。** 已知字段上限时，第一版就写到上限内，不要先出超长版本再让用户删——删的过程最容易把关键数字删掉。

**表格是硬要求时不要改成段落。** 实施方案与预算的四列对应表、绩效指标表，改成叙述后评审无法逐项核对，会被要求重新提交。

## 写完之后：存下来复用

这一步在**用户自己的工作目录**做，不是写回 skill 目录（装好的 skill 通常只读，写回会失败）。

| 内容 | 存到哪 | 下次省什么 |
|------|-------|-----------|
| 这次整理出的机构信息 | `机构档案/我方机构档案.md` | 机构介绍、团队、资质不用再问 |
| 这次摸清的资助方要求 | `资助方档案/funder-<简称>.md` | 同一家再投直接复用 |
| 写得好的段落、通过评审的目标写法 | `机构档案/可复用段落.md` | 下次直接改数字 |
| 项目结项后的成果数据 | 我方机构档案的「往期项目库」 | 成为下次的执行能力证明 |

**主动做这件事**：交付时把整理好的机构档案初版和资助方档案初版一并输出，告诉用户存到哪、下次怎么用。往期项目库攒到 5 个以上项目后，写申报材料的速度会有明显变化。

## 硬性规则

### 不许编造

| 情况 | 处理 |
|------|------|
| 用户提供了数据 | 直接用，标注来源 |
| 找到了公开数据 | 可用，标注来源并提醒用户核实 |
| 没有数据也找不到 | 标 `【待补充】`，**严禁编造** |
| 用户口述但没来源 | 可用，标 `【数据来源待确认】` |

编造受益人数、覆盖率、行业调研数字，在申报场景里是实质性风险，不是文笔问题。**论断也算**：「研究证实」「已被验证有效」这类表述写不出具体出处的，降级或删掉。

### 数据脱敏

用户上传的材料含以下内容时提醒脱敏：受助人姓名与身份证号、联系方式、银行账户与财务凭证、机构内部薪酬与人事信息、未公开的合同条款。涉及儿童、患者、受灾群体的个人信息尤其要提醒。

### 人工确认不可跳过

AI 写和查，用户确认和决策。**交付稿必须由用户通读确认后才能提交**，不能由 AI 直接定稿。

### 主体表述

资助方是企业背景基金会时，基金会与其关联企业通常是**独立主体，须分开表述**，且申报材料应从公益目的论证，不能论证项目给关联企业带来的商业收益。

企业 CSR 与直接捐赠是例外：可以单列「合作价值」一节谈品牌契合与员工参与，但**项目目标章节仍须是纯公益指标**。

## 人机分工

| 步骤 | AI | 用户 |
|------|-----|------|
| Step 0 档案 | 抽取生成草稿，或按类型起草并声明 | 确认推断项与未知项 |
| Step 1 收集 | 调用机构档案、解析材料 | 提供信息、确认提取结果 |
| Step 2 生成 | 按规则起草 | 审核初稿、补细节 |
| Step 3 预检 | 跑规则与一致性检查 | 决定改不改 |
| Step 4 审查 | 评审专家视角挑问题 | 决定采纳与否 |
| Step 5 交付 | 输出四件套 + 落地格式建议 | **必须通读全文确认** |
| 复用沉淀 | 输出档案初版 | 存到自己的工作目录 |

## 提交前自检

- [ ] 资助方要求已确认，或已声明按类型 / 通用基线起草并列出待核对项
- [ ] 7 项必须信息齐全，缺的都标了 `【待补充】`
- [ ] 背景至少 1 处数据，且标了来源
- [ ] 每个目标都有数字、有时间、有可留存的验收证据
- [ ] 目标里有产出层，尽量有成效层
- [ ] 金额一致：概要 = 实施方案合计 = 预算表合计
- [ ] 受益人数在概要、受益人章节、目标章节里一致
- [ ] 预算每项对应到具体活动，无禁止科目
- [ ] 无绝对化表述、无商业回报论证、无不可验收的主观描述
- [ ] 涉及具体阈值和分类的地方，来源是档案或官方文件，不是猜的
- [ ] 附件清单齐全，**证书有效期已核对**
- [ ] 输出格式匹配提交方式，字段字数在限制内
- [ ] 已提醒用户脱敏
- [ ] 预检报告、审查意见、待确认清单都已附上
