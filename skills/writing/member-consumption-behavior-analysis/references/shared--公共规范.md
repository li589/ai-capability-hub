# 公共规范

## 当前会话执行

- 默认由当前助手在当前会话内完成全部业务查询、分析和报告生成。
- 除非用户明确要求多个助手协作，否则禁止创建子代理、子会话或把任务交给其他代理后等待。
- “并发”只表示固定脚本或数据查询可同时执行；“改读其他业务 Skill”只表示当前助手切换到对应规则后继续处理。
- 必须等待固定查询或报告脚本完成，并在本次请求内返回业务结果或明确失败说明；不得只返回转交或等待状态。

## 门店解析

按名称查询：`sl store find --type crm --name "<门店关键词>" --format json`
按关键词/ID 查询：`sl store find --type crm --keyword "<门店关键词或门店ID>" --format json`

| 返回情况 | 处理 |
|---------|------|
| `[]` 或长度 0 | 停止并提示未找到门店，让用户补充 |
| 1 条 | 使用 `omShopCode`（放入 `shopIds`/`shopFilterTypeValue`/`omShopCodes`） |
| 多条 | 展示候选让用户确认，不静默选择 |
| token 缺门店清单 | 先 `sl token refresh dc`，再重试 |

用户未指定门店时，不传门店参数，按当前 token 默认权限执行。

## 门店缓存与口头切换

- `cache/cysms-stores.json` 只作为门店候选清单和名称解析缓存；不得把它当成用户已选择门店。
- 不要主动读取或依赖 `cache/cysms-selected-stores.json`；该文件可能不存在，且不属于 Skill 运行契约。尤其不要从 Skill 目录下的 `cache/` 读取它；缺失不是错误。门店上下文只能来自用户本轮明示、命令显式参数或当前脚本自己的 scoped cache。
- 用户本轮明确指定门店或说「换成/切到/看某店」时，必须在本轮所有相关命令中显式传入门店参数；餐饮用 `--store-name`/`--store-id`，CRM 用 `omShopCodes`/`shopIds`/`shopFilterTypeValue`，供应链用 `--organName` 等对应参数。
- 用户未指定门店且命令不支持集团/默认权限口径时，先请用户确认门店；不要因为 selected cache 存在就直接查询。

## 时间口径

默认最近 7 个完整自然日。

| 内容 | 规则 |
|------|------|
| 统计范围 | 从开始日期起，统计至结束日期当天结束 |
| 统计粒度 | 默认按天汇总；用户按月查看时按月汇总 |
| 周期对比 | 自动选取相同天数的上一周期进行对比，无需用户额外说明 |
| 对外展示 | 必须展示完整起止时间，例如“7 月 9 日 00:00:00 至 7 月 15 日 23:59:59” |

例如，用户选择本月 1 日至 7 日时，统计范围包含 1 日和 7 日全天；上一周期则取此前连续 7 天。

## 安全与输出

- 不输出 token/session/cookie/密钥/内部 ID（taskId、exeTaskId、shopId）。
- 会员姓名、手机号、编号默认脱敏。
- 命令失败 ≠ 指标为 0；空数组 ≠ 接口异常。
- 单模块失败继续其它模块，标注失败模块和受影响结论。
- 金额写"元"，人数写"人"，比例写"%"，金额 2 位小数，比例 1-2 位。
- 先给一句话结论，再展开数据。
- `claw-file` 路径用 workspace 相对路径，返回前读 `当前 WorkBuddy 文件交付约定`。

## JSON 二次解析

- 优先读取脚本输出中的 `summaryMetrics`、`summary`、`facts` 等业务化汇总字段；避免临场解析原始 DataCube 行列结构。
- 需要二次解析 JSON 文件时，优先使用 Node.js `JSON.parse`，减少 shell/jq 引号问题。
- 如必须使用 `jq`，所有中文 key 必须使用 bracket 方式：`.queries["会员消费大盘"]`；输出对象的中文字段名也必须加双引号：`{"会员消费用户数": ...}`。禁止写 `.queries.会员消费大盘` 或 `{会员消费用户数: ...}`。
