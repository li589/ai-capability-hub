# Token-Efficient Dev 效果案例

> 以下 3 个案例可直接用于 SkillHub 发布页「效果案例」补充，覆盖核心能力、典型行业场景和边界说明。

---

## 案例 1：大代码库功能开发 —— 避免上下文膨胀

**场景标题**：在大型项目中新增功能时自动精简上下文

**场景描述**：
某电商后台管理系统有 200+ 个文件，用户需要为订单模块新增一个退款审核状态机。普通 AI 编码助手会加载大量无关文件、输出完整文件副本，导致单次对话 Token 迅速膨胀。本 Skill 会自动限定读取范围，只加载订单状态机相关文件，并以 Diff 形式输出最小改动。

**示例问题**：
> 给订单模块加一个退款审核状态机，状态包括：待审核、审核通过、审核拒绝、已退款。状态流转需要校验权限。

**触发条件**：
用户提出涉及多文件、大项目的代码开发需求时自动触发。

**效果对比**：
- 未使用：平均加载 8–12 个文件，单次输出 4000+ Token
- 使用本 Skill：仅加载 2–3 个相关文件，单次输出 1200 Token 左右

## 案例 2：多轮调试 —— 终止重复输出

**场景标题**：长链路 bug 排查时减少重复代码块

**场景描述**：
用户在调试一个跨服务调用超时问题，AI 在多次回复中不断重复已经贴过的配置代码和日志片段，导致有效诊断信息被稀释，Token 快速耗尽。本 Skill 会清理已解决子线程，只保留关键报错、根因和修复方案，并直接接续输出，不再复述已确认内容。

**示例问题**：
> 这个微服务接口偶发 504，帮我排查一下。我已经把 nginx 配置和接口代码发过了。

**触发条件**：
用户在多轮对话中持续调试、排查、修复同一个问题时自动触发。

**效果对比**：
- 未使用：每轮回复平均重复 30% 以上历史内容
- 使用本 Skill：每轮仅追加新的诊断结论和修复动作

## 案例 3：代码审查 —— 精简反馈，聚焦问题

**场景标题**：批量代码审查时只看关键缺陷

**场景描述**：
研发团队在合并分支前让 AI 审查 Pull Request。普通模式下 AI 会对每一行都给出格式化建议和风格点评，产生大量噪音。本 Skill 会让 AI 只输出真正影响逻辑、性能或安全的问题，并给出明确修复方案，帮助团队快速决策。

**示例问题**：
> 帮我审查这个 PR，重点看是否有逻辑缺陷、性能问题和安全风险。

**触发条件**：
用户要求审查代码、PR、diff 或进行代码质量检查时自动触发。

**效果对比**：
- 未使用：输出大量风格建议和冗余解释
- 使用本 Skill：仅列出高优先级问题 + 根因 + 修复建议

## 边界说明案例（可选补充）

**场景标题**：不适合大量教学讲解类任务

**场景描述**：
当用户要求「详细讲解 React Hooks 原理」或「写一份完整的技术文档」时，本 Skill 不会强行压缩教学内容的深度和示例。此时系统应自动降级为普通模式，优先保证学习体验。

**示例问题**：
> 给我详细讲解一下 useEffect 的依赖数组机制，要有例子。

**触发条件**：
任务明确为教学讲解、文档撰写或非代码创作时，不强制启用 Token 节流。
