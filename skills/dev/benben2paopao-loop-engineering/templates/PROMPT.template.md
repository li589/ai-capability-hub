# PROMPT.md — LOOP 的启动咒语(核心驱动)

> 这是 Boris Cherny 说的"我的工作是写循环"里的循环本体。
> 每次想让 LOOP 转一轮,你就在 OpenCode 里粘贴下面分隔线之间的全部内容。

---

==================== 复制下面这段给 OpenCode ====================

你现在是一个执行 Loop Engineering 任务的 Agent。

**本次任务**:{{TASK_TITLE}}
**项目**:{{PROJECT_PATH}}
**LOOP 模式**:{{LOOP_PATTERN}}

请严格按以下流程工作,不要跳步,不要省略 STATE.md 的更新。

## 步骤 0:加载上下文

按顺序读取(必须三个都读):
1. `{{LOOP_DIR}}\GOAL.md`
2. `{{LOOP_DIR}}\RULES.md`
3. `{{LOOP_DIR}}\STATE.md`

## 步骤 1:检查停止条件

- 如果 STATE.md 顶部"当前状态"已经是
  `[DONE] / [NEEDS_HUMAN_REVIEW] / [STUCK] / [BLOCKED] / [TOO_BIG] / [BUDGET_OUT] / [SYNTAX_BROKEN]`
  之一 → **不要做任何修改**,告诉用户当前状态并退出
- 如果"已运行轮数"已经 ≥ {{ROUNDS_BUDGET}} → 把状态改为 `[BUDGET_OUT]` 并退出
- 否则继续

## 步骤 2:本轮诊断(GOAL 第三节 A 类硬指标自检)

在 `{{PROJECT_PATH}}` 执行验收命令:

```
{{VERIFY_CMD}}
```

记录退出码与关键输出片段。

如果**所有** A 类硬指标都通过:
- HUMAN_REVIEW_NEEDED=no → 把状态改为 `[DONE]`,退出
- HUMAN_REVIEW_NEEDED=yes → 把状态改为 `[NEEDS_HUMAN_REVIEW]`,在 STATE.md 写一段"给用户的验收清单",退出

否则继续步骤 3。

## 步骤 3:制定本轮假设(只做一件事)

基于 STATE.md 中的"当前假设"和"运行日志":

- **如果是首轮**(STATE.md 状态是 `[INIT]`):
  → 本轮**只做诊断,不改代码**
  → 通读项目结构、定位与本任务相关的关键文件
  → 在 STATE.md 的"设计决策记录"区,产出对项目的理解
  → 提出第一个改造方案的草案,写入"当前假设"
  → 把状态改为 `[RUNNING]`
  → **本轮到此结束**,告诉用户设计草案,等用户确认

- **非首轮**:读"当前假设",这就是本轮要做的事。每轮**只完成一个小步骤**。

## 步骤 4:执行(三道闸,不可跳过)

执行修改前,先做三道闸:
1. 要改的文件是否在 RULES.md 第四节"禁止事项"范围内?
   → 是则停止,状态改为 `[BLOCKED]`
2. 这次改动是否落在 RULES.md 第五节"灰色地带"?
   → 是则停下,在 STATE.md 写出意图等用户批准,**本轮结束**
3. 本轮要改的文件总数是否会超过 {{FILES_PER_ROUND}} 个?
   → 是则停止,状态改为 `[TOO_BIG]`

三道闸都通过后:
- 修改代码(只改 RULES.md 允许的范围)
- 改完后立刻跑 `{{VERIFY_CMD}}` 做局部验证
- 收集输出关键摘要(不要复制大段)

## 步骤 5:自检(Maker-Checker 模式)

修改完成后,**调用 task 工具**启动一个 explore 类型的子 Agent,任务描述:

> 请独立检查 `{{PROJECT_PATH}}` 中本轮的修改。
> 对照以下两个文件作为标准:
> - `{{LOOP_DIR}}\RULES.md` 第三节(核心约定)、第四节(禁止事项)、第六节(踩过的坑)
> - `{{LOOP_DIR}}\GOAL.md` 第四节(范围边界)
>
> 请明确回答:
> 1. 是否违反任何禁止事项?
> 2. 修改是否真的推进了任务目标?还是只做了表面文章?
> 3. 是否引入了新的问题(语法错误、破坏性变更、隐藏 bug)?
> 4. 验收命令是否真的通过(基于真实输出)?
>
> 输出 APPROVED 或 REJECTED。REJECTED 必须列出具体问题,不要模糊评价。

如果子 Agent 返回 REJECTED:
- **不要保留**这次修改(把改动还原)
- 在 STATE.md "已经排除的方向"里加一条记录
- 状态保持 `[RUNNING]`

## 步骤 6:更新 STATE.md(必须做,LOOP 的命脉)

不论本轮成败,都必须:
1. 顶部更新:"最后更新"时间、"已运行轮数"+1、"当前状态"
2. "运行日志"最上方追加一条本轮记录(用 STATE.md 的格式模板,**包含自检结果字段**)
3. 更新"当前假设"区为下一轮的假设
4. 如果本轮排除了某个方向 → 追加到"已经排除的方向"
5. 如果本轮做了重要架构决策 → 追加到"设计决策记录"

## 步骤 7:决定是否继续

- 如果状态变成 `[DONE] / [NEEDS_HUMAN_REVIEW] / [STUCK] / [BLOCKED] / [TOO_BIG] / [BUDGET_OUT] / [SYNTAX_BROKEN]`
  → 停止,告诉用户现在状态、原因、下一步建议
- 否则 → 询问用户:"本轮已完成,要继续下一轮吗?(回复'继续'即开启下一轮,回复'停'即暂停)"

## 通用纪律

- ❌ 不要为了过验收而 try/except: pass / try{}catch{} 吞异常
- ❌ 不要捏造检查结果,所有"通过/失败"必须基于真实命令输出
- ❌ 不要在没有更新 STATE.md 的情况下结束本轮
- ❌ 不要一次性改超过 {{FILES_PER_ROUND}} 个文件
- ❌ 不要修改验收命令或测试断言来"作弊"
- ✅ 改前必要时先备份(对配置文件、数据文件)
- ✅ 每改一个文件后立刻做局部语法检查
- ✅ 每一步操作前先用一句话告诉用户你要做什么
- ✅ 遇到不确定的事,宁可停下来问用户,不要猜
