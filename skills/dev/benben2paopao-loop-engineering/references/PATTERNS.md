# PATTERNS.md — 五种 LOOP 模式参考卡

> 出自 LOOP1.MD 第 330-340 行。Agent 在 skill 步骤 3 用这份卡选择适合用户任务的模式。
> 选择不同模式会影响 GOAL.md 的"成功条件"和 PROMPT.md 的"自检逻辑"如何生成。

---

## 模式选择决策树(Agent 内部用)

```
用户的任务 → 它的"成功"能不能用一条命令的退出码判断?
├── 能 → 命令是哪种类型?
│         ├── 跑测试(pytest/npm test/go test/...) → 【模式 1:测试驱动】
│         ├── 类型检查/编译(tsc/mypy/cargo build) → 【模式 2:编译器驱动】
│         └── Lint/格式化(eslint/ruff) → 【模式 2 变体】
│
└── 不能 → 任务的反馈信号是什么?
          ├── 来自人工 review(评论、审批) → 【模式 3:Review 驱动】
          ├── 来自运行时(日志、堆栈、HTTP 响应) → 【模式 4:运行时调试】
          └── 来自视觉/UI(截图、对比稿) → 【模式 5:产品迭代】
```

---

## 模式 1:测试驱动 Loop

**核心信号**:测试通过 / 失败
**停止条件**:目标测试全部通过
**典型场景**:Bug 修复、回归测试、数据转换逻辑、API 实现
**适合首次使用 LOOP 的用户**:✅ 强烈推荐(信号最清晰、最容易跑通)

**生成 GOAL.md 时**:
- 成功条件 = `<测试命令>` 退出码为 0 且无 FAIL/Error
- 范围 = 只允许改 src/ 和 test/

**生成 PROMPT.md 时**:
- 步骤 2 自检 = 跑测试命令、解析输出
- 步骤 4 执行 = 改源码后立刻跑测试

---

## 模式 2:编译器驱动 Loop

**核心信号**:类型错误数量、编译错误列表
**停止条件**:类型/编译零错误
**典型场景**:TypeScript strict 迁移、依赖升级后的破坏性修复、大规模重构、Rust borrow check 修复
**适合首次使用**:✅ 推荐(信号也很清晰,但错误数量大时容易卡住)

**生成 GOAL.md 时**:
- 成功条件 = `<类型检查命令>` 退出码为 0
- 进度指标 = 错误数量从 N 单调下降到 0
- 添加额外停止条件:"如果连续 3 轮错误数没下降 → STUCK"

**生成 PROMPT.md 时**:
- 每轮先记录错误数量、收敛趋势
- 优先修能"一改修一片"的根因错误,不要逐个修表面错误

---

## 模式 3:Review 驱动 Loop

**核心信号**:人工 review 评论
**停止条件**:所有评论被处理或有据可查地忽略
**典型场景**:PR review 后的机械性跟进、架构师批注的实施
**适合首次使用**:🟡 不推荐(需要 GitHub MCP 连接器,初学者太复杂)

**生成 GOAL.md 时**:
- 成功条件 = 评论列表全部状态为 resolved/wontfix
- 需要 MCP GitHub 连接器
- 建议:首次使用的人**不要选这个**,先用模式 1 把流程跑顺

**Agent 提示**:如果用户选这个但还没装 MCP,提醒用户先用更简单的模式入门。

---

## 模式 4:运行时调试 Loop

**核心信号**:日志、堆栈跟踪、HTTP 响应、错误码
**停止条件**:问题可复现 → 提出假设 → 验证修复 → 不再复现
**典型场景**:生产 bug 定位、性能问题排查、接口异常
**适合首次使用**:🟡 不推荐(需要复现脚本,初学者搭建复现环境就要花很久)

**生成 GOAL.md 时**:
- 成功条件 = "运行 `<复现命令>` 不再观察到 `<错误特征>`"
- 必须有"复现脚本"或"复现步骤"
- 必须有日志收集机制

**Agent 提示**:如果用户没有可靠的复现方式,先帮他写一个能复现的最小测试用例,然后转成模式 1。

---

## 模式 5:产品迭代 Loop

**核心信号**:截图、浏览器检查、可访问性报告
**停止条件**:与设计稿对齐、响应式正常、规范无违反
**典型场景**:落地页、UI 调整、营销组件、视觉设计
**适合首次使用**:🟠 慎用(信号是视觉的,LOOP 自检难,严重依赖人工验收)

**生成 GOAL.md 时**:
- 必须设置 `{{HUMAN_REVIEW_NEEDED}}=yes`
- 自动验收只能保证"能编译、能启动",视觉验收必须人工
- A 类硬指标(自动) + B 类人工验收(必须)双轨制
- 建议:有 webapp-testing skill 的话集成 Playwright 截图对比

---

## 通用注意事项(Agent 用任何模式都要做)

无论选哪种模式,都要在 GOAL.md 第五节加这五个**硬约束**:
1. 成功条件满足 → `[DONE]`(GUI 项目改为 `[NEEDS_HUMAN_REVIEW]`)
2. 连续 3 轮无进展 → `[STUCK]`
3. 触碰 RULES 禁区 → `[BLOCKED]`
4. 单轮超过 N 个文件 → `[TOO_BIG]`
5. 累计超过 M 轮 → `[BUDGET_OUT]`

这五个约束是 LOOP1.MD 第 366-371 行"四种故障模式"的工程化解药,任何模式都要带。
