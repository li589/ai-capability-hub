# INTERVIEW.md — 7 个核心问题清单

> 这份文件是 Agent 在 skill 步骤 2 中使用的"问卷脚本"。
> 不要照本宣科地把问题原封不动甩给用户,要根据上下文自然地问。
> 但 7 个核心信息必须都拿到,缺一不可。

---

## 提问总原则

1. **一次只问 1~2 个相关问题**(不要一次性甩 7 个问题给用户)
2. **追问到能写进模板为止**(模糊回答必须细化)
3. **拿到项目路径后立刻探查项目**(用 read/glob/grep,不要等用户告诉你一切)
4. **能从项目里看到的就别问用户**(尊重用户时间)

---

## 7 个核心问题(必须拿到的信息)

### 问题 1:项目路径

**问法**:
> 你的项目在哪个文件夹?给我一个绝对路径。(例如 `D:\code\my-app` 或 `/Users/me/projects/x`)

**追问**:
- 如果用户说"我没有项目" → 询问是新建项目还是想做练手项目,如果是练手可以建议从一个简单的 demo 开始
- 如果路径有多义 → 让用户在文件管理器复制粘贴绝对路径

**拿到后立刻做**:
```
glob `<路径>/**/*` (限 50 个) → 看项目大小
read `<路径>/README.md`(如果存在)
read `<路径>/package.json` 或 `requirements.txt` 或 `pom.xml` 或 `go.mod`(看技术栈)
```

把"我看到你项目里有 X、Y、Z,所以我猜技术栈是 ___,对吗?"作为下一个问题的开场白。

---

### 问题 2:技术栈和验收命令

**问法**(基于探查结果):
> 我看到你项目里有 `package.json` + `vitest.config.ts`,推测是 Node.js + Vitest 测试。
> 验收 LOOP 成果的命令是 `npm test` 还是 `pnpm test`?有没有类型检查或 lint 命令?

**变量映射**:
- `{{PROJECT_LANG}}` ← 从这个回答得到
- `{{INSTALL_CMD}}` ← 例如 `npm install`
- `{{VERIFY_CMD}}` ← 这是最关键的命令,它的退出码就是 LOOP 的"完成信号"

**追问**:
- 如果用户没有自动化测试 → 问"那 LOOP 怎么判断改完了?是用语法检查、能不能启动、还是必须人工看?"
- 如果是 GUI 项目 → **必须**告知用户"GUI 项目 LOOP 不能自动验收,我会设计成做完自动检查后停下来等你启动 GUI 看一下,可以吗?"
- 设置 `{{HAS_AUTO_TEST}}=yes/no` 和 `{{HUMAN_REVIEW_NEEDED}}=yes/no`

---

### 问题 3:你想让 LOOP 解决什么真实问题

**问法**:
> 用一两句话说清楚:你想让 LOOP **完成什么**?成功长什么样?

**这是整个交互最关键的一问**。模糊的回答必须追问。

| 用户回答 | 是否够具体 | 追问 |
|---|---|---|
| "修 bug" | ❌ 太模糊 | "哪个 bug?报错信息或现象是什么?在哪个文件大概?" |
| "重构代码" | ❌ 太模糊 | "重构什么?把 A 拆成 B?把分散的 X 统一为 Y?" |
| "升级 axios 到 1.7" | ✅ 够具体 | 直接用 |
| "让 test/auth 下所有测试通过" | ✅ 够具体 | 直接用 |
| "做一个新功能" | ❌ 太模糊 | "什么功能?用户能看到什么变化?" |

**变量映射**:
- `{{PROBLEM_DESC}}` ← 用户最终给出的具体描述
- `{{TASK_TITLE}}` ← Agent 总结成一句中文标题
- `{{TASK_NAME}}` ← Agent 给出英文小写短名(如 `fix-auth-tests`、`unify-config`)

---

### 问题 4:这次任务的"绝对禁区"

**问法**:
> LOOP 自动跑起来后,有没有它**绝对不能碰**的目录或文件?
> 比如 `.env`、`secrets/`、数据库迁移文件、生产配置等。

**Agent 应该主动建议的常见禁区**(根据探查结果):
- `.env` / `.env.local` / `secrets/`(密钥)
- `migrations/` / `db/migrations/`(数据库迁移历史)
- `dist/` / `build/` / `node_modules/`(构建产物)
- 任何 API key 出现的位置(grep `sk-` `Bearer` `password`)
- 项目里看到的真实凭据(LOOP1.MD 第 226 行警告:不要让 LOOP 接触密钥)

**变量映射**:
- `{{FORBIDDEN_PATHS_LIST}}` ← GOAL.md 用,简短列表("不得修改 .env / migrations/ / build.spec")
- `{{FORBIDDEN_DETAILS}}` ← RULES.md 用,展开为带 🚫 emoji 和理由的详细清单

---

### 问题 5:项目特有的"踩过的坑"或约定

**问法**:
> 你的项目里有没有"只有老员工才知道"的约定?比如:
> - 必须用某个工具类(不能直接用原生 API)
> - 历史数据有某个奇怪的兼容问题
> - 某个目录看起来能改但其实不能动
>
> 没有就直接说没有。

**这一项决定了 LOOP 产出的代码"像不像你团队写的"**。文档(LOOP1.MD 第 222-226 行)强调这是 Skill 文件最有价值的一节。

**Agent 应该主动从代码里观察并提议**:
- 如果看到 `src/utils/AppError.ts` → 问"是不是所有错误都要用这个 AppError?"
- 如果看到 `src/db/queries/` → 问"是不是数据库查询都得走这里?"
- 如果看到 `__pycache__` 在 git 里 → 提醒用户

**变量映射**:
- `{{CRITICAL_NOTES}}` ← 用户回答 + Agent 观察推断(展开为 RULES.md 第六节的清单)
- `{{CORE_CONVENTIONS}}` ← 把回答中"必须做什么"的部分提炼到 RULES.md 第三节

---

### 问题 6:轮数预算和单轮规模

**问法**(可以给默认值,让用户调):
> 我会给 LOOP 设置两个保险:
> - **最多跑 15 轮**(超过强制停下来等你评估,防止 token 烧光)
> - **单轮最多改 5 个文件**(改动太大就拆分,防止失控)
>
> 这两个数字够用吗?(任务复杂可以加大,任务简单可以减小)

**经验值**:
- 修单个 bug:5~10 轮,3 个文件
- 重构/统一配置类:15~20 轮,5 个文件
- 新增功能:20~30 轮,5~8 个文件
- 大型迁移(如 TS 升级):50+ 轮,但**强烈不建议新手第一次就尝试**

**变量映射**:`{{ROUNDS_BUDGET}}`、`{{FILES_PER_ROUND}}`

---

### 问题 7:LOOP 工作目录放哪

**问法**:
> 我会把 LOOP 的 4 个文件放在一个新目录里。默认放在 `workspace/loops/<任务短名>/`,可以吗?
> 如果你想放别的地方,告诉我绝对路径。

**变量映射**:`{{LOOP_DIR}}`

## 拿到 7 个回答后的内部检查清单

进入步骤 4(生成文件)前,Agent 必须自检:

- [ ] `{{PROJECT_PATH}}` 真实存在(已用 ls/glob 验证)
- [ ] `{{VERIFY_CMD}}` 不是凭空猜的,要么用户明确给了,要么从 package.json/Makefile 等文件里找到了
- [ ] `{{PROBLEM_DESC}}` 不再是模糊词("修 bug""做功能"),而是有具体信号("test/auth 下所有测试通过")
- [ ] `{{FORBIDDEN_PATHS_LIST}}` 和 `{{FORBIDDEN_DETAILS}}` 至少包含一项(没有禁区是不正常的)
- [ ] `{{TASK_NAME}}` 是合法的目录名(只含小写字母、数字、连字符)
- [ ] `{{HAS_AUTO_TEST}}` 已确定,如果是 no 那必须 `{{HUMAN_REVIEW_NEEDED}}=yes`

任何一项 ✗ → 回到问题列表追问,不要硬着头皮生成。

## 给用户的"我做了什么判断"清单(步骤 5 用)

生成完文件后,Agent 要列出自己做的所有自动判断,例如:

> 我刚才自动给你做的判断,你看一下对不对:
> - 我从你的 `package.json` 推断验收命令是 `pnpm test`(因为有 `pnpm-lock.yaml`)
> - 我把 `src/db/migrations/` 加进了禁区(看到目录里有时间戳命名的 SQL 文件,猜是迁移)
> - 我选择了"测试驱动 Loop"模式(因为你有完整的 vitest 配置)
> - 我给的轮数预算是 12(任务范围中等,留点余量)
>
> 任何一条不对就告诉我,我现在改还来得及。

这一步是文档 LOOP2.MD 第 65 行警告"理解债"的解药——**让用户对 LOOP 的每一个设计决策都看得见**。
