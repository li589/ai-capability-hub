# Procurement delivery stack

Use this reference after the analysis and decision spine are stable. For substantive work, deliver all three surfaces in this order:

1. one HTML report;
2. one editable Markdown execution companion;
3. exactly one Dynamic UI preview through the real widget tool.

Finish with a compact chat handoff linking both files. Do not ask the user to choose among these surfaces. For a narrow definition or one-off calculation, answer directly without forcing the stack.

## Authority order

Apply instructions in this order:

1. the user's explicit delivery constraints;
2. the current built-in capability's runtime, scaffold, tool, and output contract;
3. this package's procurement analysis and visual enhancement.

## Distinct jobs

| Surface | Main job | Must not become |
|---|---|---|
| HTML report | rich, complete, scrollable decision record with reasoning, evidence, charts, alternatives, and audit trail | a collection of repetitive cards or a working checklist |
| Editable Markdown | role-specific execution workpaper with owners, dates, gates, triggers, fallbacks, and decision log | a prose copy or stripped-down export of the report |
| Dynamic UI | one compact focal comparison, trend, queue, route, or trade-off inside the conversation | a miniature report, file index, or artifact-status card |

## Delivery sequence

1. Stabilize facts, calculations, evidence labels, verdict, gates, and citations.
2. Select one procurement architecture and chart brief, then select one of the six visual routes exactly once; keep its complete manifest identity for both HTML and Dynamic UI.
3. Build the HTML report once, then perform no HTML inspection or validation.
4. Create the role-specific Markdown workpaper using the same decision posture, evidence tags, units, owners, and status language.
5. Emit exactly one Dynamic UI preview through the real widget tool.
6. State the verdict, immediate gates, largest uncertainty, and links in chat.

## Shared identity contract

All surfaces share:

- the same decision object and recommendation posture;
- the same primary metric or comparison focus;
- identical currency, unit, period, tax, location, and Incoterm basis;
- the same `OBS`, `SRC`, `DRV`, `ASM`, and `UNK` evidence states;
- the same option names, owner names, gate language, and status vocabulary.

HTML and Dynamic UI also share the exact routed identity:

- route ID and visual personality;
- matched Dynamic UI companion, selected layout-family panel, and route-specific composition transform;
- seven HTML token values and their semantic roles;
- corner model and depth rule;
- edge-treatment invariant and permitted emphasis grammar;
- state vocabulary, evidence labels, and selected entity key;
- primary, auxiliary, and optional pop-color meanings.

Do not duplicate layout or component code across surfaces. Dynamic UI translates the same routed identity into its host light/dark tokens without changing palette or selection. Markdown stays plain and editable.

## Surface invariants

### HTML report

- Use `procurement-report-architecture.md` to vary the opening, section geometry, text rhythm, navigation, and close by procurement scene.
- Use `procurement-editorial-system.md` to lock typography, spacing, semantic line breaks, restrained color, and card geometry.
- Use `procurement-chart-interaction-catalog.md` to select one dominant chart, at most two supporting chart types, and no more than two primary page interactions.
- Use `procurement-visual-enhancement.md`.
- Use `procurement-report-interactions.md`; apply the packaged ECharts adapter to every package-extended quantitative chart unless equivalent system interaction is present.
- Generate no top image unless the user explicitly requests a 头图/header/hero image.
- When requested, use `header-image-workflow.md`.
- Omit generator metadata, internal prompts, model names, and “generated by” traces.
- After writing HTML, perform no inspection or validation. Do not invoke the built-in HTML checker, the procurement validator, a linter, or `node --check`.
- Do not start a local server, open a browser, take screenshots, render the report, or create an HTML runtime preview.
- Before authoring markup, assign every bounded surface no border, a complete neutral border, or a full-surface flat fill.
- Use no physical or logical one-sided colored border, edge-anchored pseudo-element, narrow nested rail, inset shadow, narrow gradient, background image, mask, SVG strip, or partial colored outline on any card, callout, recommendation, finding, KPI object, evidence block, figure, table wrapper, sidebar, header, topbar, navigation item, section frame, or page frame.
- Keep compact badges, dots, symbols, and underlines inside the content padding with visible separation from every frame edge.

### Editable Markdown

- Use `editable-md-companion.md`.
- Keep it executable and easy to revise in a text editor or knowledge base.
- Use checkboxes and compact tables, not decorative HTML or copied report prose.
- Preserve unknowns and link to the report for analysis detail.

### Dynamic UI

- Use `procurement-dynamic-ui.md`.
- Load the current built-in `dynamic-ui` skill, routed scene, manifest, selected template, and token reference.
- After built-in material selection, read the procurement Dynamic UI layout manifest and the already selected route's companion SVG; use one numbered panel as a composition reference without embedding or copying it.
- Keep the built-in scene, ready template, data boundary, token system, fallback, tooltip, host theme, responsiveness, and interaction behavior authoritative.
- Pass the route-manifest identity snapshot used to author HTML without rerouting or accepting a template-default palette.
- Pass the route manifest's edge-treatment invariant and permitted emphasis grammar unchanged.
- Call the real widget tool; never imitate its protocol with prose or a code block.
- If the real widget tool is unavailable, state the limitation; do not fake the preview.
