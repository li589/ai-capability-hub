# 行业研究团队

这是唯一可调用的行业研究 Skill。六个研究维度、研究规划、报告撰写和关键核查都作为包内功能存在；九个专业阶段保持不变，但专业阶段不等于独立任务。只有宏观政策、市场规模、产业链、竞争格局和重点企业五项联网研究创建内部任务，研究规划、趋势综合、报告撰写、关键核查和最终回复都由主 Agent 直接完成。后台只交换必要的 Markdown 文件，不维护业务 JSON、证据索引、状态机或固定依赖图。每个联网专题在同一个专业任务内完成搜索、页面核实、一次成稿和一次轻量校验，不另建证据文件或第二组成稿任务。

## 路径约定

加载本 Skill 后，将加载结果中的 `Skill Path` 所指目录记为 `<SKILL_ROOT>`；如果返回的是 `SKILL.md` 文件路径，则取其父目录。开始研究时用一次 `pwd` 取得当前 Workspace 的真实绝对路径，记为 `<WORKSPACE_ROOT>`，并把本次研究目录创建在 `<WORKSPACE_ROOT>/work/` 下，将其真实绝对路径记为 `<WORK_DIR>`。不得把工作目录创建在用户主目录、Skill 安装目录、`.trae-cn/work` 或临时目录，也不把这些路径设置为需要跨工具调用保存的环境变量。

文中的 `<SKILL_ROOT>`、`<WORKSPACE_ROOT>`、`<WORK_DIR>` 及其他尖括号内容都是运行时占位符。每次工具调用和五个基础研究任务创建前，必须替换为真实绝对路径并用引号包住；不得把占位符原样传给工具。五个基础研究任务都必须同时收到已经解析的 Skill 根目录和工作目录。

## 固定步骤

九个专业阶段名称为：

1. 研究规划
2. 宏观与政策环境分析
3. 市场规模测算
4. 产业链分析
5. 竞争格局分析
6. 重点企业研究
7. 趋势、机会与风险研判
8. 研究报告撰写
9. 关键事实与引用核查

九个名称是用户可见的工作进度，不要求创建九个执行单元。只有第 2 至第 6 步各创建一个内部研究任务，并作为同一批并行启动；第 1、7、8、9 步不得创建内部任务。专业阶段摘要不得添加行业名、冒号、“重新取证”“补充研究”“修订”或其他前后缀。每个联网研究任务内部直接完成资料核实、专题成稿和轻量校验；任务未生成目标专题稿时不自动重跑。

## 路由

- 用户调用本 Skill 且没有限制研究维度，或明确要求完整、全面、系统或全景研究：运行六个研究维度。
- 用户明确要求两个以上有限维度：只运行这些维度，不扩成全套。
- 用户只要求一个维度：只运行对应的包内研究步骤，再完成报告撰写和关键核查。
- 普通“研究”“报告”“深度”等词不能扩大用户列出的范围。

包内方法对应：宏观与政策 → `references/macro-analysis.md`；市场规模 → `references/market-sizing.md`；产业链 → `references/chain-analysis.md`；竞争格局 → `references/competition-analysis.md`；重点企业 → `references/company-analysis.md`；趋势机会风险 → `references/trend-analysis.md`。这些文件没有 Skill frontmatter，不得通过 Skill 工具调用。

## 开始与工作目录

第一条用户可见消息只写：

> 正在明确研究对象、地域、时间范围和需要回答的问题。

随后用一次 `pwd` 取得 `<WORKSPACE_ROOT>`，再用系统命令取得实际日期和时间，创建唯一的 `<WORKSPACE_ROOT>/work/industry-research-<系统时间>-<主题>/`。正常流程只使用：

```text
plan.md
research-card.md
notes/macro.md
notes/market.md
notes/chain.md
notes/competition.md
notes/companies.md
trend-context.md
notes/trends.md
draft.md
editorial-context.md
editorial.md
review.md
<报告标题>.md
<报告标题>.html
delivery-context.md
```

## 研究规划

研究规划由主 Agent 直接执行，不创建内部任务。完整读取一次 `<SKILL_ROOT>/references/planning.md`，先按逐字用户请求解析行业、地域、时间和包含排除边界。只有完整六维、研究对象仍是宽行业且用户没有给出足够的当前变化线索时，才在一次 WebSearch 工具调用中并行提交最多三条动态查询；不得 WebFetch、补搜或重试。其他请求跳过发现。搜索结果只压缩为 `research-card.md` 中最多五条“尚未核实”线索，随后直接写入 `plan.md` 与 `research-card.md`，不复述搜索结果、模板或规划过程。写入后只运行一次：

```bash
python3 "<SKILL_ROOT>/scripts/check_scope.py" \
  --work-dir "<WORK_DIR>" \
  --expected-date "<系统日期>"
```

检查失败时直接说明规划未能形成，不自动再次调用规划步骤。检查通过后，发送一段清楚的范围摘要，写明研究对象、包含和排除边界、地域、资料截止日、观察期、实际专题、用户指定企业或企业选样原则、准备核实的重点方向和下一步；不得把规划前发现线索说成已经确认的行业结论，不计算字符数。

## 六个研究维度

完整研究同时启动五个基础研究任务：“宏观与政策环境分析”“市场规模测算”“产业链分析”“竞争格局分析”“重点企业研究”。五个任务互不等待，任一项资料不足不阻止其他项完成。

五个任务都逐字复制下面四行，只替换路径，不追加行业提示、来源名单或临时规则：

```text
1. 当前 Skill 根目录为 `<SKILL_ROOT>`，工作目录为 `<WORK_DIR>`；一次完整读取 `<internal-method-path>`、`<SKILL_ROOT>/references/source-selection.md` 和 `<SKILL_ROOT>/references/visualization.md`。
2. 一次读取 `<WORK_DIR>/plan.md` 和 `<WORK_DIR>/research-card.md`，只研究既定范围并只写入 `<output-path>`；不得创建其他研究文件。
3. 规划发现已运行时首批最多两次定向搜索，已跳过时最多三次；核心问题未回答才进行唯一一次补充搜索，两批最多打开六个页面，重要问题不触发补搜。最后一批页面返回后，下一条响应直接调用一次 `Write` 写入专题稿或 `INSUFFICIENT:`。
4. 派生值只运行 `<SKILL_ROOT>/scripts/calculate_metric.py`；写完运行一次 `validate_note.py`，失败时按错误集中修正一次并复检，不重新搜索，也不读取任何运行时脚本源码；图表错误不能直接修正就删除图表。完成后只返回两到三句业务摘要。
```

专题初稿直接在 `Write` 参数中形成。任务卡负责研究流程，专题方法只负责业务问题，来源规则只负责证据采用，可视化规则只负责 Agent 的图表选择和写法；三处不得重复描述流程。

五项结束后，发送一次可独立理解的业务总结，实际说明政策或环境判断、规模口径或关键数字、产业链结构、竞争结构、代表企业差异和重要限制；不能只说“五项已完成”。

随后运行一次：

```bash
python3 "<SKILL_ROOT>/scripts/extract_context.py" \
  --work-dir "<WORK_DIR>" \
  --output "<WORK_DIR>/trend-context.md"
```

趋势、机会与风险研判由主 Agent 直接执行，不创建内部任务。完整研究只完整读取一次 `references/trend-analysis.md`，并按其后置综合模式读取 `plan.md`、`trend-context.md` 和 `references/visualization.md`；不得读取包含未核实发现线索的 `research-card.md`。禁止 WebSearch、WebFetch、新增事实、重新判断来源或重新计算前序数字，读取后直接一次写入 `notes/trends.md` 并按方法运行一次轻量校验。五个研究任务的完整正文、搜索结果和工具过程不得带回主 Agent 上下文。

定向研究只运行用户要求的包内研究阶段。多个互不依赖的基础专题仍各创建一个任务并行；包含趋势时，先完成所选基础专题并提取紧凑上下文，再由主 Agent 运行趋势。用户只要求趋势时，也由主 Agent 按 `trend-analysis.md` 的定向专题模式有限搜索后直接写稿，不创建内部任务、证据文件或额外资料核实任务。定向研究组装时不使用 `--require-full`。

## 专题结果约定

- 核心问题已回答：专题以 Markdown 标题开始，在正文写局部限制。
- 核心问题未回答：第一个非空行必须以 `INSUFFICIENT:` 开头，随后可保留已经确认的有限事实和资料边界。
- 最终事实必须来自实际打开的具体页面；搜索摘要只能发现候选来源。
- 专题只写研究结果，不写搜索批次、页面数量、校验动作、工具过程或内部状态。
- 只有资料缺口会明显改变本章判断时才保留一段 `> 资料边界：...`；指标定义、地域、时间和数据性质紧跟对应数字说明。

总入口不因 `INSUFFICIENT` 自动重跑专题，不跨专题补写，也不读取或编辑五个基础专题稿。只有用户单独要求趋势且没有可复用的基础专题时，主 Agent 才按趋势定向专题模式进行有限搜索。

## 报告生成与核查

所有已规划专题进入终态后，研究报告撰写由主 Agent 直接执行，不创建内部任务。完整读取一次 `<SKILL_ROOT>/references/composing.md`，使用已经解析的 Skill 根目录、工作目录、报告标题和完整/定向模式，只运行一次确定性组装和一次紧凑上下文提取，然后只把核心结论、行业概览和结论与展望一次写入 `editorial.md`。六章正文、图表声明、引用和参考资料保持组装结果，不由撰写步骤重新读取、组织或全文改写。

报告撰写结束后进入“关键事实与引用核查”，不创建新的审稿 Agent。总入口只运行：

```bash
python3 "<SKILL_ROOT>/scripts/finalize_report.py" \
  --work-dir "<WORK_DIR>"
```

该命令一次完成局部编辑合并、引用整理、阻断性机械检查、以报告一级标题命名的 Markdown 和 HTML、`delivery-context.md` 及内部 `review.md` 生成。文件名必须包含用户 query 对应的研究主题，形式为 `<研究主题>研究报告.md` 与 `<研究主题>研究报告.html`，不得生成 `report.md` 或 `report.html`。命令成功后不再读取完整报告、重新核查、重新发布或修改专题；失败时不搜索、不返工专题、不手写替代报告。只有命令成功退出、`review.md` 不是阻断状态、`delivery-context.md` 中列出的 HTML 存在且有效、交付上下文非空时才可交付。内部状态码不得出现在用户可见内容中。

## 图文报告

完整研究仍覆盖六个研究维度，但报告按阅读逻辑输出七个主体章节：行业概览、市场规模、产业链与关键瓶颈、竞争格局、重点企业、宏观与政策环境、趋势机会与风险；并包含核心结论、结论与展望和可点击参考资料。行业概览由已有专题综合生成，不增加研究步骤或搜索。HTML 为主要阅读版：

- 使用内嵌 ECharts 展示可靠且可比的数据；没有可比数据就不画。
- 每个专题最多包含两个图表或结构图；这是上限，不是数量目标、额外检索目标或发布门槛。
- 研究 Agent 根据数据关系选择折线、面积、条形、环形、散点或区间图，并写明图表类型；发布程序只校验数据并渲染。
- 研究 Agent 根据业务关系选择产业链、时间线、竞争矩阵或企业比较，HTML/CSS 只负责呈现。
- 多对象、多字段比较优先使用普通表格；不把长段落塞进卡片。
- 不使用 Mermaid、外部 CDN 或手写第二份 HTML。
- 图表数字必须在正文或表格中出现并带引用。
- 行业概览和各章不根据行业名称调用预设标题、图表或主题模板。

## 最终回复

可交付时只读取一次 `review.md` 判断分支，再只读取一次 `delivery-context.md`；不回读完整最终报告、专题稿或草稿。最终回复始终使用普通 Markdown，不加载富文本 Skill、不调用富文本工具，也不绘制第二套图表。

管理摘要必须可独立阅读：先说明研究范围和总体判断，再按最影响用户判断的三至五个主题组织主要发现；只在确有比较价值时使用 Markdown 表格，不固定为六行表格、六个分区或“先表格后图表”。机会、风险、成立条件和观察信号放在相关判断附近，局部资料限制只与受影响的事实一起说明。最后只附一行：

```text
[查看 HTML 报告](computer://<WORK_DIR>/<HTML 文件>) · [Markdown 可编辑版](computer://<WORK_DIR>/<Markdown 文件>)
```

两个链接必须逐字使用 `delivery-context.md` 的“HTML 文件”和“Markdown 文件”，不得自行缩写、改名或回退为 `report.*`。管理摘要只复用交付上下文中已经核实的事实、数字、计算和引用，不新增研究或另一套结论。内部为可交付状态时不宣布“通过核查”“有条件通过”，也不评价报告质量。正式产物不可交付时不输出无效链接，直接用普通 Markdown 说明当前公开资料尚不足以支持完整判断，并概括仍可使用的信息和关键缺口。

## 用户可见语言

每个专业步骤在执行期间保持安静；该步骤完成后只发送一次业务摘要。步骤之间的进度只说上一步得到的业务发现、当前研究什么和下一步解决什么。不得展示路径、命令、搜索次数、文件操作、内部规则或推理，也不得使用 bootstrap、契约、Schema、DAG、Wave、Context、SubAgent 等内部词。`PASS`、`PASS_WITH_LIMITS`、`BLOCKED`、`SUPPORTED`、`CORRECTABLE`、`UNSUPPORTED` 是内部状态码，不得出现在任何用户可见的步骤摘要、进度或最终回复中。
